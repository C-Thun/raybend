# 计划：图片元信息（方向 / 宽高）采集 + tile 展示形态重做

> 状态：**待评审**。人类已给出展示形态的方案，本计划在采纳的基础上做合理性核对与细化。
> 前置事实：目前 tiles 是**库外直读目录**（导入工作流），浏览工作流还没做 —— 所以本计划
> 既要能用在「库外目录 / SD 卡」，也要为「库内」预留信息位。

---

## 一、Context（为什么做）

1. **方向没被应用**：渲染侧（`thumbnail/render.rs::apply_orientation`）**支持**摆正，
   但热路径 `render_now(&db, path, size, now)` **没有 orientation 参数** →
   竖拍照片在网格里是**躺着**的（人类截图 P1000025 就是）。这是明摆着的 bug。
2. **宽高比无处表达**：现在格子固定 `3:2` + `object-fit: cover`（裁切）。
   相机五花八门（M43 是 4:3、竖拍变 3:4），裁切让「一眼看出横竖」这件事彻底丢失。
3. **信息展示结构死**：上一版是「上下两半」的固定结构（信息条钉在底部），
   图片只吃上两角圆角；这种结构天生无法适应宽高比变化。人类已经拍板新形态（见 §四）。
4. **行高必须等高（硬约束）**：tile 尺寸可调 + 左列宽度可拖 → 行内成员会变；
   若行高不等，拖动时界面会「扭成迪斯科舞厅」。**因此否决动态等高（justified rows）**，
   改「统一正方外框 + 内部保比例居中」。

## 二、拿信息：两条路线的实测评估

### 2.1 实测数据（本机，已跑）

| 做法 | 样本 | 结果 |
| --- | --- | --- |
| **只读文件头**（JPEG SOF 宽高 + EXIF 方向，Python 等价实现） | ext4 原生盘 40 张 | **0.022 ms/张 → 46,000 张/秒**（解析成本可忽略） |
| 同上 | `/mnt/c`（9p 跨系统挂载）174 张 | 5.35 ms/张 → 187 张/秒（**全是挂载层开销**，不是解析） |
| `identify`（ImageMagick，**会解码整图**） | 60 张 | 13.2 s → **220 ms/张** |
| 我们现有缩略图（M1-7 基线） | — | 18.9 张/秒（≈53 ms/张） |

**结论**：

- 读头 ≈ 缩略图解码的 **1/1000**（原生盘）/ 1/10（慢挂载）。**完全可以对所有条目先读一遍**。
- 慢介质（SD 卡 / 网络盘）上真正的成本是**寻道**，不是解析 → 要**并行 + 渐进**：
  先出网格（用默认比例占位），元信息到了再修正图片框（**不会重排网格**，见 §四.5）。

### 2.2 路线 A：直读（不落盘、不缓存）

- 优点：零状态、天然不会过期、实现最小。
- 缺点：**每次进入目录都要再付一次**。重复来回切目录时（选目录 → 看几张 → 退出来 → 再进去）
  会反复扫盘。

### 2.3 路线 B：**进程内内存缓存**（采纳人类判断，采用）

人类判断：读头既然这么快（原生盘 0.022 ms/张），**不值得为它落盘**；
真正要避免的只是「反复切目录时重复扫盘」。于是：

```text
Rust 侧会话级缓存（Mutex<HashMap<目录, DirMetaEntry>>，进程退出即丢）
  DirMetaEntry {
    inserted_at: Instant,                     ← 过期基准
    entries: HashMap<相对路径, PhotoMeta>,     ← 读头结果
  }
  PhotoMeta { file_size, mtime_ms, width, height, orientation, aspect_clamped }
```

- **过期**：默认 **6 小时**（人类指定）—— 防的只是「一直不关应用」的极端情况。
- **过期后的再利用**：重进目录时先拿一次 `read_dir`（本来就要做，很便宜），
  逐条比对 `(file_size, mtime_ms)`：**只有变了的才重读头** —— 于是「过期」不等于「全量重扫」。
- **容量**：条目本身极小（一条 ≈ 100 字节），但目录可能很大 →
  设上限（例如 20 万条 / 256 个目录）按最近使用淘汰，防止浏览几百个目录后无限增长。
- **不做**：磁盘 db、指纹哈希（那些是为跨进程持久化才需要的 —— 不落盘就不需要）。
- **实测口径的诚实说明**：上表数字是 **JPEG** 量的。PNG（IHDR）与 RAW（TIFF IFD / 嵌入预览目录）
  同样是「只读头、不解码」，量级应当一致，但**要在实现时补测**（Step 1 的一部分）。

### 2.4 第三个选项（评估后否决）：丢给浏览器读

让 webview 自己 `new Image()` 读 `naturalWidth/Height`：

- **webview 读不到本地任意路径** → 要么开 Tauri 的 asset 协议 + scope（安全面变大），
  要么把文件字节经 IPC 拷进前端（**每张一次全量拷贝**，RAW 更不可能）。
- 且它拿不到 RAW 的嵌入预览尺寸，也拿不到 EXIF 方向。
- 结论：**否决**。元信息一律走 Rust 侧。

### 2.5 库内 / 库外怎么统一

- **库外**（导入工作流、SD 卡）：用 §2.3 的**会话级内存缓存**。
- **库内**（浏览工作流，将来）：资产元信息本来就在 `catalog.db` 里 → 直接读，**不碰这套缓存**。
- 两者对上层的接口**一致**：`照片 id → { width, height, orientation, aspect }`，
  前端只认这个接口（今天由 cache db 提供，将来库内由 catalog 提供）。

## 四、展示形态（采纳人类的方案 + 我的核对点）

### 4.1 结构（新）

```text
┌────────────────────┐  ← 外框：**正方形**圆角矩形，边长 = tiles 尺寸档（9 档）
│   ╭──────────────╮ │     ⚠️ 外框 `overflow: hidden` —— **两条信息条必须被外框的圆角裁到**
│   │              │ │     默认**无边框、无底纹**（不占视觉）
│   │    图片      │ │     库内且有颜色标记时：外框是**该颜色的低浓底纹**
│   │              │ │  ← 图片：保比例、在外框内**上下左右居中**、四角圆角
│   │              │ │     留白 = --tile-pad；超过 3:1 / 1:3 的部分**居中截取**
│   ╰──────────────╯ │
│ ▒▒ 文件名 · 类型 ▒▒ │  ← 底部信息条：**覆盖在图片之上**（不是占位、不缩图）
└────────────────────┘
```

**两条信息条的定位纪律（人类 2026-09-16 明确）**：

- 它们是**覆盖层**：贴在图片之上，图片**始终填满外框内空间**（只留 `--tile-pad`），
  **绝不**为了给信息让位而缩小图片（选中/指向时图片尺寸不变）。
- 图片偏宽时（3:2 这类），信息条会有一部分落在图片之外、压在外框空白上 ——
  所以它**锚在外框的上下边缘**，而不是图片的边缘（同一行所有 tile 的信息条对齐）。
- 它们**吃到外框的圆角**：由外框的 `overflow: hidden` 裁出来（上条上圆角、下条下圆角）。

### 4.1.1 信息条的底纹怎么取（我的建议）

| 方案 | 评价 |
| --- | --- |
| **只用「外框底纹同色、改浓度/明暗偏移」** | ✗ 不建议单独用：外框底纹会随状态变色（指向=辅色、选中=主色、颜色标记=任意色），文字对比度跟着状态漂，迟早出现读不清的组合 |
| 只用纯白/纯黑半透明 | ✓ 稳，但会**切断**与状态底纹的视觉关系（不像「与外框底纹结合」） |
| **两层叠加（推荐）** | ✓✓ 底层 = 状态底纹（辅色/主色/颜色标记，与外框同色，所以「结合」成立）+ 上层 = **主题中性蒙层**（暗色主题压黑、浅色主题压白，透明度固定）→ 无论状态是什么颜色，文字对比度都有保证 |

新增令牌（两档密度**同值**，只随主题变，所以放在公共/主题层而不是密度块）：

```text
--tile-bar-scrim    暗色主题 rgba(0,0,0,.55) / 浅色主题 rgba(255,255,255,.72)
--tile-bar-fg       暗色主题 fg-1 / 浅色主题 fg-1（沿用前景阶梯，不另造）
```

> 不做毛玻璃（`backdrop-filter`）—— `DESIGN.md` §6 明确不做模糊，半透明平涂即可。

| 状态 | 表现 |
| --- | --- |
| **默认** | 只有图片；信息全不显示；外框无底纹（库内打了颜色标记时是**该色低浓底纹**） |
| **指向** | 外框：**低浓辅色底纹**（§5 全局规则）；底部浮出半透明信息条（文件名 + 类型 + 加锁位）；**库内**还浮出顶部一行标记区（星标 / 颜色 / 旗标） |
| **选中** | 外框底纹转**主色**；上下信息**常亮**（不再依赖悬停） |
| **库外**（导入） | 无标记区、无加锁位 —— 这些信息库外根本不存在，槽位直接不渲染 |

### 4.2 我的核对点（请确认或在批注里说）

1. **3:1 夹取只作用于网格缩略图，不作用于看图用的大图**。
   理由：看图必须看到**完整**照片（全景照片被截成 3:1 就没法看了）。
   建议：`grid` / `strip` 两档按夹取比例生成；`screen`（看图档，长边 1920）**保持原始比例**。
2. **信息条锚在外框底边 / 顶边**（不是图片边缘）：图片比例一变，锚在图片上就会上下跳；
   锚在外框上位置永远固定（同一行所有 tile 的信息条在一条线上），
   且**必须被外框圆角裁到**（外框 `overflow: hidden`）。
   它们**覆盖**图片，不挤占图片空间 —— 选中/指向时图片尺寸**不变**。
3. **颜色标记需要两个落点**：外框底纹（默认态）+ 信息条里的一个小色点（悬停/选中时底纹被盖掉，仍要能看到标色）。
4. **星标的两种形态**照你说的做：宽度够 → 5 颗（空/实）；不够 → 1 颗 + 数字；**0 星就不显示**。
5. **元信息迟到不重排**：外框是正方形、边长由尺寸档决定 → 图片框在内部变化**不影响行布局** ✓
   （这正是「统一正方外框」相对动态等高的最大好处）。迟到的比例只让图片在自己的框里长大/缩小。
   —— 所以「先出网格、再补比例」是安全的，**不需要**占位图之外的额外处理。
6. **圆角再小一点**：新增 `--tile-radius`（建议 3px；`--radius` 仍是 4px 给控件用）。
7. **`--tile-cell-w/h` 退役**，改单个 `--tile-cell`（正方边长）—— 数学更简单，
   也顺手修掉上一版「画面区写死单元格宽、被内边距顶到右边」那类错位。
