> 第一轮 `photo-organization-analysis.md` 保留为历史分析：其中“目录标签合并到照片”“上下分栏”“单组自动规则”“离线 tile 占位”已被本轮取代。
> 本轮最关键的变化：**标签分别标注照片和目录；给目录打标签只产生目录入口，不让里面的照片获得标签。**

## 1. 本轮已明确的方向

- toolsbar left 放三个无文字图标按钮，顺序为库目录、相片桶、标签；三选一，不能全关。
- 三者各自占整个 workspace left；取消上下拼接、三点分隔与面板高度比例。
- 标签面板带搜索，过滤下面的标签；按“标签 → 直接标注该标签的目录”两级显示。
- 点标签：tiles 显示当前挂载库中直接带该标签的照片；点目录：与库目录入口相同，正常浏览该目录。
- **目录标签只描述目录。** 目录中的照片不因此获得标签；不会经目录标签传播到照片筛选或自动桶。
- 相片桶为横向卡片，视觉与库卡片有区别；锁定（置顶）和 auto 排在上方。
- auto bucket 支持多组规则：组间 OR，组内 AND；每个条件类型在一组里只能出现一次。
- toolsbar mid 标签按钮右侧增加桶动作入口，承接“选中照片加入/新建桶”“当前筛选转自动桶”。
- 筛选转自动桶只保存筛选条件，编辑时明确选择库范围；当前目录、标签节点、桶的导航范围不带入（本轮已确认）。
- 新建自动桶必须弹出完整条件链；与编辑自动桶共用同一弹窗，可在其中修改条件、选择库、新增条件链（OR 组），不是只读确认。
- 点桶：tiles 展示其来自当前已挂载库的照片；未挂载库成员仍保留，不混进当前 tiles。
- 遮罩不再为目录标签服务；为后续 AI 纠错预留，首版不急于暴露此功能。
- 模块按上下两期交付：上期完成主要整理功能，下期主要完成 AI 增强；分别规划，见 §12。

仍沿用：bucket 是持久成员集合，进入即留下；管理基于照片，不引入 issue 成员或手工成员排序；过度自动入库不做。

## 2. 三入口、一个照片浏览区

### 2.1 面板选择与照片来源分开

上期实现将状态分为：

```text
leftPanel = repositories | buckets | tags
browseSource = directory(repo, path) | directTag(tagKey) | bucket(bucketId)
viewFilter = 当前照片筛选条件
```

- leftPanel 没有 none，初始库目录；重复点当前图标保持原状。图标有悬停说明、无障碍名与单选组键盘行为。
- **切换左面板只换导航面板**，不自动切换中间照片来源、不清空照片选区或筛选。点某个实际节点/卡片才切换来源；获批画稿和实现均按此行为。
- 当前来源在 tiles 的现有信息位置以名称/路径明确显示；切换左面板后仍知道当前看的是哪个目录、标签或桶。
- 三个面板保留各自的搜索文字、展开与滚动状态；照片来源及选中对象只有一份，不保留三份互相矛盾的当前选中状态。
- 同一目录出现在标签树与库目录树里时，引用同一个 `(repoId, dirKey)`。切换面板可反映同一个选中目录，但不因选中目录而强制展开目录树。
- 沉浸看图等既有模式可以隐藏整个左列，但不能把 leftPanel 设成 none；退出时恢复。
- 来源变化沿用现有选区/锚点规则；PhotoGrid 保持同一实例，不建立三套网格。

### 2.2 挂载范围

“已挂载”以仓库会话的可读状态为准：连接在线、身份核对成功且未主动卸载；不是 app.db 中所有已登记路径，也不是只等于最近点击的一个库。

标签和桶查询对挂载集合取同一份本次查询快照，逐库读取；挂载/卸载事件使相关结果重读，旧异步响应按查询版本丢弃。卸载不删除桶成员、标签关系或规则中的库 ID；也不能因查询自动重新挂载已主动卸载的库。

### 2.3 从整理照片区进入导出

从标签或桶照片区进入导出时，捕获**全部当前选中照片**的 `(repoId, assetId)`，在导出工作区现有状态条显示待入队数。上方导出画廊仍浏览当前库/目录；点击画廊中的新选择或“取消选中”会放弃这份待入队选区。选择导出预设后，现有“送入队列”动作将每张照片的**主定稿**按库分批生成快照，连同各自库根加入同一预设队列；不自动启动导出。不同库的相同整数 asset ID 绝不合并。

离线库、快照变化或某库入队失败时，已成功条目保留在队列，未成功的照片继续留在待入队选区并显示数量/错误；库恢复后可重试。再次入队按库 ID、照片 ID 和定稿内容哈希去重。导出队列现有命令 `export.enqueue`（默认 `Enter`）与按钮走同一动作，不另设命令或热键。

## 3. 标签树的颗粒度

### 3.1 两种关联，不传播

同一个文字“旅行”可以同时关联：

```text
照片：A、B
目录：库甲/云南、库乙/海边
```

点“旅行”得到直接标注的 A、B；展开后看到两个目录。点“库甲/云南”进入云南目录，里面没有单独标“旅行”的照片也会正常显示。

**不在父标签结果中混入这两个目录的全部照片；也不把“包含打了旅行标签的照片”的目录自动列成子节点。**

建议未来 AI 属于“照片自身的来源”：直接照片集合 = 手动 + 有效 AI，扣除照片遮罩。目录始终另算：

```text
PhotoTags(p) = (Manual(p) ∪ AI(p)) − Masks(p)
DirectoryTags(d) = 直接写在目录 d 上的标签
```

照片信息、照片搜索/筛选、导出标签、auto bucket 的标签条件都使用 PhotoTags。目录标签只服务目录信息及目录导航，不给照片导出元数据写目录标签。

目录入口的浏览范围与现有库目录保持一致（包括既有子树/`_RAW` 处理），不另造“标签目录专属范围”。**浏览目录可以展示其中照片，与让它们继承标签是两回事。**

### 3.2 点击、展开、搜索

| 动作 | 左栏变化 | tiles 变化 |
| --- | --- | --- |
| 点击标签行 | 选中；有目录子节点则展开 | 查询当前挂载照片的直接标签 |
| 点击标签箭头 | 只展开/收起目录关系 | 不变 |
| 点击其下目录 | 选中这个目录，留在标签面板 | 调用现有目录导航，**不额外施加父标签条件** |
| 输入标签搜索 | 过滤标签名称 | 不变 |
| 搜索隐藏当前来源对应标签 | 隐藏该树行，保留搜索 | 当前来源不变，来源说明仍可见 |
| 再点击当前标签/目录 | 保持选中并重读 | 读取最新状态 |

“点击标签行展开”是本轮明确的标签节点行为，在面板控制层处理；不改变通用 TreeNode 的“选中不自动展开”规则，尤其不能传染到目录节点。标签的选中态被程序恢复时也不自动展开。

上期只有两级：标签 → 目录入口。目录行显示库名与目录名，完整路径保留在节点信息中；不在标签下面再复制一整棵目录树。目录关联数量一次按库聚合查询，无关联目录的标签不显示箭头；空目录只要有明确标签绑定，也可列出。

标签搜索只匹配标签名，不递归搜索目录或照片。沿用规范化文字及转义后的子串匹配；中文短词不依赖 trigram 三字下限。搜索和展开都要支持分页/虚拟化，不能输入一次就逐库数所有照片。

### 3.3 目录与照片的打标入口

建议：

- 照片沿用当前标签弹窗；拖照片到标签行只给照片添加手动标签。
- 库目录行的现有菜单增加“设置目录标签”，复用标签选择器，写目录关联。
- 标签下面的目录行菜单提供“移除此目录的该标签”，只移除关联，不删目录、不改照片。
- 目录子节点先只承担导航，不把拖照片到该节点解释成移动磁盘文件。
- 创建新词不自动给当前照片或目录打标；从明确的“设置标签”动作创建则添加到该动作的目标。
- 首版不提供跨所有离线库的全局改名/合并/删除标签；仍可管理具体照片/目录上的关联。

标签词表可以全局展示；未挂载库的目录子节点不加入本次实时树结果。某个词在挂载范围内没有照片/目录时，给出相应空态，不等同于该词从来未使用。

## 4. 数据和算法因此简化

### 4.1 文字身份与关联

继续建议以规范化文字作为 tag_key：复用 Rust 的去首尾空白、非空/长度检查、NFC、小写；不做同义词、简繁、自动翻译。app.db 提供全局输入建议；catalog 保存本库使用的文字及关联，避免单独搬库后只剩无意义的全局数字 ID。

建议逻辑结构：

```text
catalog:
  tag_terms(tag_key, display_name)
  asset_tag_sources(asset_id, tag_key, source)
    PK(asset_id, tag_key, source)
    INDEX(tag_key, asset_id, source)
  directory_tags(dir_key, tag_key)
    PK(dir_key, tag_key)
    INDEX(tag_key, dir_key)

AI 阶段预留:
  asset_tag_masks(asset_id, tag_key)
    PK(asset_id, tag_key)
```

来源目前只写 manual；AI 后续通过同一接口加入。目录不是 asset_tag_sources 的第三来源。数字 ID → 文字的旧数据迁移仍须可靠词典映射，找不到名字保留未解析旧记录，不猜名。

目录先按库内相对路径绑定属于建议：全库搬盘不改关联；外部改目录名要重新绑定，不能根据里面几张照片的移动猜测目录身份。挂载但目录路径失效时保留关联并显示不可进入；不静默删除绑定。

### 4.2 读取成本

- 标签树展开：各挂载 catalog 按 `directory_tags(tag_key, dir_key)` 读目录关联，再汇总。**无需扫描目录文件，无需 join 照片。**
- 标签父节点：按 `asset_tag_sources(tag_key, asset_id, source)` 找照片，按 asset 去重；AI 阶段在统一入口加文字遮罩。
- 给目录加/去标签：写一条目录关联，并刷新该词的目录子节点；**不遍历照片、不使照片缓存失效、不触发自动桶照片重评。**
- 给照片加标签：只影响照片关联、当前直接标签结果和依赖此词的自动规则。
- 打开目录：正常进入现有目录浏览/对盘流程，此时才读这个目录的磁盘状态。
- 每个标签旁不实时计算跨库精确照片总数；当前 tiles 总数随查询计算即可。

不再需要上一轮建议的“为了继承标签给 asset_files 增加 organization_dir_key”，也不需要目录来源的物化刷新、虚拟合并或新文件补挂标签。

现有实验仍能说明不同查询方向的取舍，但其三来源目录 join 已不对应本版模型。不能把历史 0.85–12.75 ms 直接当作本版产品指标。未来实际查询仍复用同一 store/query 与分页体系，按查询计划决定是否需要双路径。

### 4.3 遮罩预留的程度

首版预留统一 PhotoTags 查询入口、明确 source 身份、幂等来源更新 API 和以下语义；不为了未来 AI 提前摆出一组空控件，也不必现在创建无生产者的遮罩表。

- 禁止的是某张照片上的规范化文字，不是全局 tag 数字 ID，也不是目录标签。
- 遮罩保留原始来源；AI 重跑不能解除它。
- 显式手动添加同词可以解除禁止；取消禁止仅移除遮罩，有来源才重新出现。
- AI 写入只替换 AI 自己的集合，核对输入/模型版本，失败不提交半份结果。
- 标签浏览、筛选、导出和自动桶必须通过同一有效照片标签语义，防止后加遮罩时漏一个消费方。

表与 UI 到 AI 实施时走正式迁移与设计；目录标签不会使用照片遮罩。

## 5. 相片桶本体

### 5.1 一个桶可同时手动收片和自动收片

建议桶仍只有一种对象：名字、锁定状态、规则组、自动运行状态、成员。没有“普通桶不能手动变自动”或“自动桶不能手动放入”的类型墙。

- 没有规则组 = 普通桶；有规则组 = auto bucket，可暂停。
- 成员是纯集合，放入幂等，同照片命中多个规则组仍只有一份。
- 修改规则、照片失去匹配资格，都不自动退桶。
- 自动桶手动移出要同时记桶级排除，之后任何规则组都不能把它加回；手动再次放入清除排除。
- 普通桶移出没有后台回填，无需预先制造自动排除；后续升级自动桶时按新规则正常补收。
- 删除桶只删除桶/成员/规则/排除，不改照片、目录、标签或磁盘文件。
- 锁定建议仅为置顶并保护桶本体免被删除，仍允许增减成员、修改规则；暂停自动收片是独立动作。
- 删除最后一组规则要明确表现为“停止自动收片，保留已有成员”，不能把空规则解释为匹配所有照片。

### 5.2 排序和离线

建议稳定排序：**锁定桶 → 未锁定 auto 桶 → 普通桶**；锁定且 auto 的桶只出现一次，两个状态都能显示。组内按名称及稳定 ID 排，不因为后台收片、数量变化或悬停而跳位。暂停的 auto 仍在 auto 区。

桶与成员放 app.db，名单跨卸载保留；tiles 仅查询成员中当前挂载库的可读照片。卡片可显示“当前挂载 42 / 全部成员 80”，未完成可用性核对时不用假零。没有任何相关库挂载时，显示“此桶有成员，但所在库尚未挂载”，不能显示成空桶。

照片键已采用持久 `organization_uid` 加库 ID；catalog 内整数 ID 仍用于查询，显示层复合键为库 ID 加资产 ID，写入桶时再核对 UID。FileId 只服务物理文件对盘。

不默认采用上一轮的“强制按库分组”裁剪。多库照片作为同一 TilesSource 呈现，复用既有排序/按时间分组；跨库身份、分页与合并必须在数据适配层处理，不能做第二个 PhotoGrid。仅改左面板本身不会消除这部分工作量。

### 5.3 横向卡片（Pencil 稿已确认）

建议卡片强调“装了哪些照片”：

- 左侧用两张轻微错位的缩略图形成小叠片；空桶用桶图标，不用库卡片的磁盘/路径图标块。
- 中间第一行名字；第二行成员数量与来源库数量，auto 可补“2 组规则 / 已暂停”等短状态。
- 右侧锁定/auto 状态与菜单；不放磁盘路径、挂载设置齿轮。
- 叠片采用稳定的两个成员及现有缩略图；后台新增照片不反复换封面。没有缓存时用占位，不为卡片启动原片解码。
- 选择/hover、菜单、键盘、密度和颜色继续复用现有 UI 原语；只在内容结构上区别于 RepositoryCard，不复制其连接状态业务。

卡片细节见已确认的 `design/browse.pen` 和 `design/browse.md`；真机视觉仍由人类验收。

## 6. auto bucket 多规则组

### 6.1 受限的 OR-of-AND

```text
匹配 = 组1 OR 组2 OR … OR 组N
组i = 所属库条件 AND 星级条件 AND 标色条件 AND ……
```

例如：

```text
组1：库甲 AND 星级≥4 AND 标色∈{红, 黄}
组2：库乙 AND 照片标签∈{鸟, 动物}
```

“红或黄”仍是一条标色条件；“鸟或动物”仍是一条照片标签条件，不违反每种条件只能出现一次。每组建议用字段结构保存，而不是允许任意重复节点的表达式树。

建议首版复用当前控件能表达的持久条件：库集合、星级下限、标色、赞踩、照片锁状态、照片标签。标签条件读取 PhotoTags，**目录标签不参加匹配**。后续日期/相机等条件继续按“一字段一条件”扩展，不提前建通用逻辑编辑器。

每组必须有非空的明确库集合。仅选库的规则可以允许，但编辑器必须直接显示“接收这些库的全部照片”，不能把空白新建行当成已启用的全匹配规则。零组不代表全匹配。

上期将规则组限制为最多 16 组；每组库范围与标签值各最多 64 个，以限制后台工作与界面长度。重复库 ID、标签、值和完全相同的规则组在保存时规范化去重；不做复杂逻辑化简。多值字段与组间 OR 都无需做笛卡尔积展开。

### 6.2 复用现有界面的方法

当前 BrowseToolbar 的控件直接依赖浏览 store，不能在编辑 auto 规则时借用它给照片打标的回调。

实施时从既有控件抽出受控条件编辑能力：输入条件值、输出条件变化；浏览筛选适配器和自动规则适配器共用它。条件 chip、星级阈值、颜色值、标签选择器都只有一套。规则编辑器外层只增加库范围、组容器和“或 / 添加一组”，组内固定 AND，不再摆 AND/OR 开关。

**事实核对**：Rust 底层 Filter 的默认组合值是 OR，但当前前端 BrowseFilter/FilterBar 默认 AND，并且可切换“全部 / 任一”。保存动作必须以实际生效的筛选语义为准，不能只看 Rust 默认值。

### 6.3 调度随规则组增加，但无需全量扫描

- 建立“库 → 规则组”“条件字段/标签 key → 规则组”的依赖索引；只评估变化涉及的组。
- 每张照片命中该桶任意一组即可停止该桶的后续判定；批量 SQL 可以逐组查询后对照片引用做集合并。
- 每组的库范围始终与该组其它条件 AND，绝不能把库当作组间 OR 的另一分支。
- 给目录打/去标签不投递照片自动桶任务；只有照片标记、照片标签、导入/对盘发现的照片变化等触发。
- 新建/编辑规则持久化 revision 与待补扫范围；按组涉及库补扫，重叠库与范围可合并。
- 复用已有 catalog 事务后补偿路径：变化与待处理记录同事务；app.db 写成员时核对规则 revision、桶仍存在、桶级排除；提交成功才确认已处理 revision。重放依靠唯一成员键去重。
- 暂停阻止新的自动加入，手动仍可放入；恢复做一次相关挂载库补扫。离线库等挂载后处理，不后台擅自重新挂载。
- 后台观察到的已提交状态最终收敛；不追溯尚未评估就被改回的瞬态匹配。此项为建议的一致性边界。

## 7. toolsbar 中的桶动作

建议标签按钮右侧只增加**一个桶动作按钮**，点击展开菜单，不随筛选模式偷偷改变主动作含义。

| 菜单动作 | 条件 | 后续 |
| --- | --- | --- |
| 将选中照片加入桶… | 当前有选中照片 | 搜索/选择已有桶，或“新建桶并加入” |
| 将旗标照片加入桶… | 有 pick 旗标照片 | 使用同一个目标桶选择器，明确显示数量 |
| 新建自动桶… | 可选择已登记库；不要求已有筛选 | 打开与编辑共用的规则弹窗；有筛选时带入可编辑草稿，无筛选时从空白链开始 |

已有桶包含 auto 桶，手动放入照常有效。flag 与选中项不暗中求并集；放入成功不默认清 flag，不切换当前 tiles 来源。需要查看目标桶时通过成功反馈的“查看桶”或左栏进入。

目标桶选择器中的“新建桶并加入”在 app.db 同一事务中创建桶及成员；取消不留下空桶。拖入已有桶复用同一加入动作与返回结果，不复制成员写入逻辑。

新建与编辑自动桶使用**同一规则弹窗**，仅初始数据与提交目标不同。入口均显示桶名、完整条件链、每链库范围和匹配预览，可新增/删除条件链、修改每个条件；“添加一组”直接用同一受控条件组件。从筛选导入也可以继续自由增加新链，不是固定草稿的确认页。

新建无筛选时展示一个尚未生效的空白链，选好库并通过校验后才能提交；编辑从已保存规则初始化。草稿内修改不改变当前浏览筛选，也不提前启动后台；取消不写库，保存时才原子提交桶与规则 revision。取消在左、确认在右。规则预览是“当前可匹配”数量，不冒充已经累积的桶成员数。

暂不增加“把当前筛选追加到某桶”等更多顶层按钮；编辑既有桶即可新增条件链。

## 8. 从当前筛选生成自动规则：不能无声改变含义

### 8.1 转换规则

以当前**实际生效**的照片筛选快照为输入：

- “全部 / AND”：一条规则组，保留每个字段及多值。
- “任一 / OR”：每个独立条件成为一个规则组，每组都复制相同的目标库集合。
- 例如“星级≥4 OR 红/黄标”变成“所选库 AND 星级≥4”或“所选库 AND 标色∈{红, 黄}”，不是拆成全部都必须满足。
- 选中照片名单、flag 的瞬时 ID、排序、缩放、时间分组、左栏搜索文字都不成为自动条件。
- 有 flag 或尚未支持的条件时，草稿明确列出，阻止直接保存；不能悄悄丢弃。可先调整条件，或通过现有选片/旗标加入普通桶。
- 草稿是一次快照，后续改变当前浏览筛选不会偷偷改已经保存的自动桶。

### 8.2 当前目录/标签/桶范围如何处理（已确认）

**崔总已确认：只保存筛选条件，编辑时明确选择库范围。** 点击“新建自动桶”时，有当前照片筛选则只将其条件复制为弹窗草稿。目录位置、标签树父节点、桶成员集合是当前导航来源，不变成规则条件或另一个桶依赖。

新建编辑器必须显式展示：

1. 目标库集合，默认当前查询涉及的已挂载库 ID；保存后固定这些 ID，不自动扩展到今后所有新库。
2. 转换后的全部规则组。
3. 若来自目录/标签/桶视图，说明“原导航范围不带入，将在所选库中按以下条件自动收片”，提供所选库范围的异步匹配预览。
4. 最终按钮为“创建并启用自动收片”，而不是直接一键落库。

这使规则不依赖另一个桶，也不把原本只看一个目录的结果无提示地扩大成整库。**转换保留条件逻辑，不保存当前 tiles 的导航来源范围。** 库范围的初始预选是界面建议，实际保存值始终来自编辑器中明确列出的库集合。

## 9. 实时刷新与错误状态

- 给目录打标签后刷新标签树关系；父节点照片结果不因此增加。
- 给照片打标签后刷新父节点结果及相关规则；标签树不因为照片所在目录而长出节点。
- 同文字同时标在目录和照片上时，两种关联独立；删除一边不影响另一边。
- 挂载/卸载影响当前可读集合，重查标签树、标签照片和桶照片；未挂载记录保留，失败与空集合区分。
- 删除一个标签与目录的关联时，如果当前仍在看这个目录，继续正常浏览；只是原来的标签树入口消失。
- 当前桶被删除时，不能保持一个已不存在的成员查询；建议回退库目录入口的可用范围，给出明确提示。
- 批量跨库打标/修改按库拆事务，逐库汇报失败；加入桶集中写 app.db，成员引用需在执行前捕获，避免切换选择后写错对象。
- 挂载状态变化导致某些照片不能继续操作时，保留其它成功项并给出失败原因；不以隐藏离线 tile 代替操作结果说明。
