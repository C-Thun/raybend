## 1. 建议达到的产品程度

**目标：完整的 SDR 摄影色彩闭环。** 输入有依据、编辑保留色域与精度、显示按当前屏幕正确呈现、导出携带与像素相符的色彩信息。既覆盖 sRGB，也覆盖广色域照片与显示器；不能只让 editor 正确、browse 或导出仍偏色。

| 层次 | 建议范围 | 边界 |
| --- | --- | --- |
| 首个基础闭环 | RGB 位图 ICC v2/v4 识别与转换；无配置时有明确依据和回退；RAW 内置相机矩阵；浮点广色域处理；Windows 显示管理；RGB 导出与色彩标记；输入选择、资源管理、版本兼容 | 实施可分波完成，但只交付输入或一个面板不等于完成色彩管理 |
| 同一主题内后续完善 | 批量输入指定、每机型默认规则、预设可选色彩管理组、软打样与目标色域警告、自定义相机 profile | 不让 DCP 完整兼容、打印机打样拖住基础闭环 |
| 远期 | HDR 照片编辑/导出与动态范围映射、打印布局/驱动、CMYK 成片工作流、硬件校准、macOS/Linux | **HDR 桌面上的 SDR 照片显示仍属首期兼容**；高精度表面也可能为 SDR 广色域服务 |

支持正确使用现有校准结果；没有可靠显示器描述/校准时，应标出回退，不能宣称软件凭空让屏幕准确。颜色管理负责解释和转换，色度计测量与生成校准文件属于另一项工作。

## 2. 当前代码基线与需要保留的能力

2026-09-30 阅读工作区源码所得；并行任务会继续改动导出/XMP，实施前再读对应文件。

| 位置 | 当前事实 | 推论 |
| --- | --- | --- |
| `raw/rawler_backend.rs` | `LINEAR_STEPS` 包含 `Calibrate`，到线性 sRGB；随后 `linear_from_intermediate` 转为 `RawImage16` | 不能在已经转换并装入 u16 的像素上补一个相机 profile 就认为获得相机原始色域 |
| `develop/pipeline.rs` | `LinearImage.rgb: Vec<u16>`，范围 0–1；`encode_and_curve` 等环节有 clamp 与 sRGB 编码 | 换矩阵不足以升级广色域；需把像素范围、算法假设和输出边界一起梳理 |
| `display/output.rs` | 已有完整源解码、共用显影与 RGB16 输出；位图用 `from_srgb16` | 导出已有精度与复用基础，但 RGB16 仍不等于广色域/有 ICC 管理 |
| `render/image.rs`、`render/gpu.rs` | 当前 `RenderImage` 为 RGBA8，采样采用 sRGB 纹理，surface 色彩空间为 Auto | 不能先压成 sRGB 8 位再期望最终显示 LUT 恢复被裁掉的颜色 |
| `render/presentation.rs` | Windows 产品用 DX12 + DirectComposition visual | 新显示策略扩展这个平台接缝，保留已验证的合成隔离 |
| `thumbnail/render.rs`、`export/output.rs` | 缓存 AVIF 与导出编码已有共用路径；尚未形成 ICC 输入/输出契约 | 接通这些路径，不另写一套“色彩管理专用导出器” |
| `store/develop.rs`、`store/issues.rs` | 编辑栈、不可变 issue、规范 JSON 与版本化哈希 | 色彩编辑要融入同一模型；旧版本渲染语义也必须保留 |
| `develop/lut_import.rs`、`store/luts.rs` | 已有受限扫描、原子复制、SHA-256、去重、软删除 | 可抽出共同的文件资产底座，ICC/DCP 各自校验，不照抄 LUT 管理器 |
| `src/lib/presets.ts` | 六类预设按组选存/覆盖，已有版本号 | 新增色彩管理可选组，不另建第二套编辑预设 |

已有 `image 0.25.10` 的 decoder 提供 ICC 读取接口，JPEG/PNG/TIFF/WebP 等 encoder 也有对应接口。实际产品部分格式走自有元数据或另一编码器，仍须逐条接通；不能由“库提供接口”推导“应用已经支持”。AVIF 的 ICC/nclx 元数据能力需独立验证。

## 3. 先分清五类色彩信息

| 类别 | 回答什么 | 归属 | 随照片/XMP走 |
| --- | --- | --- | --- |
| 输入配置 | 这些原始像素代表什么颜色；RAW 用哪套相机解释 | 每个编辑基准的照片状态；有效选择进入 latest/issue | **是** |
| 工作空间与处理版本 | 用什么坐标、范围和算法处理照片 | 管线契约；新照片采用当前默认，旧栈固定旧语义 | **是，保存有效标识/版本** |
| 显示器配置 | 此刻如何在这块屏幕呈现 | 本机、每个窗口/显示目标 | **否** |
| 输出配置 | 成片要交付哪种色彩空间 | 导出预设及任务快照 | 成片嵌配置；导出配方可单独表达，**不混入照片编辑栈** |
| 软打样配置 | 模拟某个输出目标之后会怎样 | 查看器状态；可保存打样目标偏好 | 默认**否**；调整照片以适应打样时，实际调整仍进编辑栈 |

界面把 ICC/ICM 统称“色彩配置文件”；RAW 相机 profile 与通用 RGB ICC 分开筛选。DCP、ICC 与创作 LUT 不是同一种数据，不能因都有 profile/LUT 字样就互换。

**两个操作必须区分：**

- **指定输入配置**：像素数值不变，改变对数值的解释，外观可能改变；用于修复缺标或错标。不改原文件。
- **转换输出色彩空间**：转换像素，尽可能维持颜色外观，再写与新像素匹配的配置；用于导出。

不存在“把所有照片换上一个默认 ICC 就色彩一致”的规则。

## 4. Rust 与 GPU 的准备

### 4.1 一条处理链，末端按用途分支

处理主链：源像素与色彩元数据 → 输入解释/相机校准 → **浮点线性工作空间** → 现有显影操作（各自明确工作域）→ 按用途产生结果。

| 用途 | 末端处理 |
| --- | --- |
| 原生显示 | 正常查看或软打样 → 当前 Windows 呈现策略 → 当前屏幕 |
| 缓存/DOM 图片 | 转成明确标记的标准 RGB 编码 → AVIF → WebView 自己管理显示 |
| 成片导出 | 转目标输出 profile → 量化/编码 → 嵌 ICC 或正确标准色彩标记 |

**显示器变换只在显示分支；永远不烘进照片、导出成片或持久缓存。** 基础曲线/创作风格的 tone mapping 是图片处理，设备显示转换是呈现；从命名到接口都分开。

### 4.2 工作空间建议

建议新管线固定使用**线性 Rec.2020 原色、D65 白点、浮点值**，首版界面只读。它是工程选择，不宣称能以 0–1 覆盖所有可能颜色；允许必要的负值与大于 1 的值，不能过早截断。

不在全局设置提供任意切换工作空间的日常开关：这会改变白平衡、亮度权重、曲线、饱和度与 LUT 的解释，维护成本远高于一个下拉框。ProPhoto/ACEScg 保留为方案比较项，只有明确需求和样本证据才改建议。

- CPU 参考计算使用 f32；GPU 以 RGBA16F 为优先候选，关键运算 f32。分辨率分档、分块和内存预算沿用现有能力，不为浮点整链复制大图。
- RAW worker 应在相机空间/高精度线性数据仍完整的位置接入输入转换；继续保持隔离解码。协议须带像素编码与色彩身份，协议版本一并升级。
- 相机矩阵、白平衡、色适应只执行一次；明确矩阵的白点、照明与是否已白平衡。不能把 D50 ICC PCS 与 D65 工作空间直接当同一个 XYZ。
- JPG/PNG/TIFF/AVIF/WebP 保留源位深与色彩元数据，输入变换后再缩图或编辑，避免先走 `to_rgb8`。
- 审计当前 sRGB 假设：亮度系数、色温增益、曝光、曲线、HSL/饱和度、降噪、动态反差与提前 clamp。并非所有操作都必须在线性域，但每个操作的域必须清楚。
- 现有 CUBE/Hald 创作 LUT 保留已知的输入/输出域；用显式转换适配新主链。原有 LUT 没有声明广色域时，不能直接拿 Rec.2020 像素去采样并称“兼容”。

### 4.3 ICC 引擎与 GPU 变换

继续采用 FUTURE 已登记的 [Little CMS Rust 绑定](https://github.com/kornelski/rust-lcms2)作为候选 CPU 色彩引擎，承担 ICC 校验、转换基准和 GPU 变换生成；这轮不添加依赖。CPU、GPU、导出共享配置解析和转换描述，不各自发明色彩规则。

- ICC v2/v4 的 RGB 常见矩阵/TRC、CLUT 路径列入支持目标；按 profile 类别与通道数过滤用途。损坏、超大、未知类型有明确状态；CMYK/DeviceLink/iccMAX 不默认宣称支持。
- 简单路径可用矩阵 + 1D 曲线；复杂路径用由同一引擎生成的 3D LUT。涉及反向曲线、白点与渲染意图时，不靠手读几个标签拼近似转换。
- LUT 的域、shaper、边界处理、插值与精度需要对照 CPU 验证；33³ 是试验起点，不能把无界浮点值直接塞进 0–1 立方体截断。是否需 65³/四面体插值由误差预算决定。
- 纹理格式的硬件 sRGB 编解码与 surface 色彩声明是两件事。应用已算出的设备编码值不能再被 sRGB OETF 编码一次；也不能只换 `Unorm` 就认为 ICC 已正确。
- LUT/transform 后台生成并按完整色彩身份缓存；最新请求胜出，原子替换。换显示器通常只换末端转换，不重新解码整张照片。
- 原生照片、洞口底色、GPU 覆盖层都要声明来源空间；UI 色彩从 sRGB 转到同一呈现目标，不能误走照片的相机输入转换。

### 4.4 缓存与直方图

**持久缓存不是工作缓冲。** 现有 AVIF、DOM `<img>`、RAW worker 与 GPU 纹理都必须知道读到的像素是什么。

建议基础期将缩略图与 1920 预览规范化为带正确色彩标记的 **sRGB AVIF**：保证兼容和行为可解释，但这类代理会舍弃超出 sRGB 的颜色；其用途是浏览/过渡，不用于证明广色域编辑的最终效果。广色域真实预览走高精度主链。广色域代理以后可升级为经过 WebView 与原生双通道验证的标准编码，不能保存无标记的线性 Rec.2020 AVIF。

源内嵌预览有自己的色彩身份；不能把 RAW 相机输入配置直接套到已显影 JPEG 上。照片输入被手动重指定后，旧内嵌预览只能是明确的过渡图，最终代理须从正确输入重新生成。

缓存键含源版本、有效输入配置指纹、编辑/处理版本、代理编码版本；**不含显示器 ID/profile**。换屏不重建整库缓存。缓存丢失可重建，ICC 原件不是缓存。

直方图/取色取自明确且设备无关的编辑或输出参考域；默认沿用现有 RGB 直方图的可理解含义并标出参考空间，不悄悄变成线性曝光分布。换显示器数值不变；打样目标色域警告与传感器/曝光高光溢出分开。

## 5. Windows 集成：需要打通读取、跟随与呈现

**需要与系统打通；默认读取并服从本机显示配置，不代替系统管理显示器。** 保留薄壳边界：平台层提供显示目标/状态，核心 Rust 管色彩模型与转换，前端只展示与发意图。

| 系统状态 | 应用应做什么 | 限制 |
| --- | --- | --- |
| 普通 SDR，Advanced Color 未激活 | 取得当前屏幕默认 ICC；应用做图像→显示器转换 | 没有可靠 ICC 时明确“按 sRGB 回退”，不把它叫“已校准” |
| ACM/Advanced Color 激活 | 声明应用输出的标准色彩空间，由系统完成显示器映射 | 不再额外套真实显示器 ICC；简单 sRGB 交付可正确显示 SDR，但限制可呈现色域 |
| ACM 下希望完整 SDR 广色域 | 优先验证 scRGB 浮点 surface，与当前 DirectComposition visual 配合 | 属于 SDR 广色域呈现能力，不必等待 HDR 照片编辑；验证不过则明确降级 sRGB |
| HDR 桌面 | 同样识别系统状态，按 SDR 内容规则处理白电平/亮度关系 | 不能只认 HDR 布尔值、忽略 SDR 白电平，导致照片与 WebView 亮度不一致 |

Microsoft 明确区分了传统 ICC 与 Advanced Color 管理；Advanced Color 开启时，传统默认显示 profile 查询可能得到“无 profile”，这有兼容语义，不能直接判成屏幕没有色彩管理。[官方说明](https://learn.microsoft.com/en-us/windows/win32/wcs/advanced-color-icc-profiles)

scRGB 交付、色彩空间声明及 SDR 白电平须一起验证；不能只把纹理改成 fp16。[DirectX Advanced Color 指南](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/high-dynamic-range)

本地 wgpu 30.0.1 已有 `ExtendedSrgbLinear`，注释注明支持原生 DX12；`DisplayP3` 不由 DX12 报告。枚举存在只证明接口有入口，不证明当前显卡、驱动与合成表面已经可用。

### 5.1 必须有的系统能力

- 将窗口/照片视口映射到实际显示目标；读取该目标当前有效 profile、系统管理状态与必要的亮度信息。不能一直读主屏。
- 新 API 必须能力探测并有 Win10 兼容回退。`ColorProfileGetDisplayDefault` 文档列出的最低客户端为 **Build 20348**，不能沿用旧稿“Win10 2004+ 全部可用”的假设；回退到经验证的 WCS/ICM 路径。[API 文档](https://learn.microsoft.com/en-us/windows/win32/api/icm/nf-icm-colorprofilegetdisplaydefault)
- 启动、跨屏、热插拔、系统 profile/ACM/HDR 变化后刷新；事件驱动并合并抖动。恢复焦点/从系统设置返回时重新核验，提供手动刷新兜底。不永久缓存首次读取，也不每帧扫描文件。
- 每个窗口分别维护呈现目标，包括 fullscreen。窗口横跨不同屏幕时，首版应用管理路径选择照片视口占比最大的屏幕；另一侧不承诺同时精确。窗口完全移到一块屏幕后正确切换是验收条件。
- 提供“打开系统色彩设置”“重新检测”和只读诊断。显示器手动覆盖仅作为高级诊断，按屏幕保存，并在系统管理路径中限制会引发双重转换的组合。

### 5.2 应用不承担的系统动作

不自动安装/关联系统 ICC，不修改 HDR/ACM 开关，不加载 `vcgt`/`MHC2` 到显卡，不调用 gamma ramp 去“补校准”。这些由系统或校准工具负责；ICC 描述转换不能代替校准加载，也不能再加载一次。[Windows 校准管线](https://learn.microsoft.com/en-us/windows/win32/wcs/display-calibration-mhc)

不要给普通界面一个“系统已加载校准曲线”复选框，让错误开关把职责变得含糊。是否完成真实校准与环境光是否合适，不能仅凭 ICC 存在判断。

WebView 管 DOM 图片，原生管 GPU 照片；两条交付路径都需明确标记并真机对照。不能未经本机验证就写“WebView 一定准确”，也不靠强制 Chromium 色彩开关统一结果。

### 5.3 系统互操作 adapter 边界（崔总 2026-09-30 明确要求）

**必须在接入系统 API 之前定义边界，不在业务代码堆完 Windows 调用以后再抽 adapter。** 此要求覆盖本主题全部系统互操作，既包括读取，也包括监听与打开系统界面。项目级原则落在 `memory/ARCHITECTURE.md` §2.2。

按责任划分接口，不规定必须使用动态分发/插件框架；可通过 trait、枚举分发和依赖注入实现。下面是逻辑边界，实施时不必机械拆成三个顶层模块。

| adapter 边界 | 输入/输出与职责 | 具体系统实现封装什么 |
| --- | --- | --- |
| `ColorEnvironmentAdapter`（建议名） | 接收项目自身的窗口/视口定位信息；返回显示目标、能力、管理状态、SDR 白电平、有效 profile 来源/字节快照及状态版本；订阅失效事件 | Windows 屏幕枚举、显示配置、WCS/ICM/DXGI 查询、系统/注册表通知；未来平台有各自实现 |
| 既有 `PresentationAdapter` 扩展 | 根据统一呈现请求与 surface 实际能力选择格式/色彩空间；返回实际采用方式及降级原因 | DX12/DirectComposition 与其它平台表面的配置差异；不再创造一个 GPU 上下文或渲染循环 |
| 系统色彩资源/设置入口 adapter（可作为环境 adapter 的窄接口） | 枚举系统配置、请求读取指定系统资源、打开色彩/HDR 设置；返回明确支持或不支持 | 系统 ICC 安装目录/关联查询、设置页跳转、平台错误；不把注册表路径、系统 URI 交给前端拼接 |

依赖方向：**UI → 现有 API/薄壳装配 → 核心色彩服务 → adapter 接口**；平台实现在装配时注入。色彩服务负责输入/工作/显示/输出策略与变换，平台 adapter 提供事实和执行呈现接入；两边不各维护一份 ICC 选择规则。

- 接口只暴露自有类型与不透明标识；`HWND/HMONITOR/LUID`、COM、WCS 枚举和平台路径留在实现内。沿用 `render_window.rs` 的原生窗口胶水，不让前端、`DevelopStack` 或普通显影算子认识 Windows 句柄。
- 快照区分 **可用/不存在/不支持/读取失败/状态未知**；“没有 ICC”不能代替“系统管理关闭”。能力探测与 Win10 旧 API 回退都在 Windows adapter 内。
- 监听使用可释放订阅，窗口销毁/显示目标变化时取消；事件只是触发重读，不直接把半更新状态当完整快照。恢复焦点与手动刷新也调用同一接口。
- 快照有 generation/版本，转换任务带同一版本；跨屏后丢弃迟到的旧结果。设备丢失重建后重新验证呈现能力，不复用未经核实的旧 surface 配置。
- 同一 profile 字节的解析、校验和变换仍由核心统一引擎完成；adapter 不自建另一个 ICC 引擎。应用自己的配置资产复制/哈希继续走共用文件底座，不绑定系统安装目录。
- 全局设置、editor、browse 和 fullscreen 共用同一个环境服务及窗口级状态，不能各查一套系统配置。
- 无头/离屏/测试使用 fake adapter，返回显式指定的标准目标；“系统能力未知”不能伪造为真实屏幕已校准。macOS/Linux 先保留可替换契约与明确不支持状态，不假装已完成实现。
- 冒烟/单测用 fake 覆盖跨屏、profile 更换、ACM/HDR 切换、事件合并、旧结果丢弃、API 不可用与窗口销毁；真实 Windows adapter 的显示准确性仍归真机验证。

## 6. editor right「色彩管理」面板

位置按本轮要求为第三组 **`曲线 · 预设 · 色彩管理`**。第二组现有“色彩”继续负责色温、饱和度等调整；这里负责色彩解释与查看目标。

2026-10-04：对应 Pencil 设计与首版界面已落地，复用现有页签、ProfileSelect、Dialog 与信息提示。以下保留最终功能方向；首版支持范围和性能闸门以 `cm-w2.md` 至 `cm-w5.md` 为准。

| 分区 | 内容 | 状态与行为 |
| --- | --- | --- |
| 输入 | 当前基准 RAW/SOOC；检测到的配置；实际使用配置；自动/手动选择；恢复自动 | 分清“内嵌”“元数据推断”“默认假定”“手动覆盖”“配置缺失/不支持”。输入改变纳入撤销与 latest；RAW 仅列相容相机配置，位图列 RGB ICC |
| 工作空间 | 当前工作空间、旧版兼容状态（有需要才展示） | 只读；不放日常切换开关。高级信息折叠，不塞进主要操作流 |
| 显示 | 当前屏幕、自动管理方式、有效配置/回退状态 | 只读摘要；跳转全局设置。换照片不会重设屏幕配置 |
| 软打样（后续完善） | 开关、输出目标、渲染意图、黑点补偿、色域警告；需要时纸白/黑墨模拟 | 默认关闭；显眼标识“打样中”。纸张模拟只在相应目标和意图下可用；不改 latest/issue |
| 资源入口 | 管理/导入色彩配置文件 | 打开全局同一资源管理器；不在面板再复制一棵独立文件库 |

没有照片时禁用输入操作，显示器状态仍可读。不要给“输入色彩解释”放一个总开关：关闭后像素仍然需要被解释；真正需要的是恢复自动或显式回退。

首版软打样提供已验证 RGB 矩阵/TRC 目标的相对色度模拟，默认关闭；感知、BPC、纸白/黑墨尚未提供，不显示虚假可用开关。最终方向仍以输出目标预演，打印机 ICC 可在后续用于模拟，不代表应用已经能打印或输出 CMYK。照片呈现意图优先提供“相对色度 + 黑点补偿”和“感知”；目标是否提供有意义的感知表需检查。绝对色度/纸白模拟收在高级项。

## 7. 全局设置、默认规则与批量

### 7.1 统一全局入口

在既有 `Ctrl+,` 入口扩展设置分区，保留快捷键设置。色彩管理分区包含：

| 功能 | 建议 |
| --- | --- |
| 配置文件库 | 批量导入 `.icc/.icm`；后续加 DCP；显示名称、类别、来源、机型适用性、可用性、是否被引用；恢复/移除沿用既有资产范式 |
| 输入默认规则 | 有合法内嵌配置优先；无配置时看可靠格式标记；仍未知的 RGB 位图默认假定 sRGB，并保留“假定”状态；RAW 默认相机矩阵 |
| 每机型默认 | 后续支持按机型/必要时具体相机匹配相机 profile；不允许一份相机 profile 无条件套全部 RAW |
| 输出默认 | 新建导出预设默认 sRGB + 嵌入配置；输出意图默认相对色度 + 黑点补偿，具体能力按目标核验 |
| 显示 | 每屏自动跟随、系统状态、诊断与系统设置入口 |
| 打样偏好 | 记住常用输出目标；启用状态与照片编辑分离 |

优先级方向：**照片明确指定 > 合法内嵌/可靠来源信息 > 有条件的匹配规则 > 通用回退**。机型规则覆盖相机内置矩阵可以明确配置，但不无声覆盖位图的有效内嵌 ICC。AVIF/PNG 存在不同色彩描述时，按各自容器规范决定优先级，记录来源/冲突，不能把通用列表当解析规范。

**默认规则只负责初始化尚未固化的照片状态。** 旧 latest/issue 保存已解析的有效配置和处理版本；改全局默认不得导致整库已编辑照片变色。需要将新默认应用到旧照片时，走显式批量操作。恢复自动也要记录本次重新解析的结果，不能让定稿依赖未来的全局默认。

### 7.2 “批量”有三种，不混为一个开关

1. **批量导入文件**：一次导入多份 ICC，校验/分类/去重，形成全局资产库。
2. **批量指定输入配置**：给明确的一组照片设置或恢复输入解释；入口归 browse 既有批量交互。冻结目标照片 ID 和编辑基准，预先显示数量、相容性、将覆盖多少已有选择；混合 RAW/位图时按相容性分组或拒绝，不强套。只改 latest，命名 issue 保持不可变；刷新派生图并纳入现有撤销能力。
3. **批量转换输出**：通过导出预设完成，源文件与现有 issue 不变。

“当前选中一张”与“勾选的待处理集合”要沿用项目语义明确展示，不把选中状态直接当批量集合。批量色彩操作改的是编辑栈，不借评级/标签的 `mark` 通道硬塞；复用编辑提交、撤销与缓存失效能力。

### 7.3 配置文件是资产

复用 LUT 的受限扫描、复制、内容哈希、原子落盘、引用保护；**只抽共同底座，ICC 校验、DCP 校验、LUT 封面等保留各自适配器**。不是把 ICC 文件塞到 CUBE 解析器里。

- 以原始文件字节的 SHA-256 识别外部资源；名称/绝对路径/本机 DB ID 不能作为跨机器身份。同名不同内容要共存，同内容不同名字可去重。
- 全局库在应用数据目录，文件不是可删缓存。已用于库内照片的自定义配置，建议保存库随行副本（逻辑归属为库资源，目录名实施时确定），让“库 + 原片”搬家后仍可重建；全局库是选择入口，不是唯一生存地点。
- 被 issue 引用的文件不可因面板移除而消失，先隐藏、受引用保护；替换文件产生新身份，旧定稿继续指向旧字节。
- 缺失时保留引用并提示；可提供明确标记的临时查看回退，**精确导出应暂停并要求解决**。不能照搬当前创作 LUT 的“丢失就静默忽略”。

## 8. 与预设、issue、XMP 的关系

### 8.1 编辑预设：可以收，但限于照片相关部分

为已有预设新增可选“色彩管理”组，**默认不勾选**，避免保存一个影调风格时意外绑定相机输入。已有六类的默认行为不因此改变。

| 信息 | 编辑预设是否保存 |
| --- | --- |
| 输入选择策略/明确相机配置、相容条件 | 可以，显式勾选；跨机型应用须校验 |
| 正确重放预设所需的处理版本/工作域 | 作为兼容元信息；不能以应用风格预设为由偷偷升级整张照片管线 |
| 某张源文件特有的内嵌 ICC/源路径 | 不机械照搬；“自动”应在目标照片解析 |
| 显示器 ICC、ACM/HDR、校准状态 | 不保存 |
| 输出 ICC/意图/嵌入选项 | 归导出预设 |
| 软打样开关和屏幕信息 | 不保存到编辑预设 |

应用前解析依赖，缺失色彩组不静默降级。建议整个应用计划在提交前验证；若允许只应用其它组，必须明确选择。照片/issue 存有效结果，预设可存可重用选择策略，两者不等同。

### 8.2 issue 与历史兼容

输入配置、工作空间/处理版本会影响像素，必须参与规范序列化与 issue 身份；屏幕和打样状态不参与。

**升级不能作废旧定稿。** 给旧栈明确的 legacy-sRGB 语义并保留相应渲染路径；新管线用于新栈。升级旧照片需显式操作、可撤销，原命名 issue 不被重写。兼容路径是同一引擎内的版本分支，避免另立一套导出/缓存实现。

允许重建派生缓存；不允许只重算哈希却用新算法渲染旧参数。DB 改动只走既有迁移、快照和完整性检查；哈希/schema、处理算法版本、资源文件版本分别管理，不能混成一个版本号。

### 8.3 给正在设计 XMP schema 的衔接约束

**建议现在留好扩展结构，色彩功能落地时再写真实字段；不要先输出空的“已支持”色彩配置。** 本轮不改正在并行设计的 XMP 正文/实现。

| 概念 | 后续需要表达的语义（不是本轮定稿字段名） |
| --- | --- |
| 编辑色彩状态 | 输入基准、自动/手动选择、实际解析到的输入配置、工作空间与白点/编码标识、处理版本 |
| 外部资源引用 | 资源种类、内容哈希算法与值、可读名称、内置稳定标识或随行资源定位；不能只存绝对路径或本机自增 ID |
| 重放语义 | 区分“沿用旧版解释”与“采用新色彩管线”；缺省字段代表当时版本的默认语义，不能代表未来全局默认 |
| latest/issue | 每份快照保留自己的色彩状态；配置改变影响身份，屏幕变化不影响 |
| 输出配方 | 若 XMP 需要携带，使用独立导出/任务语义，不与源输入字段混淆 |
| 未知版本/资源缺失 | 保留原内容并报告不能精确重放；不丢字段后宣称成功。导入尚未排期，也不妨碍先把导出契约写完整 |

`photoshop:ICCProfile` 在 Adobe 文档中是 **Text** 属性，能描述配置名，但不是 ICC 二进制文件、内容指纹或完整渲染配方。不要用它承担 RayBend 的全部色彩状态，也不要把工作空间/显示器名字冒充文件嵌入的 profile。[Adobe 字段定义](https://developer.adobe.com/xmp/docs/xmp-namespaces/photoshop/)

推荐将应用色彩状态放入既有 `rb` 命名空间所承载的版本化编辑载荷；沿用 `specs/issue-xmp-contract.md` 的 DB 真相源与 sidecar 通道原则。不把自有语义伪装成 Adobe `crs:` 兼容。

**引用不等于携带文件。** 常规 XMP 保存资源身份/定位；原片内嵌配置可由原片恢复，内置配置凭稳定版本恢复，自定义 ICC/DCP 需要库随行资源或显式的资源包。单独一份 XMP 加名称/哈希不能保证自定义色彩效果可重现。是否提供资源包、内嵌二进制扩展及第三方配置可否随包分发，留给迁移/打包单元定；当前就要保留资源种类与指纹的扩展位。

导出图片须**先转换像素再嵌目标 ICC**，并清理/更新冲突的源 EXIF 色彩标记与 AVIF nclx 等信息。源文件不写回。JPEG/PNG/TIFF/WebP/AVIF 逐格式验证；某编码器尚不能正确表达目标 profile 时，限制该组合并说明原因，不能静默去标。默认总是携带目标色彩描述；仅 sRGB 高级兼容选项才考虑允许去标，不把“剥离拍摄元数据”误当成“剥离 ICC”。

## 9. 建议实施顺序与验收边界

只定依赖次序，不给未经验证的周数；后续每次开工细化一个波次。

| 次序 | 解决的问题 | 可交付判据 |
| --- | --- | --- |
| A：契约与样本 | 五类归属、色彩身份、旧栈兼容、XMP 扩展、系统 adapter 接口与 fake、带参考值的样本 | 评审通过的语义与平台边界；不先写空 UI 冒充功能 |
| B：输入/输出闭环与底座 | ICC、浮点工作域、RAW 接缝、现有算子适配、共享输出、资源保全 | CPU 对照正确，导出像素与标记一致，旧 issue 可复现 |
| C：Windows/GPU 呈现 | 传统 ICC 与系统管理分支、跨屏、HDR 桌面 SDR、DOM/原生协调 | 支持组合通过真机；降级路径有明确边界。可以早于 B 完成做独立平台 spike |
| D：产品接入 | 面板、全局资源/默认、批量、预设可选组、XMP 实际字段 | 复用现有命令/编辑/撤销能力，输入变动在全部视图生效 |
| E：专业扩展 | 软打样、打印目标模拟、相机 DCP/ICC、默认机型规则细化 | 对相应格式与样本逐项验收，不声称只读几个 DCP 标签就兼容全部相机风格 |

D 的基础面板可随 B/C 按功能逐步接入；B/C 未闭环之前不宣布“完整色彩管理”。软打样第一版可只做 RGB 输出目标，打印机 CMYK 模拟另验。

**Agent 可验（冒烟/单测/离屏）**：独立期望值的 ICC 转换；源位深保留；负值/超 1/NaN/边界策略；CPU/GPU 误差；ICC 损坏/超大/类别不匹配；多段 ICC 与不同容器标记；资源同名/重命名/中文路径/竞争；缺资源与旧 schema；批量目标与撤销；输出嵌入后由独立读取路径核验；换屏只更新末端、缓存不串源。构建通过不是色彩准确证明。

**需崔总真机确认**：sRGB/广色域屏，校准配置切换，多屏拖动与 fullscreen，ACM 开关，HDR 桌面 SDR 白电平，照片与 DOM 同色块/灰阶，实际照片的肤色/渐变/高饱和色，预览与导出在同一色彩管理查看条件下的一致性。不把相机 JPEG 风格与 RAW 默认显影不同直接判成色彩管理错误。

### 命令与热键方向

打开面板、管理配置文件、批量指定/恢复自动、软打样开关、目标色域警告应接统一命令注册表。现有 `Ctrl+,` 保留为全局设置入口；**其它新增命令建议 `defaultKey` 留空**，原因是偏专业、低频且避免占用既有编辑键，可在命令面板查找和自定义。实施时仍须经过冲突/保留键检查并使用统一键位文案；面板内普通下拉项不各占一个命令。

## 10. 本轮建议定下的方向

1. SDR 全链路为目标，首期就识别 ACM/HDR 桌面；完整 HDR 照片与打印另排。
2. 新管线采用浮点线性 Rec.2020，工作空间由处理版本固定；旧 issue 保持原有语义。
3. 面板位于 `曲线 · 预设 · 色彩管理`；照片输入可编辑、工作空间与屏幕只读、打样为预览状态。
4. 设一个全局配置文件库和条件默认规则；批量区分导入资源、指定输入、导出转换。
5. 编辑预设能显式选存输入色彩管理，默认不带；输出走导出预设，设备配置留本机。
6. XMP 现在预留照片色彩状态、处理版本和可携带的资源身份；不把监视器塞进 issue，不把一段配置名当作完整文件。
7. **已确认约束**：所有系统互操作先设计 adapter；枚举、读取、监听、设置入口与呈现接入均不得散落在业务层。

面板位置与 adapter 原则来自崔总明确要求；其余技术/产品取舍仍是建议，不标成已采纳。下一步按讨论结果确认取舍，再做具体波次和 Pencil 画稿。

## 11. 对 2026-09-26 草案的修正

- 页签已增加预设，新的位置应为 `曲线 · 预设 · 色彩管理`。
- 原稿把 RAW 输出概括成 f32，漏掉随后转换为 u16 的实际交接；同时导出现在已有 RGB16 共用引擎，不再是“只有格式约定”。
- “缓存一律存工作空间像素”改为“缓存有明确标准编码、永不烘屏幕”；符合 AVIF 与 DOM 消费方式。
- “作废全部 issue”改为保留版本语义与不可变快照；派生缓存可失效，原编辑资产不可失效。
- ACM 与 HDR 内容编辑拆开，不能把系统管理兼容全部推迟到 HDR 里程碑；也不能无条件应用真实显示器 ICC。
- 不强制一个 Unorm surface 方案、不把 33³ 当精度承诺。旧稿 33³ LUT 内存数字错误：RGBA16F 约 281 KiB、RGBA32F 约 562 KiB（不含对齐/驱动开销）；以真实格式核算。
- 新 Windows API 的最低版本按官方文档修正；旧稿的全局“API 必然泄漏”“非 D50 必拒绝”“DOM 已经一定正确”不作为未经条件核验的产品规则。
- 移除“系统已加载校准”开关；应用不承担校准曲线加载。移除任意默认工作空间切换。
- 已有 codec ICC 接口先复用，不预先决定新增 img-parts 或自写 TIFF IFD；DCP 也不在未评估支持范围前锁定 parser 依赖。
- 批量色彩指定复用编辑提交能力，而非评级/标签 mark 通道；ICC 缺失不套用创作 LUT 的静默忽略策略。

## 12. 主要依据

除上文就近引用外，方向依据包括：

- [ICC profile 与设备类别](https://www.color.org/getting-started/)：输入、显示与输出 profile 的用途边界。
- [Little CMS 浮点与无界处理论文](https://www.littlecms.com/CIC18_UnboundedCMM.pdf)：浮点范围与变换类型的关系；不据此承诺任意 CLUT 自动支持无界数据。
- [darktable 输入色彩模块](https://docs.darktable.org/usermanual/development/en/module-reference/processing-modules/input-color-profile/)：相机输入与工作空间分层的参考，不照搬其全部产品选项。
- 本地 `image-0.25.10/src/io/{decoder,encoder}.rs` 与各 codec、`wgpu-types-30.0.1/src/surface.rs`：接口核验；实际支持仍以本项目各路径接通和验证为准。
