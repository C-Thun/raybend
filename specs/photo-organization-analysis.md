# 相片整理：第一轮算法建议

> **历史分析，当前提案以 `photo-organization.md` 为准。** 2026-09-30 后续补充已明确：目录标签只关联目录、不传播到照片；左栏改为三入口整栏互斥且不可全关；auto 支持组间 OR、组内 AND；桶 tiles 只展示已挂载库照片。本文件的目录来源合并、上下分栏、单组规则、离线占位及强制按库分组建议不再是当前方向。保留实验与推理作为历史证据，不把旧性能数值视为新版指标。
>
> 另经前端核对：Rust 底层 Filter 的默认值为 OR，但现有 BrowseFilter / FilterBar 默认 AND，且支持切换“全部 / 任一”；转换自动规则应依据实际生效条件。

> 2026-09-30。**待崔总评估的建议稿，不是已采纳规格，不代表功能开工。**
> 输入：`photo-organization.md` 与本轮关于左栏、文字标签、三来源合并及全来源遮罩的补充。
> 本轮只做源码核对、算法分析和合成数据实验；未修改业务代码、数据库、Pencil 设计稿。

## 1. 建议结论

保留 bucket + tag 两个原语。标签采用**文字语义键、来源分别保存、查询时合成、遮罩最后统一扣除**。
目录标签不展开成每张照片的关联；auto bucket 采用**持久待处理记录 + 增量评估 + 幂等装桶**。

本方案真正昂贵的不是三个集合求并集，而是目录标签写入放大、全量分面计数、跨库身份与恢复、自动桶遗漏或重复处理。
先限制这些外围能力，可以保留标签核心体验。

| 项目 | 首版建议 |
| --- | --- |
| 标签身份 | 规范化文字；不依赖 `app.db` 的数字 ID |
| 来源 | 手动、目录、AI 分开保留；同文字可同时有多个来源 |
| 最终标签 | `(手动 ∪ 目录 ∪ AI) − 遮罩` |
| 目录标签 | 目录只存一条关联，读取时关联照片所属目录；不递归普通子目录 |
| 遮罩 | 按规范化文字禁用全部来源；来源刷新不能解除遮罩 |
| 自动桶 | 指定库、有限正向条件、匹配后留下；修改条件不移除旧成员 |
| 离线 | 桶名单和上次已知信息可见；实时标签查询只覆盖可读的已打开库 |
| 优先裁剪 | 全局改名/合并、同义词、每个标签实时计数、复杂条件树、AI 推理、跨库全局排序 |

## 2. 源码核对后的修正

1. **当前词典只做精确规范化去重，不做近义词识别。** `store/tags.rs` 使用 `trim → NFC → 小写`；`Trip/trip` 相同，`鸟/飞鸟/bird` 不相同。原稿中的“防近似重复”需要收窄表述。
2. **现有 catalog 不自含标签文字。** `asset_tags` 仅存 `asset_id/tag_id/tagged_at`，名称在另一份 `app.db`。`register_tag_with_id` 只检查数字是否占用；缺失名字不能凭 ID 恢复，不同设备相同 ID 也不证明同一个词。
3. **正常重扫不等于删除重建 catalog。** `store/rebuild.rs` 经 diff 对齐既有资产，保留匹配资产 ID；缺失文件做标记。不能笼统地说“重扫就导致 asset id 变化”。
4. **FileId 是物理文件身份，照片是逻辑资产。** `assets` 对应照片，`asset_files` 可以同时含 JPG 与 RAW。Windows 文件身份还包括卷号，不能只取 128 位文件号。[Microsoft FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info)
5. **目录索引要补，不能说现有索引全部够用。** 当前 `app.db.directories` 是统计缓存；标签需要 catalog 内的可靠目录关联，不能依赖这个可重建统计表。
6. **筛选器可复用，但不能原样保存当前 `Filter`。** 当前标签条件是 `Vec<i64>`，维度内任一命中，维度间默认 OR；自动桶的库范围必须始终约束全部条件。
7. **分隔条已经存在。** 直接一般化 `SplitStack`、`SplitHandle`、`lib/stack-resize.ts`，不引入第二套拖动实现。现有目录树自身最小高度为 88px，不能直接当作整个库目录面板的最小高度。
8. **已有提交后补偿模式。** `store/rebuild.rs::Pending / acknowledge_changes` 已保存未确认变化；新能力应扩展同一提交/补偿通路，而不是另建一套前端事件总线承担可靠性。

## 3. 标签的精确定义

### 3.1 文字就是语义键

`tag_key = fold_name(clean_name(input))`，沿用现有 Rust 唯一规范化入口：去首尾空白、非空与 64 字符检查、NFC、小写。比较使用已算好的 key，不靠 SQLite `NOCASE` 处理 Unicode。

- 不自动做全半角合并、内部空格压缩、拼音、简繁、同义词或 AI 语义近似。
- 普通搜索可给近似候选，但关联与遮罩始终做 key 精确相等。
- 本地保留展示文字；切换界面语言不翻译或改写已有标签。
- 标签词典仍可放 `app.db` 做跨库输入建议；每个 catalog 同时保存它用到的词与来源关系，成为自含真相源。
- 首版不做改变 key 的全局改名/合并。把“鸟”改成“飞鸟”是换词；旧的“鸟”遮罩**不会**自然屏蔽“飞鸟”。这正是文字遮罩必须明确的边界。

### 3.2 三来源与遮罩

对照片 p：`E(p) = (M(p) ∪ D(p) ∪ A(p)) \ X(p)`。

**UI 上只有一颗有效标签；存储中可以有三份来源证据。** 来源位标志只用于结果说明，不能用单个来源值覆盖其他来源。主来源标识建议手动 > 目录 > AI，展开后列出全部来源；这个优先级不影响存在性，遮罩永远最后生效。

| 动作 | 写入规则 | 可见结果 |
| --- | --- | --- |
| 手动添加“鸟” | 加手动关联；同一事务清除这张照片“鸟”的遮罩 | 立即出现 |
| 移除手动来源“鸟” | 只删手动关联 | 目录或 AI 仍有则继续出现 |
| 禁止“鸟” | 写入文字遮罩，保留全部来源证据 | 全部来源的“鸟”都不出现 |
| 取消禁止“鸟” | 只删遮罩，不凭空添加来源 | 仍有任意来源才出现 |
| 删除目录标签 | 只删目录的关联 | 手动、AI 同名标签仍在 |
| AI 刷新成功 | 在事务里替换该照片的 AI 集合 | 手动、目录、遮罩不变 |
| AI 失败或取消 | 不提交半份结果 | 原有有效 AI 结果保留；失效策略另见 §8 |

“tag 与遮罩二选一”建议解释成**最终显示互斥**，不强制销毁被遮住的原始证据。否则取消遮罩无法恢复原手动标签。无来源、无禁令是自然空态，不等于“禁止”。

合并标签上的操作必须区分“移除手动来源”和“禁止此标签”；不能让一个无说明的移除按钮有时真消失、有时马上出现。建议常规标签操作使用“禁止”，来源详情提供“移除手动来源”。移除/禁止沿用禁行图标和现有确认纪律。

遮罩不放进正常标签集合。它只在“已禁止”详情里显示文字、来源和解除入口；筛选、搜索、导出元数据与自动桶都使用同一个 `E(p)`。

### 3.3 catalog 内的最小数据模型

以下为逻辑结构，不是本轮要执行的迁移：

```text
tag_terms(tag_key TEXT PK, display_name)
asset_tag_sources(asset_id, tag_key, source, ...)
  PK(asset_id, tag_key, source)              -- source = manual / ai
  INDEX(tag_key, asset_id, source)
directory_tags(dir_key, tag_key, ...)
  PK(dir_key, tag_key)
  INDEX(tag_key, dir_key)
asset_tag_masks(asset_id, tag_key)
  PK(asset_id, tag_key)
asset_files 增加 organization_dir_key
  INDEX(organization_dir_key, asset_id)     -- 仅照片源文件参与
```

`tag_key` 可以作为本地词表的文字外键，遮罩依然直接按文字身份工作。无需把“mask”伪装成来源，也不引入另一套全局 UUID 标签体系。内部关联继续用 catalog 的 `asset_id`。

不持久化完整 `effective_tags` 表。关系与反向索引已足够起步；如将来实测确实需要结果索引，它只能是可丢弃重建的派生数据，不取代来源真相。

## 4. 目录：一条规则，不给十万张照片补十万条标签

### 4.1 归属规则

目录 key 是库内相对路径的现有规范化形式。整个库搬盘不改 key。

照片的目录集合由它的 `bitmap/raw` 源文件计算；sidecar、缓存和 issue 导出文件不参与。一张照片在多个目录留下源文件时取这些目录标签的并集，按文字去重。

**`_RAW` 使用既有逻辑目录规则**：复用并收敛 `assets::normalize_raw_dir` / 既有配对规则，末级 `_RAW` 折算到所属照片目录。这是源文件归属，不是开放一般子目录继承。例如 `旅行/a.JPG` 与 `旅行/_RAW/a.NEF` 都归 `旅行`；`旅行/第二天/b.JPG` 不继承 `旅行` 的标签。

`organization_dir_key` 在导入、重扫路径变化和文件重新归属时由 Rust 一次计算，同一事务更新。查询不能对每条路径临时切字符串再做 `LIKE` 全表匹配。

离线或缺失时保留 catalog 上次已知的目录归属；重新对盘后更新。首版目录标签绑定**位置路径**：外部重命名目录不猜测整体迁移，旧绑定保留待重新绑定；旧路径再次有照片会继续按此位置的规则生效。不能静默清理旧标签。如果需要“跟着实体目录移动”，应单独增加目录身份机制，不能从部分文件移动推断整目录移动。

### 4.2 成本

| 动作 | 不物化目录标签 | 逐照片物化目录标签 |
| --- | --- | --- |
| 给 N 张照片所在目录增加 T 个标签 | 写 T 条规则及待评估范围 | 写约 N×T 条关系 |
| 新照片进入目录 | 登记自身目录，读取即生效 | 另补 T 条关系，必须可靠补齐 |
| 改目录标签 | 更新规则即可 | 修改全部受影响照片的派生关系 |
| 照片搬目录 | 更新源文件目录归属 | 处理旧来源删除、新来源补齐、遮罩保护 |

节省的是**标签真相的写入**；如果该目录关联自动桶，后台仍可能必须评估 N 张照片、写 N 个新成员。这部分输出成本无法靠“不物化标签”消失，但它可以分批进行，不阻塞打标签本身。

## 5. 读取、筛选与性能

### 5.1 详情读取

对当前页 P 张照片，以批量 ID 表/有界参数查询分别读取直接来源、目录来源和遮罩；Rust 按 `(asset_id, tag_key)` 合并来源，再扣除遮罩。成本与**当前页关联量**相关，不与整库照片数直接相关。

只在展开详情时追加完整目录来源/AI 说明。不逐 tile 发三次 IPC，不把整个库所有标签搬到前端。实现应由 `store/tags.rs` 同一服务承担，查询、右栏、弹窗、搜索、导出和自动桶都接这一个语义入口。

### 5.2 反向查照片

单个文字标签 t 的候选：

```sql
WITH candidate AS (
  SELECT asset_id FROM asset_tag_sources WHERE tag_key = :tag
  UNION
  SELECT f.asset_id
  FROM directory_tags d
  JOIN asset_files f ON f.organization_dir_key = d.dir_key
  WHERE d.tag_key = :tag AND f.role IN ('bitmap', 'raw')
)
SELECT c.asset_id
FROM candidate c
WHERE NOT EXISTS (
  SELECT 1 FROM asset_tag_masks x
  WHERE x.asset_id = c.asset_id AND x.tag_key = :tag
);
```

这个 SQL 只说明单词候选，排序、范围和照片可用性仍复用查询引擎。多标签 ANY 必须先按 `(asset_id, tag_key)` 扣遮罩，再对照片去重；不能因为照片遮住 A 就把仍满足 B 的照片整体排除。需要 ALL 时对有效 key 集合求交或计数，首版自动桶可以只开放 ANY。

多字段索引的最左列要对应检索方向，不能指望 `(asset_id, tag_key)` 同时高效服务按 tag 起查。[SQLite 查询规划说明](https://www.sqlite.org/queryplanner.html)

### 5.3 首屏使用有界双路径

只有反向候选查询也不够：常见标签命中几十万张时，先构建全部候选再排序，比顺着已有时间索引读取首屏更慢。

建议先交付这条确定性策略，不维护一个昂贵的精确选择率系统：

1. 从当前范围、当前游标之后，按已有排序索引最多检查 4096 个候选资产。
2. 如果得到足够一页（实验为 200 条），直接返回该页。
3. 不足一页，则转到标签反向索引方案，按同一范围、游标和最终条件查出完整这一页。
4. 两步在同一短读事务里完成；回退结果替代探测结果，不简单拼接，避免重复/遗漏。
5. 继续翻页使用稳定排序键与资产 ID 作为游标。无可用排序索引的模式直接走候选查询；跨库首版按库分组，不提前构建全球统一顺序。

4096 是实验起点，成本有上限；深页 OFFSET 不能当作该策略的替代。首版先支持能稳定使用索引的排序路径，现有其它排序需在接入时单独核对。

此策略不依赖过期结果缓存。进入/重读依然读取最新 catalog；磁盘变化经过现有重扫/监视链对齐。前端取消旧查询，结果携带范围与版本，旧结果不能覆盖新选择。

### 5.4 合成实验

脚本与完整结果：`experiments/photo-organization/bench.mjs`、`100k.json`、`1m.json`。

环境：WSL，Node v26.5.0 自带 SQLite 3.53.3；内存数据库，已建索引并 `ANALYZE`，预热后 7 次中位数（物化写入为 3 次）。10 万 / 100 万照片，分别有 15 万 / 150 万源文件，约 25 万 / 253 万直接来源关系；常见词命中约 63%，稀有词约 0.1%。

| 取排序后的首 200 条 | 10 万：逐照片 EXISTS | 10 万：标签索引候选 | 10 万：有界双路径 | 100 万：有界双路径 |
| --- | ---: | ---: | ---: | ---: |
| 稀有标签 | 108.33 ms | 0.08 ms | 4.29 ms | 12.75 ms |
| 常见标签 | 0.51 ms | 25.60 ms | 0.56 ms | 0.85 ms |
| 无匹配标签 | 88.43 ms | 0.002 ms | 3.99 ms | 8.31 ms |

百万照片时，常见词索引候选首屏约 345 ms，精确计数约 310 ms。给巨型目录增加一个标签的纯内存写入，单条规则约 0.003 ms；物化 10 万 / 100 万条关系约 24.84 / 288.54 ms。磁盘 WAL、同步、IPC、真实 catalog 的宽表与额外条件都不在此实验中。

**可下的结论**：查询方向选择重要；目录写入放大可以避免；实时统计全部标签不值得作为首版要求。**不能下的结论**：成品在 Windows 真库上已达到这些延迟。实验不是 Rust 集成测试、真实照片库或 GUI E2E。

实验还断言两种查询的完整结果相同、双路径首屏相同、三来源去重、来源移除后补位、遮罩在目录重刷后仍生效、解除遮罩后恢复。

### 5.5 计数与词典搜索

- 标签面板先列词，不自动对每一行做跨库精确 `COUNT(DISTINCT asset)`。
- 当前选中标签的数量允许异步返回；计数与名单使用相同有效标签语义及库范围。没有算完显示待计算，不显示假零。
- 词典排序沿用手动使用统计/近期使用作为建议；它不是照片查询的真相，也不宣称离线全库精确。目录和 AI 不灌进“手动常用”排序。
- 按词搜索先搜本地词表，再查关联；中文两字词可用已转义 LIKE，不因 FTS trigram 的三字下限漏掉。查询取消与结果上限是必须的，禁止把无上限模糊搜索扩成任意自动桶条件。

## 6. bucket：身份、离线与跨库

### 6.1 数据位置与成员身份

直接放 `app.db`，不增加 `buckets.db`。锁定、规则、成员与成员排除在同一单写者中提交。

建议给 `assets` 补一个不可变的 128 位 `asset_uid`，桶成员键为 `(bucket_id, repository_id, asset_uid)`；库内 SQL 关联仍使用原整数 `asset_id`。UID 可用已有随机源生成并用唯一约束兜底，无须新增大型依赖。

- UID 表示照片，导入/重扫/路径变化/重新配对保留既有照片 UID；合并拆分照片将来必须有专门映射规则，首版不增加这类操作。
- FileId 加卷号继续服务磁盘对盘，不作为桶成员身份；RAW/JPG 不会各成为一个桶成员。
- 桶同时保存文件名、相对路径、拍摄时间等最小展示快照，可选已有缩略图引用；不存原图或保证离线大图。
- catalog 丢失后从裸文件重新建库，不承诺自动恢复 UID 或桶关联；须恢复 catalog 备份。随机 UID 也不能凭空重建丢失关系。
- 只用 `(repo_id, asset_id)` 是更小的可行初版，但旧备份恢复后 ID 再分配会增加错配风险；因此本建议选择 UID，避免把数据库重建恢复夸成 FileId 能自动解决的问题。

### 6.2 基础交互与降级

建议“锁”含义为**置顶并保护桶本体不被删除**，不冻结成员、不暂停自动加入；需要暂停时单独开关。成员可移出，照片原文件不动。

放入集合幂等；选中项与 flag 走两个明确动作，不暗中取并集。放入后默认保留 flag，让同一批照片还可加入另一个桶。

首版跨库桶按库分组，各组沿用既有排序，暂不做跨库统一时间线/自然排序。仍复用 `PhotoViewingStage / TilesSource`，复合键必须携带库身份，批量操作按库拆分。跨库操作不承诺整体事务：逐库报告成功、失败和离线项。

离线项允许从桶移除，因为这只写 app.db；打标签、评级、导出需要在线库。离线项不能当成“标签为空”参加实时筛选：无筛选时保留占位，开启依赖 catalog 的筛选时放到“离线未评估”组并明确数量，不能默默丢弃或假装命中。

词典 tag 点击默认查当前可读的已打开库；允许进一步限制为当前库/目录。桶点击取持久成员名单。两者共用照片展示与条件引擎，但查询范围须在界面上可见；关闭左面板只隐藏面板，不暗中清掉正在看的结果。

## 7. auto bucket：只补充成员的增量系统

### 7.1 规则与成员语义

首版条件建议：**所属库必选；星级下限、标色集合、赞踩集合、有效标签 ANY**。维度间固定 AND，维度内多选 OR；首版不支持任意嵌套 OR/NOT、正则、桶引用、flag、任意全文条件。库范围在最外层 AND，不能跟其他条件一起 OR。

至少提供一个非库条件，避免空表单误收整个库；如需要“整库自动加入”，以后作为明确动作提供。

复用现有筛选条件编译与星级语义，持久规则用规范化文字及库 ID，而不是全局 tag 数字 ID。相同规则指纹可共享同一次评估，结果分发各桶；新增这一优化不能变成维护第二份规则引擎。

规则修改后只补充符合**新规则**的照片，旧成员保留。修改条件、照片降星、移除标签都不会自动退桶。首版不做“重算并删除旧成员”。

手动移出需要 `bucket_exclusions(bucket_id, repo_id, asset_uid)`：移出成员与写排除在同一事务，自动加入必须检查排除。手动重新放入则清排除并加成员。更改规则保留排除；它表达的是对这个桶的明确拒绝。

### 7.2 哪些变化评估哪些范围

| 触发 | 评估范围 |
| --- | --- |
| 手动标签、遮罩、评级、色标、赞踩、AI 结果变更 | 变化照片 × 依赖这些字段的规则 |
| 导入完成、重新发现文件 | 新照片/变化照片 × 相关库规则 |
| 目录标签变化 | 该逻辑目录的照片 × 引用变化文字的规则 |
| 移动文件、改变源文件归属 | 变化照片 × 依赖目录产生标签的规则 |
| 新建/修改/恢复自动规则 | 所选在线库的有界初始扫描 |
| 离线库重连、外部文件变化被对盘发现 | 重连校对后的待处理范围；无法证明无遗漏时补该库规则扫描 |

app.db 中规则变化与“该规则待补扫”一起提交；catalog 中业务变更与待处理资产/目录 revision 一起提交。内存事件仅用于唤醒，不能作为唯一记录。

对当前活动目录继续复用现有磁盘监视和进入时重读；首版不承诺监视未展开的每个目录。外部变化在对盘发现之后才进入自动桶流程，不能把“无全盘扫描”说成“全盘瞬时发现”。

### 7.3 崩溃、并发与分批

统一扩展现有 catalog 提交后补偿机制，增加可区分消费者的 revision/确认水位。不能让刷新计数的旧确认顺便清掉尚未装桶的工作。

1. 业务事务同时写变化与待处理 revision。
2. 后台从 catalog 的一致快照读取一批（建议起点 1000 张），在 Rust/SQL 现有查询层求值。
3. app.db 单个事务核对桶仍存在、规则 revision 未过期、照片不在排除集，再幂等写成员和展示快照。
4. app.db 提交成功后，按本次处理的 revision 确认 catalog 工作；确认期间产生的新 revision 必须保留。
5. 崩溃在确认前会重放；唯一约束保证不重复。规则变更使旧任务失效，由新 revision 的补扫收敛；手动移出后过期任务也会被排除记录挡住。

新规则初始扫描先记录待扫任务，分批按稳定资产键推进；扫描期间的变更继续进入待处理记录，完成后补这些变化。避免一个长读事务撑大 WAL。持久队列要合并同资产/同目录范围，量大时合并成库级补扫，不能无限积累事件日志。

并发先限制为最多两个库读评估、app.db 一个写者；工作间让出执行机会，不争抢解码/导入。限额与 1000 行批次是调度起点，不是硬性的性能承诺。

不能依赖 `ATTACH + COMMIT` 解决 WAL 模式的多库崩溃原子性，SQLite 只保证单文件内的原子提交；因此采用可重放的分步提交。[SQLite ATTACH 事务说明](https://www.sqlite.org/lang_attach.html)

**一致性降级需要明确接受**：自动桶评估的是后台实际读取的已提交状态。若照片短暂满足条件、又在评估前被改回，不承诺保留这段瞬态命中；离线期间未观察到的变化也不补历史。如果要求“曾经命中过一次就必须进桶”，必须存完整事件特征或同步求值，成本和复杂度明显增加。首版建议不追溯瞬态。

## 8. AI 的边界

本轮预留独立来源、类别映射版本、模型版本、输入内容版本及置信度，不选模型、不新增推理依赖。待做时仍只输入 384px 缩略图，输出少量固定类别；置信度低就不生成标签，照片源像素改变使旧 AI 结果失效并排队重评。

任务完成前核对输入版本，旧图推理结果不能覆盖新图。失败不能把部分结果写成完整集合；若原结果来自已失效输入，保留原始证据但不参与有效 AI 集合，直到有效结果重新提交。

固定类别映射到持久的文字 tag_key；改界面语言不改变这个映射。AI 重新执行可以恢复其来源证据，但不能清遮罩、覆盖手动来源、改写词典常用排序。这样以后换模型仍不用改合并与过滤算法。

## 9. 左栏与命令的具体建议

崔总已明确：toolsbar left 的 `buckets / tags` 两开关、互斥、重复点击关闭；开启时上半区为当前面板，下半区保留库目录；三点分隔条可上下拖动，各自有限高。

建议补齐以下默认值，数值待 Pencil 稿确认：

- 状态只有 `none | buckets | tags`，切换函数 `next = current === clicked ? none : clicked`。
- 第一次开启按扣除分隔条后的可用高度 50:50；后续恢复一个共享比例，切换 buckets/tags 不跳高度。
- 上区最小高度建议 160 CSS px；下区建议 220 CSS px，且不得小于自身固定控件高度加现有目录树 88px 下限。密度变化统一读取布局令牌。
- 总高不足两区最小高度之和时，保留最小高度并允许左列外层滚动，禁用无可用余量的拖动；不偷偷覆盖另一面板、不把最小值压到 0。支持的最小窗口尺寸下应优先避免进入此降级。
- 沿用三点 `SplitHandle`、按帧更新、松手保存比例；现有 `SplitStack` 需要核对把手占高后的最小比例计算，修正只在原组件/数学函数中完成。
- 下方库目录保持同一组件实例，保留滚动与展开状态；开关不重建 PhotoGrid。children 在 JSX 插入点 `untrack`。
- 首版仅接 browse；import 的来源目录不是已入库照片，先不扩展同名入口语义。
- 加入桶按钮位于 toolsbar mid 标签按钮旁；拖入复用现有 tile 拖动载荷，并增加库+照片 UID 适配，不复制拖拽实现。

命令体系：将面板两开关、加入桶（选中/flag 两动作）、移出桶、桶锁/解锁、暂停/恢复自动加入、禁止/解除标签等可触发动作登记统一 catalog，启用条件取自同一上下文。首版新增动作的 **`defaultKey` 全部明确留空**：低频、现有面板/拖动入口足够，避免占据现有编辑/浏览键位；仍允许在设置中分配，走既有冲突和保留键检查。标签添加沿用现有入口，不创建第二套命令。

## 10. 功能取舍顺序与迁移边界

建议能力顺序是**文字标签底座及查询 → 手动桶及跨库适配 → 有限 auto bucket → AI**。这是复杂度建议，不是本轮已批准的实施计划。

| 先不做 | 换来的收益 | 保留的体验 |
| --- | --- | --- |
| 标签层级/同义词/自动翻译 | 遮罩与索引始终精确、无语义漂移 | 中文、Unicode、大小写规范化 |
| 全局改名/合并/跨离线库删除标签 | 无跨库分布式迁移与“复活”问题 | 添加、移除来源、禁止、词典查找 |
| 面板全部标签的实时精确计数 | 避免每次变更重算所有库 | 当前筛选数异步查询 |
| 任意规则树、负向条件、桶套桶 | 依赖追踪与增量范围可控 | 库 + 常见标记 + 标签 |
| 跨库全球排序/全球时间线 | 避免多库分页合并和离线快照排序一致性 | 一个桶含多库，按库分组浏览 |
| 瞬态命中历史、所有目录即时外部监视 | 不存无界事件历史、不持续全盘扫描 | 已发现且已提交状态最终收敛 |
| 第一波 AI 推理 | 避免模型、打包、阈值与重评干扰底座 | 三来源协议一次定好 |

已有数据库必须走 `store/migration.rs`：迁移前快照、版本闸门、事务、完整性检查。实施时再分配迁移版本，避免与其他工作抢版本号。

旧 `asset_tags` 迁移为 manual：在原配套 app.db 可可靠解析名称时映射到文字 key，合并同 key 的关联，catalog 保存本地词条；无法解析或来源有冲突的旧 ID 保留为“未解析旧标签”，不猜成新词、不静默删除、不用它匹配语义遮罩。当前裸整数模型已经丢失的名字，迁移算法无法恢复。

迁移需由协调层把已核实的旧词条映射交给 catalog 的现有迁移事务，而不是新增启动时临时 ALTER 或另一条修复通道。app.db 词典是可补建的输入建议，失败不回滚已可靠提交的标签真相。

后续实现验收必须覆盖：全部来源组合与遮罩、无来源的禁止记录、空值/64 字符/Unicode/NFC/大小写、同 key 重复、RAW 归属、目录路径变化、任何来源更新失败、批量事务回滚、ANY/ALL 遮罩语义、双路径结果一致、断电重放、移出与自动加入竞争、规则修订与离线重连、旧 ID 缺名/冲突、跨库同整数 ID 不串照片。负载实验保持手动运行，不加入秒级单元测试默认路径。

## 11. 需要评估的产品取舍

1. 接受“精确规范化文字”语义，不做同义词；不在首版做改变 key 的全局改名。
2. 接受保留被遮住的来源证据，以便取消遮罩恢复；显式手动添加会解除同文字的禁止。
3. 接受目录按逻辑路径绑定、普通子目录不继承，`_RAW` 沿用既有照片归属；外部改目录名需重新绑定。
4. 接受自动桶只补不退、手动移出永久排除（直到手动放回）、不追溯后台未观察到的瞬态。
5. 接受首版跨库按库分组、离线照片保留占位但不参与实时 catalog 筛选判断；不做全量标签实时计数。

以上均为本轮建议，不能在其他记忆/计划文件里登记为崔总已拍板。
