# 导入判重与冲突兜底（内容指纹）

> 2026-10-12 立项。触发：崔总做「重复导入」测试时导入在第 32 张**报错并中断**
> （`数据库错误：UNIQUE constraint failed: asset_files.rel_path_folded`）。
> 同日崔总给出判重口径（见 §2）并要求按此实施。
> 规格正文遵循 `AGENTS.md` §5.4；进度只看 pi 的 `todo`。

---

## 1. 现状与根因（代码级）

### 1.1 判重的三层（改动前）

| 机制 | 位置 | 判据 |
| --- | --- | --- |
| 源侧判重（跳过） | `import/plan.rs` `skip_reason` → `KnownSources::contains` | **源文件身份** `(卷序列号, FileId128)`；兜底 `(源绝对路径 folded, size, mtime)` |
| 目标侧冲突（改名让位） | `import/plan.rs` `resolve_conflict` | **只问盘**（`FsProbe::file_exists`）+ 本批 `claimed` + 续跑 `Reserved` |
| 落库 | `store/assets.rs` `insert_file` | **裸 INSERT**，撞 `UNIQUE(rel_path_folded)` 即报错 |

### 1.2 三个缺陷

1. **判重只认「源是谁」**：同一批照片换个目录再导（拷贝一份 = 新路径 + 新 FileId）一条也匹配不上。
2. **冲突判定不看库**：库里有一行、盘上没有（标了缺失/回收站/差分刚登记）时规划当成空位 → 撞唯一索引。
3. **落库无兜底**：`apply(Op::Register)` 的 INSERT 在 `CatalogSink::flush` 的**一个批事务**里 → 一条撞库 = **整批回滚**、run 停在 `running`。违反规格 §4.4/§4.5「单个文件失败不打断整批」。

### 1.3 真实竞态（本次中断的直接成因）

导入把文件写进 `photos/` → 文件监听（`repo.rs` `CatalogWatcher` → `catalog://dirty`）触发差分同步 →
`store/rebuild.rs::rescan_scope` 抢先登记这些新文件 → 导入自己的 `Op::Register` 稍后插同一路径 → UNIQUE 炸 → 整批回滚。

### 1.4 已修（Phase A，2026-10-12 落地）

* 冲突判定同时吃**盘 ∪ 库**（`plan::KnownTargets`，lib 从 `asset_files.rel_path_folded` 读）；
* 登记兜底三态：路径空 → 插入；已被登记且**角色 + 大小一致** → **认领**（不插新行，补来源列）；不一致 → **只这一条失败**，不中断整批；
* `Op::Register` 自带状态（`imported`），执行器不再补 `Mark`（否则兜底标的 `failed` 会被盖掉）。

## 2. 口径（崔总 2026-10-12）

1. **指纹只用于「导入时 × 同一目标目录层」的防重确认**，很轻量：
   不做跨目录判重、不作为库内相片的身份/唯一性、不加唯一索引。
   同一内容后来落到库内多个目录（用户改了导入模版）是允许的 —— 库内收敛交给将来的移动功能。
2. **同名比较键 = 渲染后的目标名**（库内实际文件名，如 `MYP1000022.JPG`），不是源文件名。
3. **指纹口径**：位图**全文 sha256**；RAW 用**采样指纹**（不动全文，见 §5）。
4. 库内老照片**没有指纹**时：在命中「同一目标路径被占」时**实时建立并回填**，不做全库批量回填。
5. **同步竞态**（§1.3）：落库侧**认领**，不新增跨模块互斥。
6. **关掉「避免重复导入」**：不查指纹、不做内容判定，纯重名改名让位（与改动前一致）。

## 3. 判定（逐文件）与改名（整组）

### 3.1 配对（plan 阶段既有的东西，不新增规则）

源侧分组键 = `(源内真实目录, 折叠主体)`（`plan.rs`），与 workspace 左侧勾了哪些根无关 ——
每个源根跑一次 `plan()`，`source_dir()` 是相对该根的目录，所以两个同名源目录不会串组。
分组的职责只有三件：**命名**（jpg 与同组 RAW 同名）、**落位**（组里有位图 → RAW 落 `A/_RAW`；
源里没有位图 → RAW 落 `A`）、**改名时整组一起改**（§3.3）。

### 3.2 逐成员判定（命中即停）

对每个成员，在**它自己的落点路径**（`compose(dir, stem, ext)`）上问一句：

| 状态 | 条件 | 动作 |
| --- | --- | --- |
| **Free** | 该路径盘上、库里都没有 | 直接导入（不碰指纹） |
| **Skip** | 占用，且**大小相同 + 指纹相同**（口径也要相同） | 跳过这一条（原因写明「同一张照片（内容一致）：库内 <路径>」） |
| **Conflict** | 占用，但大小不同 / 指纹不同 / **无法核对**（库内文件缺失、读不动） | 需要改名（§3.3） |

* 大小不同的候选**不算同一份**：`size_bytes` 相同才去读指纹（省掉绝大多数无谓读盘）。
* 「无法核对」按 Conflict 处理：宁可改名导入，也不覆盖、更不把源照片丢掉。
* 判定**逐文件**：允许「jpg 已在库、只补导 RAW」这种只导一个的情况。
* 侧车（`.xmp` 等）不是照片，规划期就跳过，不参与。

### 3.3 整组消解（改名）

* 组内**任一**要导入的成员是 Conflict → **整组（所有要导入的成员）共用一个后缀**：
  在 `A/` 与 `A/_RAW/` 上一起找最小的 `n`，使每个要导入成员的 `<stem>_0n.<ext>` 都 Free
  （`_01…`，复用全项目唯一口径 `plan::collision_stem`）。
  —— 保证 `A/MYP1_01.JPG` 与 `A/_RAW/MYP1_01.RW2` 仍然同名配对（否则库侧按 stem 配对被拆成两个格子）。
* 组内 Skip 的成员不参与改名（它不导入）。
* 已有 `Reserved`（续跑时我们自己留下的名字）优先于占用判定：能落回原名就落回原名。
* **跳过的成员不消耗序号**：内容判重命中时把已取的号**回滚**（`Sequences::restore`），
  免得一次「重复导入」把库里的编号往后推。

### 3.4 关掉防重

`PlanOptions::avoid_duplicates = false` 时：§3.2 的 Skip 分支整个不生效（不读指纹），
只有 §3.3 的重名让位照旧 —— 想强制重导就重导一份 `_01`。

## 4. 数据模型

迁移 `catalog_0021_content_hash.sql`（走既有迁移框架，纯加列，可空，不回填数据）：

```sql
ALTER TABLE asset_files ADD COLUMN content_hash      TEXT;  -- 小写 hex；NULL = 未建立
ALTER TABLE asset_files ADD COLUMN content_hash_kind TEXT;  -- 'sha256-full' / 'sha256-sample'
```

* 这两列是**派生缓存**，不是真相源：删了只会让下次判重多读一次盘。
* **不加唯一索引**（口径 1：指纹不是库内身份）。
* 查询走既有的 `UNIQUE(rel_path_folded)`（按目标路径查，不做全库名字扫描）。

## 5. 指纹算法（`media::fingerprint`）

| 口径 | 算法 | 用在哪 |
| --- | --- | --- |
| `sha256-full` | 整文件字节的 sha256（仓库已有 `sha2`） | 位图 |
| `sha256-sample` | `sha256(size_le_u64 ‖ head 1 MiB ‖ mid 1 MiB ‖ tail 1 MiB)`；文件 ≤ 3 MiB 时取整文件 | RAW 及其它大文件 |

* **口径由媒体类型决定、不随大小变**（比较要求口径相同，随大小变就永远比不出相等）。
* RAW 不做全文哈希：单张 10–25 MB，采样只读 3 MiB（`AGENTS.md` §2.24 的减法）。
* 判「同一份内容」需**三条同时成立**：口径相同、hex 相同、`size_bytes` 相同。
* 采样口径理论上存在「采样相同而内容不同」的可能（大小也相同）—— 判重会把它当同一张，
  这是刻意的取舍（不是安全边界）。

## 6. 建档与回填时机

| 时机 | 做什么 |
| --- | --- |
| 导入复制后 | 对**库内副本**算一次指纹（位图全文 / RAW 采样），随登记落库 |
| 判定命中占用、库内那行没有指纹 | 对**库内那一份**实时计算 → 同一批事务里回填（`Op::SetContentHash`） |
| 源文件侧 | 只在 §3.2 的 Skip 分支需要时读；同一次规划内按源文件缓存 |

## 7. 冲突兜底（三种情形，都不许中断整批）

| 情形 | 处理 |
| --- | --- |
| **A. 规划时路径被占**（盘或库） | §3.2/§3.3：Skip 或整组改名 |
| **B. 登记时路径已被别人登记，且大小与刚复制的文件一致** | **认领**（不插新行，补来源列） |
| **C. 登记时路径已被登记，大小不一致** | 只标这一条 `failed`（原因「库内已有同名路径、内容不同」），**不中断整批** |

实现抓手：`apply(Op::Register)` 先查一次；真插入包在 `savepoint` 里，撞 `UNIQUE` 就
`ROLLBACK TO`（连新建的 asset 行一起撤）再走 B/C —— 任何单条冲突都不可能带走批事务。

## 8. 计数与界面

* `import_items.reason` 文案区分：同一文件（身份）/ 同一来源（路径+大小+mtime）/ **同一内容（指纹，带库内路径）**。
* 「已导入 / 跳过 / 失败」三个计数口径不变；C 类冲突进失败清单（可导出）。
* **不改界面结构**；文案走既有 `reason` 通道。

---

## 9. 与「导入 XMP 配置」的关系（`specs/xmp-sidecar.md` §7 修订）

* sidecar 采纳只在**整组完整导入**时发生（拆分/改名/跳过 → 不采纳）：plan 需要把
  「这一组是否完整导入」的信息交出来（`PlannedItem.complete`），随 `NewAsset` 传到外壳。
* 判重与 sidecar 采纳共用的正是**同一个分组**（§3.1），不另起一套。

## 11. 实施中采用的口径（崔总 2026-10-12 未逐条否决，按此执行；复核可改）

1. 库内同名行**盘上文件缺失** → Conflict（改名导入），不跳过（跳过会让源照片永远进不了库）。
2. 组内**部分跳过**：库内 jpg 内容不同(Conflict)、库内 raw 内容相同(Skip) → jpg 改名 `_01` 导入、raw 跳过。
3. **续跑**（崩溃重来）：`adopt` 整组一致 —— 组里任一成员有上次的名字，整组沿用同一个后缀。
4. plan 之后、登记之前别人抢占同名路径（§1.3 竞态）：登记侧认领（大小一致）/ 单条失败。
   **这是最终口径，不是欠账**（崔总 2026-10-12 定）：这种「占位的是另一份文件」的情况**不改名**，
   就判这一条导入失败（错误清单里写明「库内已有同名路径、内容不同」）—— 极端窗口、代价可控，
   不值得为它加一条「事后动文件」的路径（那会带出组一致性、失败模式与测试三处新成本）。
5. 库内**同 stem 的 RAW 在 `A` 层**（早先单独导过 RAW），本次成对导入要落 `A/_RAW/名`：
   判定只看该成员自己的落点目录 → 会形成同一资产下两个 RAW 副本；**暂不处理**（罕见，属库内整理）。
6. 源文件名与库内不同名但内容相同 → 照常导入（不做跨名内容判重，口径 1）。
