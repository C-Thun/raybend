> 单元：**导入（库外/来源目录）网格的取图与按时间分组**。崔总 2026-10-11 定方案，逐条按回话实施。
> 三轮把设计写歪过（见文末「走过的弯路」），本文是**最终口径**。
> 相关：`memory/FUNCTION-BROWSE.md`（按时间分组）、`lib/time-group.ts`（分组算法唯一实现）、

## 0. 崔总口径（原话，实施不得偏移）

> ① 使用文件信息内的创建时间建立初始框架，这个瞬间就可以完成
> ② 把 source_time 的逻辑整合进读文件信息的流程（现在不是动态多线程处理的吗？），干掉
>    source_time，也就不存在什么 TIMES_BATCH 了
> ③ 做好界面随多线程文件构建实时重排界面时间分组框架的效果，我认为以目前的速度来说，基本不影响
>    用户操作，因为刷框架的速度远快过用户滚目录的速度
> ④ 时间信息放在每张图片的缓存中，这样切目录的时候有缓存直接根据缓存中的信息构建按日期分组框架，
>    做好与实时读取的信息竞态即可（可能存在缓存未构建完全的情况，所以还是需要对比一下，反正死活读
>    一遍文件列表呗）

后续修正（同一天，口述）：

* **既然已经解了 EXIF，就把整块 EXIF 放进缓存** —— 鼠标点向 tile 时 flowinfo 立刻有内容，不再读盘；
* **缓存读了就是真相**（不要去写「缓存只是加速」那种绕法）；
* 第 ④ 条的「竞态」= **读完文件列表后与缓存对账，只把「未处理的」推进队列**（不是全推）；
* 界面重排要**精细化**：一张的时间变化只会导致三件事 —— 见 §3 的界面层；
* **消费者固定 2 个**（瓶颈在磁盘不在计算）；
* 缓存**按目录分开建树**；目录**卸载再挂载**（拔盘重插）时清掉重读。

## 1. 三层模型（每步处理的关键信息）

### 第 0 步 · 清单层：一次文件系统读

| | |
| --- | --- |
| **输入** | 目录路径 |
| **读什么** | 一次 `read_dir` + 每条的 `size / mtime / created`。**不打开任何文件** |
| **每张产出** | ① 身份（目录 + 文件名 + 大小 + mtime，后面所有缓存按它匹配）；② 类型（位图/RAW）；③ **初始时间** = 文件名里的日期 → 否则 **`min(created, mtime)`** |
| **去向** | 直接给界面 → **瞬间**搭出按日期分组的框架与格子 |
| **代价** | 几百张几毫秒~几十毫秒（「1 秒够了吧」——绰绰有余） |

为什么 `min(created, mtime)`：从卡上直接读时两者一致；复制过来的文件 `created` 是**复制那天**、
`mtime` 才是拍摄那天 —— 取小值才与「按时间」的正确顺序一致，显示日期也不会比排序看起来晚一大截。

### 第 1 步 · 队列层：对账 + 只推未处理的，2 个消费者不停吃

* 清单到手后与**该目录的缓存**对账（缓存按目录建树，身份 = 大小 + mtime）：对得上的**直接用缓存**
（缓存就是真相，不再读盘）；对不上的（新图/换了内容）**才推进队列**。
* 队列**固定 2 个消费者**，只要队里有没处理的一直吃；**不是屏幕驱动**、滚出屏幕**不撤销**。
* 屏幕唯一的权力：把窗口内**还在队里未处理**的**提到队首**。

### 第 2 步 · 一次读拿全（出图那一次）

* 打开这个文件一次（就是出小图那一次），从同一份字节里拿：
  1. 小图（384 字节）；
  2. **整块 EXIF**（拍摄时间 + 相机/镜头/曝光/光圈/ISO/焦距/GPS/软件…凡 flowinfo 要的）；
  3. 显示尺寸与方向（渲染这一步本来就知道）；
* **绝不**：为时间/EXIF 再读一次文件、不调会去嗅探整文件的接口（`image_dimensions`）、不取真身。
* 去向：**写进「该目录该张图」的缓存条目**（会话级，按身份匹配；文件变了自动不命中）。

### 第 3 步 · 界面层：只做两件事 + 局部重排

1. **填格子**：结果填进**已经存在**的格子（不重挂、不重建 DOM）。
2. **按时间模式下渐进重排**，一张的变化只有三种操作：
   * ① **建一个新的日期分类**（此前没有这一天）；
   * ② 把它**从原来的分类移除**（该分类空了就删掉这个分类）；
   * ③ 把它**加入新的分类**（按拍摄时间插到该天的正确位置）。
   **禁止**「收到一批 → 整表重排 → 整树重建」。
* **两层都升序（先到后）**（崔总 2026-10-12）：日期层由早到晚、层内按拍摄时间升序；
  增量维护与整表分组（`lib/time-group.ts::groupByTime`）必须是**同一个方向**，不许一边一种。
* 判定门槛：**时间/来源没真的变就什么都不做**（缓存查询的常态是「没变化」→ 滚屏时零重排）。
* 「只升不降」：EXIF > 姊妹继承 > 文件名 > 创建时间/mtime。

### 第 4 步 · 切目录 / 拔盘

* 清单照旧重读（便宜、必做，用来与缓存对账）；
* 先按缓存把框架搭到最真（零 I/O），再只把未处理的推进队列；
* **拔盘（卸载）→ 忘掉该目录的缓存**（`dir_meta_forget`）：下次插回来重新读，不拿旧盘的信息当真相。

## 2. 红线（效率的硬约束）

1. **tiles 这条路上不许有第二次读文件**（时间/EXIF 随出图那一次读回来）。
2. **任何一条 IPC 都要毫秒级返回**：实测一条 6 秒的命令会把与它不相干的请求全按住
   （连 2–3 ms 的状态轮询都被拖到 1.7 s；注入的 JS 排到 12 秒才执行）。
3. **在飞请求固定 2**（前端队列与后端消费者都对齐）：一次 8 个响应涌进 WebView 主线程，
   滚动输入就轮不到处理（「滚不动」的直接原因）。
4. **缓存查询零 I/O**：界面要时间只查缓存（`dir_meta_ensure` 的 `cacheOnly`），
   查不到就保持清单层的兜底时间，等它真的出图时补上。

## 5. 走过的弯路（记在这里，免得下次再走）

1. **把「读文件信息」理解成「再单独读一遍全目录」**：做了 8 × 48 张的独立补读流程，
   纯额外 I/O、还和出图抢磁盘 —— 真机实测 ON 比 OFF 慢十几倍。要的是**搭在本来就在做的读上**。
2. **保留了「界面逐张拉」的投递方式**，还把整目录一次性压进队列：几百次往返 + 几百个响应
   全砸在 WebView 主线程上 → 「滚不动」。正确形态是固定 2 个消费者、界面只提优先级。
3. **把缓存说成「只是加速」**：崔总指正 —— 缓存读了就是真相；对账只看「有没有」，
   没有的才去处理（推队列）。
