# M1-7 步骤 5：5000 张规模 + 重启后状态一致

完成时间：2026-09-16 12:44:07 CST

## 验的是 M1 完成定义里那条

> 建库 + 导入 **5000 张**照片，**重启后状态保持**。

## 怎么验（全部可重复执行）

```bash
# ① 5000 张：建库 + 导入 + 计时（详见 perf-baseline 记录）
target/debug/examples/crash-drill seed /tmp/rb-scale 5000
target/debug/examples/crash-drill import-once /tmp/rb-scale/repo /tmp/rb-scale/src

# ② 重新打开库 → 状态是否保持（第二遍导入全部判重即证明「账还在」）
target/debug/examples/crash-drill import-once /tmp/rb-scale/repo /tmp/rb-scale/src

# ③ 同规模下崩溃 + 重启 + 续跑
bash scripts/crash-drill.sh /tmp/rb-crash-scale 5000 2500
```

## 结果

**① 导入**：11.27 秒，5000 张全部成功；`assets=5000 asset_files=5000 imported=5000`。

**② 重启后状态保持**：第二遍 0.19 秒走完，**5000 张全部判重跳过**（`skipped=5000`，`imported=0`）
——说明重开库之后，判重所依赖的身份、来源与序号状态都还在。

**③ 崩溃 + 续跑（这次撞上了最坏的时间点）**：

```text
崩溃现场：未收尾批次 1 个 / imported 2620 / pending 2380 （其中目标文件已存在 29）
.part 残留 1 个（允许：说明那次复制被打断了）
库里的账：imported 5000 / skipped 2620 / failed 0
磁盘上 5000 个文件；库里 imported 的目标路径 5000 个
  ✓ 磁盘上没有任何一张照片出现两次（按内容核）
  ✓ 每张源照片在库里都恰好有一份（不丢也不多）
  ✓ 磁盘与库里一一对应（既无孤儿也无缺账）
  ✓ assets / asset_files 与磁盘文件数对得上
```

**「目标文件已存在 29」是关键**：崩的那一刻有 29 个文件已经复制到了目标名字下、那一行却还没提交
——正是步骤 2 修掉的那个重复风险的现场。修好之后，续跑**认得**这 29 张、直接登记不重拷，
所以最终磁盘上 5000 个文件、库里 5000 条，**一对一的按内容核对**通过。

**网格侧的量级**：同一批数据在 5 万张时窗口计算仍是 72.6 µs/次（见 perf-baseline 记录），
说明「网格在几万张时会不会炸」在逻辑层已经过关；**视觉上的卡顿与否仍归人类在真机确认**。
