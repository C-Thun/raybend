## 2. 算法：它到底在做什么

```text
① L = log2(亮度)                         ← 乘性曝光差变加性
② 边缘保持多尺度分解
     B1 = 引导滤波(L, 细半径)   D1 = L  − B1    ← 细尺度（质感）
     B2 = 引导滤波(B1, 粗半径)  D2 = B1 − B2    ← 中尺度（结构）
③ base 压缩：T(B2)                        ← 「降整体光比」（绕中点的有理式软压缩）
④ detail 分级增益：D_i + gate·soft(g·D_i)  ← 「抬局部反差」
⑤ L' = T(B2) + Σ…，再按 2^(L'−L) 缩回 RGB  ← 只动亮度，保色相
```

**为什么它能同时做这两件事**：逐像素曲线（曝光/反差/高光/黑区）有一条数学天花板 ——
一条曲线整体压光比意味着平均斜率 < 1，于是任意两点的差值也被一起压小，局部反差跟着塌。
这一支多了一个**空间维度**，所以两件事不再互斥。这也是它与 `contrast`（全局反差曲线）
的本质区别，`AGENTS.md` §11.5 的术语条目按这个口径写。

**四道门控**（缺一道就会在某一类照片上翻车）：

| 门控 | 不做的后果 |
| --- | --- |
| 阴影（`shadow_floor`） | 阴影抬亮 + 微反差 = 噪点放大器 |
| 噪点（`noise_reference`） | 平坦区（天空、墙面）里全是颗粒 |
| 端点（`highlight_cut`） | 死黑死白附近出现「爬行」的假细节 |
| 局部对比（软饱和） | 强边缘推成光晕与塑料 HDR 感 |

## 3. 关键决策与理由（含四个**踩出来的**坑）

### 3.1 为什么选引导滤波，不选双边滤波

双边滤波在强边缘附近有**梯度反转**：边缘一侧本该更亮的像素反而变暗，base 层长出反向过冲，
detail 层就带一圈光晕。引导滤波是局部线性模型，结构上不会反转。
`filters.rs` 有一条 `guided_model_rejects_gradient_reversal` 专门钉这件事。

### 3.2 `analyze` 与 `apply` 分离 —— 拖得动拉杆的全部秘密

分解（贵）只依赖图像与尺度参数，**与强度无关**；强度只驱动压缩量、增益与重组（便宜）。
所以渲染线程把 `LocalToneState` 与线性源一起常驻，**拖动这根杆本身根本不重算分析**。
不这么切分的话，24MP 每帧重跑一遍分解，就是 `AGENTS.md` §11.4 那种「拖一格就断」的病。

### 3.3 坑一：`eps` 的量级错了（差点让整个功能白做）

引导滤波的正则项 `eps` 决定「多大算边」。初版取 `0.0025`（幅度 0.05 stop），
实测**所有**信号都被判成边（a ≈ 1）：纹理全留在 base 里、被压缩一起压平，
detail 层无货可增 —— 局部反差当场塌掉一半。按真实照片的信号量级重新定标：

| 信号幅度 | 方差 | eps=0.0025 留在 base | eps=0.25 | eps=0.60 |
| --- | --- | --- | --- | --- |
| 噪点 0.02 stop | 0.0004 | 0.14 | 0.00 | 0.00 |
| 细纹理 0.20 stop | 0.04 | 0.94 | 0.14 | 0.06 |
| 中等纹理 0.35 stop | 0.12 | 0.98 | 0.33 | 0.17 |
| 结构边 1.0 stop | 1.00 | 1.00 | 0.80 | 0.63 |
| 强边 3.0 stop | 9.00 | 1.00 | 0.97 | 0.94 |

取 `fine_eps = 0.25`、`coarse_eps = 0.60`：纹理归细节、边缘归 base。

### 3.4 坑二：`added_detail` 返回的是**增量**，不是细节

写成了 `target = T(B2) + gate·(added_D1 + added_D2)` —— 等于用增量**替掉**了细节本身。
后果是拉杆一离开 0，整张图的纹理全部消失、只剩一层压缩过的 base。
`strength == 0` 的恒等单测看不见它（那条路径提前返回），守它的是
`tiny_strength_is_almost_identity`（强度 1e-6 走真算法路径）。

### 3.5 坑三：软限幅在 limit 以下也在衰减

用 `x/(1+|x|/limit)` 当「安全网」封 base 压缩量，它在 `|x| = limit/2` 时已经吃掉 33%。
结果 1.54 stops 的压缩被削成 0.95，**光比压缩从承诺的 55% 掉到 75%** ——
而单看代码完全看不出来。改成真正的软饱和：`|x| ≤ limit` 时原样返回、超过才平滑收住
（`soft_saturate`，拐点处两侧导数都是 1）。

### 3.6 坑四：分块并行时把「块底行号」当成了图像高度

`apply_rows` 给上采样器传的 `height` 决定了纵向缩放比。传 `first_row + 本段行数` 时，
分析图是全图的 1/4 情况下每个块各算出一个不同的缩放比，**块边界会出现横向条带**。
守它的是 `applying_at_a_larger_size_covers_every_row_without_banding`
（已做反面验证：把 bug 放回去，测试立刻红）。

### 3.7 删掉了「黑场锚」（试过，代价大于收益）

初版有一条「离 p02 往上 2 stops 内压缩量渐退到 0」的黑场锚，想法是「最深处不许被抬」。
实测两件事：① 平滑渐变图的 p05 与 p02 几乎重合，锚一盖就是一大片，
**光比压缩从 55% 变成 86%**；② 而它想防的「纯黑被抬成灰」其实由**乘法**天然保住了
（`0 × 任何倍率 = 0`）。所以整条删掉，只留 `base_limit` 封病态的过度抬升。
用户想要更深的黑场，用 `blacks` 参数 —— 不该在这里偷偷替他设。

### 3.8 为什么是「融合的一趟」而不是两张图

24MP 的中间线性图是 144MB 的内存往返，而这条链本来就是逐像素的。
所以把局部色调映射**融进 `render_rgb8` 那一趟**：读一次源、写一次显示像素。
`LocalToneRows` 就是为了这件事从 `apply_inplace` 里抽出来的 ——
「怎么算」只有一份，两条路都调它（`fused_path_matches_the_two_step_path` 钉着）。

## 4. 实测数字

`cargo run -p raybend --example local-tone-probe -- /mnt/c/src/tmp/pic/P1000019.RW2 /mnt/c/src/tmp`
（本机 WSL，dev profile `opt-level=2`，22 线程）

### 4.1 耗时

| 场景 | 像素 | 耗时 |
| --- | --- | --- |
| 合成 6000×4000 缩到 1/4 | 1.5MP | 15 ms |
| **analyze**（与强度无关） | 1.5MP | 110 ms |
| **apply** 预览档 1920×1280 | 2.4MP | 14 ms |
| **apply** 1:1 档 6000×4000 | 24MP | 99 ms |
| 真机 RAW 5184×3888：线性解码 | 20MP | 1432 ms |
| 真机：分析图 + 线性链 | 1.26MP | 222 ms |
| 真机：analyze | 1.26MP | 156 ms |
| 真机：apply 预览档 / 1:1 档 | — | 11 ms / 67 ms |

**结论**：`apply` 与现有管线（24MP 默认 75ms、带色度 126ms）同一量级，
W3 口径 #1「参数一变就重算全尺寸」站得住。**拖动动态反差杆本身只需要 apply 那 11/67ms**；
只有曝光/反差/高光/黑区/色温变了才会触发重新 analyze（缓存按 `Resolved::chain_key` 失效）。

> 优化记录：`RowUpsampler` 最初每像素做 5 次浮点除法 + floor + 浮点转整数，
> 把横坐标下标与权重改成**整帧预计算一次**之后，1:1 档从 331ms 降到 99ms。

### 4.2 效果（真机 P1000019.RW2，预览档）

| 强度 | 暗部 p02 | 亮部 p98 | 光比 | 相对原始 |
| --- | --- | --- | --- | --- |
| 0.00 | −8.9585 | −0.5404 | 8.42 stops | 100% |
| 0.25 | −8.5008 | −1.0070 | 7.49 stops | 89% |
| 0.50 | −8.0556 | −1.4702 | 6.59 stops | 78% |
| 0.75 | −7.6394 | −1.9228 | 5.72 stops | 68% |
| 1.00 | −7.2478 | −2.3819 | 4.87 stops | 58% |

暗部被抬 1.71 stops、亮部被压 1.84 stops，光比收到 58%（`compression_floor = 0.55`
的承诺 + 细节层的贡献）。暗部从 8bit 的 14 级抬到 22 级 —— 是「开阴影」不是「加雾」。

## 6. 遗留问题与已知偏差

1. **会放大噪点**：`D1` 里就是噪点。门控压住了平坦区的增益，但真正干净的解法是先降噪 ——
   所以 M3-W4 的 `lumaNr` 做出来之后，这个模块排在降噪**之后**更顺。
2. **`chain_image` 会把超过 1.0 的高光夹掉**，融合路径不夹 —— 于是「分析看到的图」与
   「实际处理的图」在溢出区略有差异（分析端少算一点高光余量）。影响很小，
   但如果将来发现高光压缩不够，先看这里。
3. **编辑器直方图仍是 SOOC 的**（W3 遗留项，计划里归 W4）。滑杆紧贴它下面，
   已在旁边写明一句，免得被当成 bug。
4. **`analyze` 要 110–156ms**，它由「线性链参数」变化触发（拖曝光就会重算）。
   若体感不够跟手，下一步可以：把分析图缩得更小、或让分位数估计对曝光做解析补偿。
5. **参数命名**：`dynamicContrast` / 中文「动态反差」由 Agent 起（人类授权）。
   若将来要做「自动参数估计」（L0 规则层），这根杆可能要改成双极 —— 届时是**新口径**，
   要写迁移而不是悄悄改范围。
6. **没走命令注册表**：这是编辑参数、不是用户可触发的命令，按 `AGENTS.md` §2.15 的
   判断基准**不适合接入**（它本来就会出现在快捷键设置之外）—— 依据是「摄影师工作流」，
   不是「像 VS Code」。故未给 `defaultKey`。

## 7. 给人看的验收清单（E2E 归人类，`AGENTS.md` §2.8）

前三条是**最短门槛**，后四条是同一条清单的继续（都在 Windows 产物上做）：

1. 进编辑 → 右栏「总览」页，**直方图下面**应当多出一根「动态反差」；
2. 拖它 → **画面跟着变**（暗部抬亮、亮部压住，同时纹理不变糊），松手落库；
3. 拖回 0 → 画面**逐位回到原样**；
4. 拖它时**直方图不变** —— 那是已知项（旁边写了说明），不是 bug；
5. 同时拖「曝光」→ 画面会重新分析一次（约 0.2–0.4s），这是预期的；
6. `Ctrl+Z` → 回到拖动前的值；
7. 「影调」页签里**不应该**有第二根「动态反差」（同一根杆只允许出现一次）。
