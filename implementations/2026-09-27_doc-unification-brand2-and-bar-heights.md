## 关键决策与理由

### 1. 辅色那条我读错了规矩 —— 改的是**文档措辞**，不是设计

`DESIGN.md` §5 原来写「**这是一条全局规则，所有元素一律遵守**：鼠标指向 → 辅色底」。
这句话在**语境**上只讲「指向 / 点击」两个状态，但**读起来像在给辅色划独占领地** ——
我就是这么读的，于是把导出里「处理中/已完成用辅色框（锁定）」「当前操作区用辅色边框（焦点）」
判成了「违规」。人类当场纠正：**那不是问题**。

所以修法是**给规则限定作用域** + **补一节讲清辅色的职责**（§5.3），而不是改设计、也不是改实现。
两条硬规则只保留：① 与「点中」有关的一律用主色；② 同一处不要用主色与辅色表达同一件事的两个程度。
并且写明判据冲突时**先看识别率**——不要为了「守规矩」把界面搞糊。

> 这正是「**规格漂移引发误判**」的一个实例：措辞的模糊不是文字洁癖问题，
> 它会让下一个人（或下一个 agent）做出错误的改动。所以这次统一**不是**为了好看。

### 3. `design/export.md` §7 的命令表：那是一份**看起来像规格的废弃提案**

原表标着「命令（**建议 id**）」，实现却落成了另一套（7 条里 5 条 id 不同），而且**没有回填**：

| 原表（建议） | 实际在 `catalog.ts` |
| --- | --- |
| `export.queue.add` | `export.enqueue` |
| `export.selection.clear` | **无独立命令**（复用 `edit.clearSelection` —— 原表正文自己就这么说，表格里却写了另一个 id，**自相矛盾**） |
| `export.queue.resetAll` | `export.reset` |
| `export.start` / `export.stop` | `export.run`（一个开关） |
| `export.scope.cycle` | `export.scope` |
| `export.stopAll` / `export.save` | ✅ 一致 |

另外原表给开始/停止的结论是「**留空**（建议 `Ctrl+Enter` 备用）」，实现把 `export.run` 的默认键
定成了 **`Mod+Enter`** —— 实现侧有记录、理由也站得住（开关 + 不与输入态冲突），但设计文档没同步。

→ 已按实际条目回填，并加一条约束：**以后定完键位，同一轮就把实际 id 写回本表**。
