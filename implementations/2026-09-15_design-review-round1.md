## 关键决策与理由

### 1. hover 与 selected 用不同色相（而不是不同深浅）

旧的 `DESIGN.md` §5 定义 hover 是「叠一层极淡前景色」（灰），selected 是主色低透明度。
用户的新规则把 hover 改成**辅色底**、selected 改成**主色底**。这不只是颜色替换：

> **用色相区分比用深浅区分强得多** —— 用户一眼能分辨「我只是划过」与「我已经选定」。

### 2. 「实色 vs 低透明度」按面积分档（不是两套语义）

用户说「所有的选中都做成主色底」。但若工作流胶囊、Recent 行、树行、库卡片**全都是主色实色**，
一屏会出现 6+ 处实色主色块，界面会变成绿色的 —— 直接违反 `DESIGN.md` §1.3「主色要用得克制」。

折中：**小控件（分段胶囊、磁铁方块、图标按钮）= 主色实色；大面积（行、卡片）= 主色低透明度**。
两者都是「主色底」，只是浓度不同。已在 `DESIGN.md` §5.1 与 `main.md` §7 标注为待确认项。

### 3. 「不要强制展开树」简化了实现

用户提的这个细节实际上**让实现变简单**：

```text
树的展开状态 = 纯用户操作状态，不受选中状态影响
选中背景色   = 渲染每一行时，判断该行目录是否 == 全局选中目录
```

不需要任何「为了显示选中而展开」的逻辑，也不需要维护「展开到某层」的命令式调用。
树没展开到那一层时那些行根本不存在，自然不会显示选中 —— **这个"问题"会自然消失**。

### 4. Ark UI 适配性核对结论：修改成本低

用户要求核对现有方案在 Ark UI 中的适配性。查证的结论：

| 设计中的部件 | Ark UI | 成本 |
| --- | --- | --- |
| 三段拖拽 `SplitHandle` | `Splitter`（Panel / ResizeTrigger / ResizeTriggerIndicator） | 低 |
| 来源目录树 | `TreeView` | 低 |
| 工作流胶囊 / 密度分段控件 | `ToggleGroup`（单选）或 `RadioGroup` 样式化 | 低 |
| 磁铁方块 | `ToggleGroup` 单项 | 低 |
| 包含子目录开关 | `Switch` | 低 |
| `easy copy` 气泡 + 复制 | `Tooltip` + `Clipboard` | 低 |
| 帮助菜单 / 弹窗 | `Menu` / `Dialog` | 低 |
| tile 缩放滑块 | `Slider` | 低 |
| **照片网格虚拟化** | **无** | **中** —— 需自研 `VirtualGrid`（已在 `PLAN.md` M0-6 规划） |
| **`shortpath` 缩写** | **无** | **中** —— 纯字符串算法，需自实现 |

**结论：除两项本来就要自研的以外，其余全部有对应部件，无需为迁就组件库而改动设计。**
