# 「为什么真机 import 还是卡」诊断记录（读，不改代码）

> 时间：2026-10-11 23:0x（本记录完成时间见文末）
> 方法：走仓库既定的真机通道 `pnpm perf:win` 那一套（Windows `--remote-debugging-port=9333`
> → 已授权的 `netsh portproxy` 9334 → WSL 侧 CDP），连进**正在运行的 debug 应用**，
> 在页面里拦 `fetch`（Tauri v2 的 IPC = `http://ipc.localhost/<cmd>`），逐条记录前端发出的命令与耗时。

---

## 1. 结论（一句话）

**渲染路径没有慢，慢的是「按时间分组」那一次性的 `source_times` 批读**：它一次读 306 个文件的
EXIF、在真机上花 **6.0 秒**，这 6 秒里**整个 IPC 流水线和界面都被它占住** —— 屏幕上是占位 + 转圈，
新图只能等它结束才开始一张张出来（用户看到的「卡 4、5 秒才出一张」）。这轮改的 JPEG/384/内存缓存
**全部生效，但被这 6 秒盖住了**。

---

## 2. 三组实测数字（都在真应用里，不是探针模拟）

### 2.1 渲染路径：快

| 项 | 实测 |
| --- | --- |
| `thumb_get` 热（同一张再取） | **11–14 ms**（内存缓存命中） |
| `thumb_get` 冷（首屏没渲染过的 JPG） | **143 ms/张** |
| 8 路并发冷渲染 8 张 | **271 ms**（≈34 ms/张） |
| 屏上图的档位 | **384×288 / 288×384，~25 KB JPEG** ✓ 这轮口径生效 |
| 空闲时 IPC 往返（volumes_list / export_queue 这类） | 1–4 ms |

### 2.2 卡点：`source_times` 一次 6 秒

前端进入目录后的命令序列（时间轴，均取自真实 IPC 记录）：

```text
+  171ms  source_scan        6ms
+  951ms  thumb_get ×8      11–14ms   ← 首屏里已在内存里的那几张
+  955ms  source_times      6033ms   ← ★ 一次读 306 个文件的拍摄时间
+ 1777ms  thumb_get        5213ms
+ 2537ms  thumb_get        4455ms
+ 3310ms  thumb_get        3682ms
+ 4111ms  thumb_get        2882ms
+ 4899ms  thumb_get        2093ms
+ 5590ms  thumb_get        1402ms
+ 6281ms  thumb_get         711ms
+ 6984ms  thumb_get           9ms   ← 与 source_times 结束（+6988ms）同一瞬间
+ 6988ms  source_scan / organization_reconcile  796ms
+ 8383ms  thumb_get        3712ms   …（第二波，继续排队）
```

读法：`source_times` 跑着的时候发出去的每一条 `thumb_get`，**都在它结束的那一刻才回来**
（5.2s → 0.7s 依次递减 = 队列被按住后一次性放行）。同一时刻，我在页面里注入的 JS
也**一直排到 +12 秒才被执行**（主线程同样被按住了）。

### 2.3 反证：没有 `source_times` 时，一切正常

对**已经按时间读过一遍**的目录再进一次（`pic2`）：前端压根不再调 `source_times`，
同一套 `thumb_get` 变成 **144–351 ms**、状态 200 带真 JPEG 数据，`requestAnimationFrame`
全程只有一次 250 ms 的断档（界面不卡）。→ 卡的就是那一条命令，不是渲染、不是 IPC 基建。

## 3. 为什么会这样

1. **一次通吃**：`src/features/photo-grid/store.ts` 的 `TIMES_BATCH = 512`
   （2026-10-11 改的，注释里写「实测 306 张读 EXIF 只要 ~140 ms —— 贵的是往返次数」）。
   那个 140 ms 是**在已缓存的目录上、用 release 探针**量的；真机上第一次进目录时，
   这 306 个文件是**冷读**（145 个 RAW 各 20–30 MB），单条命令就变成 **6 秒**。
2. **一条命令占住整条流水线**：这 6 秒里后续 IPC 全部排队（§2.2 的递减数列直接量到了）。
   界面同时被冻住（注入的 JS 12 秒才轮上）—— 用户感受就是「像被阻塞住」。
3. **并且它和缩略图抢同一批文件**：`source_times` 的 4 线程读头 + 首屏 RAW 的解码同时压磁盘，
   两者互相拖慢（我随后在空闲态逐张 `file_exif` 实测只要 **2.8 ms/张（JPG）/ 3–56 ms（RAW）**，
   可见那 6 秒主要是冷 I/O + 互相争抢，不是 EXIF 解析本身贵）。
4. **滚屏更差**是因为每滚出新一批就有新的冷解码（RAW 完整解码 1.2 s/张、JPG 冷 143 ms/张）
   排在同一个流水线里，还要和「按时间」这类长命令抢位。

---

## 4. 建议（按性价比）

1. **把 `source_times` 拆小并让出**：`TIMES_BATCH` 512 → 32~64，每批之间 `await` 让出一帧
   （`store.ts` 的循环骨架本来就有 `setTimeout(0)`，改常量就见效）。长命令变成一串短命令，
   缩略图就能插进去 —— 治「6 秒全冻」。
2. **两次全目录读合并成一次**：`dir_meta_ensure`（宽高/方向）与 `read_times`（拍摄时间）
   **各自把 306 个文件头读了一遍**。一次读同时返回两者，冷进目录的 I/O 直接砍半。
3. **时间戳按文件身份缓存**（size+mtime，会话级，跟 `dir_meta_ensure` 的缓存同一套）：
   同一个目录再进来（以及编辑后回网格）就不用再读一遍。
4. 顺带确认（登记待查）：Tauri v2 的 `ipc.localhost` 请求是否**串行处理**。若成立，
   「任何一条命令不许长时间占住」就该写进架构纪律（现在只写在缩略图那一侧，不够）。

## 5. 我自己的两个失误（记下来，免得重犯）

1. **该先读仓库现成的真机通道**：`scripts/perf-win.mjs` 开头就写着「exe 带
   `--remote-debugging-port=9333` 起、WSL 经已授权的 portproxy 9334 直连」——我却先去自己搭
   反向隧道，白花了一大截时间。**下次要连真应用，先看 `perf:win` / `shot.mjs`**。
2. **探针测的是「空闲 + 热缓存」的稳态**：`examples/source-import-probe` 反复跑同一个目录，
   文件早进了系统缓存；真机首次进入是冷读、且同时在跑别的命令。**「探针快、真机慢」不是探针撒谎，
   是场景不同** —— 以后真机诊断一律以拦 IPC 的实测为准，探针只用来比同场景下的相对变化。
