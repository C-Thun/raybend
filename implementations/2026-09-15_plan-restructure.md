由用户指出流程问题后做的**规划结构重构**，不涉及产品代码。包含两部分：

1. **重构**：把「一次性规划整个 M0」改为「一次只规划一个工作单元」；

## 问题与根因

第一轮规划把 **整个 M0 的 7 个波次一次性铺成一份计划文件**（还把 M0 之后的设计阶段也塞了进去），
提交 plannotator 后产生了 70 个 progress 条目。实施中暴露两个问题：

| 问题 | 表现 |
| --- | --- |
| 计划文件范围过大 | 实施中的变更会让整份计划的勾选状态失真，计划文件与真实进度脱节 |
| tracker 被未开工条目占满 | 50 条未开工条目常驻界面，干扰「现在该做什么」的判断 |

根因：**把「路线图」和「实施计划」混成了一个东西**。路线图（M0 要验证哪些未知）是稳定的；
实施计划（这一波具体怎么做）在开工前才应该细化，提前一年细化必然失真。

## 关键决策与理由

### 1. 计划文件命名改为 `plans/<milestone>-<单元>.md`

`plans/M0-1.md` 而非 `plans/M0.md` —— 名字本身就声明了范围（M0 的第 1 个工作单元），
避免下一次又往里塞新波次。

### 2. 归档用「普通列表」，不用 `- [ ]` 勾选框

`PLAN.md` 附录 A 里的归档内容**刻意不写成勾选框**，因为：
`mark_done` 会**真实改写计划文件**里的勾选状态 —— 只要文件里有 `- [ ]`，就可能被当成待办跟踪。
写成普通列表 + 开头明写「**⚠️ 不要把下面当成待办清单直接开工**」，从数据结构上杜绝误跟踪。

同理，`PLAN.md` 中 M1–M6 的「完成定义（DoD）」也从 `- [ ]` 改为普通 `-`（**23 条**）：
路线图描述的是「什么算完成」，不是「勾掉什么算做完」。

### 3. 归档内容的选择

附录 A 保留的是**仍有参考价值**的部分（不是原文照搬）：

- **A.1 平台验证分工**：哪一步在 WSL 做、哪些必须在 Windows 复测 —— 这条在 M0-1 实测后依然有效
- **A.2～A.7 各波次的检查项**：当时的思路与踩坑预警（如 RapidRAW「差 1 像素」的坑）
- **A.8 剩余 DoD** + 已达成部分
- **A.9 UI 设计阶段**（M0 之后、M1 之前）
- **A.10 UI 层选型实测数据**：Ark UI / Tabler 的版本号、组件数、活跃度对比 —— 原本只在 `plans/M0.md` 末尾，
  现移到 `PLAN.md`，同时把 `AGENTS.md` §7.6 / §7.7 的「见 `plans/M0.md` 文末附录」改为「见 `PLAN.md` 附录 A.10」

### 4. 关于 `mark_done` 清空未完成条目

`plans/M0.md` 删除后，`mark_done` **没有文件可改写**了 —— 这一点解除了此前「勾掉会把假的『已完成』
写进计划文件」的顾虑。因此这次调用 50 次 `mark_done`（step 18–66、68）清空了 tracker，
**它只是重置 tracker 状态，未在任何文件里留下虚假的完成标记**（已用全仓库 grep 验证：0 个 `- [ ]`）。

## 验证方式

```bash
# 1. 全仓库无未勾选框（原 50 + 23 = 73 条）
grep -rn "^- \[ \]" --include="*.md" . | grep -v node_modules
# → 无输出

# 2. 无指向已删除文件的引用
grep -rn "plans/M0\.md" --include="*.md" AGENTS.md PLAN.md DESIGN.md README.md
# → 仅 PLAN.md 附录里那句「完整原稿：git show cfb84a2:plans/M0.md」（有意保留）

# 3. tracker 归零
# → "Plan Complete! ✓" / "PLAN MODE OFF"

# 4. 工作区干净
git status --short   # → 空
```
