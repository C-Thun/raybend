# catalog 版本升级中的必需预置图生成

需求时间：2026-09-29。

## 需求原文

> 关注一下catalog.db/app.db的升级程序，对于app来说可能启动时如果要migrate升级，那在splash界卡一会儿我可以接收（这个我理解不会太慢），但是catalog.db假设要升级，假设后来增加了新的生成一些预置图的要求的话，可以考虑在catalog上线后（能自动进入升级程序，同时可以有个弹窗加遮罩禁掉用户的操作，提示用户`库数据升级中`

本轮范围确认：崔总选择「本轮修正启动和遮罩流程」，预置图生成本身等具体要求确定后再接入。

## 背景与落点

本轮 SQL 迁移继续走 store/migration.rs；CatalogSessions 自动重连/打开已经接入自动迁移。现有 MigrationGate 负责全窗口阻塞，升级快照按执行 ID/revision 处理晚监听与多 catalog 并发。

预置图的类型、资产范围、版本触发条件尚未给出；不得把现有任意可重建缓存都变成全库强制等待。具体需求到来后，以本文原文和 memory/FUNCTION-REPOSITORY.md §2.2.1 写一个工作单元的规格。

## 验收要点

- 必需生成任务属于整体库升级，SQL 已完成不能提前撤掉升级遮罩。
- Rust/worker 生成，分批、幂等，持久记录完成状态，中断后续做；新增 DB 状态只走现有 SQL 迁移框架。
- 掉盘、缺原图、损坏原图、空间不足和单图失败的等待/重试策略必须具体定义。
- 5 秒位置探测上限不能把长生成任务当成拔盘故障；保留同库单飞与 I/O 预算。
- 不在前端实现图像处理，不把图片生成塞进 SQL 长事务；缓存删除后仍能从原图与配置恢复。
