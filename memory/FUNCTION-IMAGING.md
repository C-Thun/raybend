## 0. 总原则：**库外 vs 库内**

| | 范围 | 取数方式 |
| --- | --- | --- |
| **库外** | `import` 里的源目录（还没进库） | **实时列目录、按可见区取小图**（2026-09-29 慢机械盘修订）：不先扫全目录元数据；首次小图仍须摆正方向 |

## 1. 格式支持范围（人类 2026-09-24 定）

### 1.1 位图

| 方向 | 范围 |
| --- | --- |
| **导入** | **jpg / tiff / png / webp / avif + heic，共 6 种** |
| **导出** | **webp / avif / jpg / png，共 4 种**；TIFF RGB16 仅供 browse 外部编辑器输出（2026-09-26 定案）（**不含 HEIC**） |

### 1.2 RAW

- **导出（2026-09-28 定）：只导出「标记为 RAW 的 issue」** —— RAW 以一条标记行回到 export tiles 的 issue 条，
  选中它导出的 **IRA = RAW 直接转码的灰度图**（空栈直走解码管线，**不经任何曲线与修改**，供与原图对比）。
  **原 RAW 文件本身没有「导出」概念**（将来或另给「复制出去 / 打开所在目录」）；导出格式仍是 webp/avif/jpg/png 四种。
- **导入：尽量支持**，能力跟着 **rawler 基础库**走（后端候选见 `memory/FUTURE.md` §B）：
  * 普通马赛克（Bayer）先支持全；
  * 早期的 **X3**（Sigma Foveon）可以不支持；
  * 富士 **X-Trans** 看工具（rawler）是否支持决定。

### 1.3 JXL 与快照

- **JXL**：未来支持**导入 / 导出全流程**（等生态成熟）；**不用于缓存 / 快照**。
- **issue 大图快照**：**恒为 AVIF**（收回「将来换 JXL 做快照」的设想）。
- AVIF 的编码代价实测与「为什么是 AVIF」见 `memory/FUTURE.md` §C8。

### 1.4 实现前提（现状事实，别忘）

| 格式 | 现状 | 要做什么 |
| --- | --- | --- |
| **avif** | ✅ **已接**（2026-09-24）：`image` 的 `avif-native` feature（底层 **dav1d** 静态库）+ `ravif` 编码器 | 已做：Rust 侧能解我们自己的缓存图（`display::pixels_from_avif`）与导入的 avif。**待补：真 avif 文件的导入冒烟**（现只有合成图 round-trip） |
| **heic** | `image` **完全不支持**；识别 / 导入 / 建索引正常，**像素链路全断**（缩略图 / 看图 / 编辑器 / 导出都拿不到像素 → 占位图） | 要自带 HEVC 解码器；Windows 上 `<img>` 也不能代劳（Chromium 不解 HEIC）。候选与开工清单见 `memory/FUTURE.md` §C10。**崔总 2026-10-09 定：成本太高，暂不接入**（不在 avif 这一批，也不在近期排期） |

> 浏览器（`<img>` / `view_image`）**不需要**我们解 AVIF —— 它自己会解；
> 需要解码器的是 **Rust 侧要像素**的地方（编辑器 GPU 纹理、缩略图/直方图等本地处理）。
>
> **dav1d 的构建代价**（已沉淀成脚本，别再踩）：WSL 侧靠系统库（`apt install libdav1d-dev`，1.4.1）；
> Windows 侧没有 pkg-config，用**一次性构建的静态库** —— `scripts/build-dav1d-win.cmd`
> （meson + ninja + nasm + VS Build Tools，产物 `C:\rb-deps\dav1d-1.5.0\`），
> 构建时由 `scripts/lib/dav1d-win.mjs` 把位置经 `SYSTEM_DEPS_DAV1D_*` 环境变量告诉 cargo。
> 许可登记见 `THIRD-PARTY-NOTICES.md`（BSD-2-Clause）。

## 2. 库内两种缩图 + 真身：分工总表

| | 谁在用 | 尺寸 / 格式 | 存在哪 | 生成节点 |
| --- | --- | --- | --- | --- |
| **thumb**（缩略图） | `tiles` 网格、**所有** `film` 胶片带、定稿卡片 | 长边 **384**（**只剩这一档**；192 已取消）· **AVIF 90 / 4:4:4** | **`thumbs.db`**（当前共用 `%LOCALAPPDATA%\com.cthun.raybend\cache\_sources\thumbs.db`） | 导入时生成；进 tiles/film 时补齐缺失；编辑落库后刷新当前张 |
| **preview**（**载入占位**） | 看图的第二段还没到时的顶替者、总览、编辑视口的过渡图 | 长边 **1920** · AVIF | **库根 `cache/full/<asset>/…-v<pipeline>.avif`**（跟着库走） | **导入 SOOC 收尾**；编辑 latest 进/出编辑与**提交时**（提交后排队在后台，单飞 + 最新者优先，不押用户动作，2026-10-10）；存 issue 时（后台生成；同栈直接复制 latest 预览，见下） |
| **真身**（看图成品） | `view` / `compare` / `fullscreen` 真正看的那张 | **该变体自己的像素**（不缩放）· **JPEG q92**（~9MB/20MP） | **库根 `cache/full/<asset>/…-full-….jpg`**；**未编辑的 SOOC 不缓存**（直接给原文件字节） | 看图时（冷缓存现算：无编辑 ≤3s、带编辑 ≤5s），命中缓存毫秒级；`view_image(…,"full")` / `export_variant_image(…,"full")` |

> **看图的口径（崔总 2026-10-11 定，`specs/view-true-image.md`）**：看图界面（view / compare /
> fullscreen / editor 视口）显示的一定是**该变体自己的像素**；1920 只做**载入期间的占位**
> （角标「正在载入原图…」，真身一到**原地替换**，zoom/pan/布局一个都不动）。
> ❗**禁止**任何「按缩放档位/容器大小选一个凑合尺寸当看图成品」的逻辑 —— 那是被明确否认的需求。

> ⚠️ **事实纠正**：缩略图**不在 `catalog.db` 里** —— 在缓存库 `thumbs.db`（`AGENTS.md` §6.4 的「小图」那条）。
> `catalog.db` 只存元数据；缓存整目录删掉功能降级但可用（§6.5 的红线）。
>
> ❗**上表只管库内**（崔总 2026-10-11 定，`AGENTS.md` §2.24）：**来源目录（import / 未入库）的图一律 JPEG**，
> 并且**只在进程内存里**（`thumbnail::memory::SourceThumbs`：缩略图档 256 MB、真身档 10 张），
> **一行都不落盘** —— 临时目录下次打开内容可能完全不同，落盘的行永远读不回来。
> import **没有 1920 这一档**（占位直接用 384 顶着；`specs/thumbnail-tiers-and-import-memory.md`）。

### 2.1 显示尺寸口径（2026-10-11，`specs/display-size-source.md`）

**缩图与真身管的是「像素」，显示尺寸管的是「界面上这张多大」——两者独立，但必须同源。**

**每个变体只认自己那一份尺寸**（崔总 2026-10-11 真机：「view 里 raw 图尺寸没有跟着本身走，
而是缩进了 sooc 的尺寸里」）：`sooc` ← 位图行；`raw` ← RAW 行；`latest` ← 栈输出；`issue:N` ← 该定稿。
缺值 = **还没拿到**（由 `export_snapshots` 的懒补读一次文件头补上），**绝不退到别的变体** ——
`?? base` 那种回退会让同一张照片在两次访问之间换倍率（懒补跑前 / 跑后）。

`raw` 行记的是**出图尺寸**（rawler 显影管线的输出，`RawlerBackend::output_size`），
不是文件头的整帧 —— 崔总 2026-10-11：「原则上 rawler 出图是多少，那就应该是多少」
「**对 RAW 来说不能用私自解算像素数来替代正式 develop 输出的真实位图像素数**」。
G9 实测：整帧 5264×3904 / 出图 5184×3888。**展示的分辨率必须等于出图的像素**。

两条来源的分工是钉死的：**位图**认我们自己的文件头解析；**RAW** 只认 rawler 回传。
RAW 行没值就是**未知（NULL）**，不许拿 `assets` 的 EXIF/文件头尺寸顶替，界面按「还没拿到」处理。
详见 `specs/display-size-source.md` §2.1 与 `specs/display-size-lifecycle.md`。

`latest` 的输出尺寸**每次现算**（当前源尺寸 + 栈里的几何）：`develop_stacks.output_*` 那两列
只是当年算好的缓存，源尺寸一修正就旧了 —— 现算拿不到才退回它（`store::sizes::latest_size`）。
布局尺寸 = 该变体尺寸，于是「100%」= **该变体真身的 1:1**（不是 1920 位图的 1:1）。

术语与存储（**与方向一样记在库里**，不再由界面现算）：

| 术语 | 定义 | 存哪 |
| --- | --- | --- |
| **原始轴尺寸** | 文件头里的 width/height（**未**应用方向） | `assets.width/height`（语义不变） |
| **展示尺寸** | `oriented_size(原始轴, 方向)` = 屏上「宽 × 高」 | `asset_files.display_width/height`（+ `orientation`，**每文件一份**） |
| **输出尺寸** | `EditGeometry::output_size(源展示尺寸)`（已含方向与裁切/旋转）**= 该变体自己的源经它自己的几何之后的实际裁切结果**（崔总 2026-10-11：「本质上是定稿的实际裁切」） | `develop_stacks.output_*`（latest）、`issues.output_*`（每条定稿）—— **两处都只是当时算好的缓存**，读侧现算优先（源尺寸会被修正），存值只兜底 |

**唯一解析口**：`crates/raybend/src/store/sizes.rs::display_size(conn, asset, variant)`
（`sooc` / `raw` / `latest` / `issue:N`；老库列为 NULL 时按矩阵回退 —— 回退链写在该文件的文档注释里）。
前端只做选择与回退（`src/lib/display-size.ts`），**不算第二份方向/几何数学**。

❗**读侧的 NULL ≡「现算」，不≡「基准尺寸」**（崔总 2026-10-11 真机反馈后立的账）：
`develop_stacks.output_*` / `issues.output_*` 是 v19 才有的列，v19 之前建的编辑与定稿全是 NULL ——
这种行必须在**读侧按它自己的栈/定稿现算**（`sizes::latest_size` / `sizes::issue_output_size`，
落在 `store::query::page` 与 `store::issues::list`，**零 I/O**）；回退成基准展示尺寸是错的：
那是另一个口径（未裁切的原始画面），真机症状就是「裁过的 latest 被拉成 4:3 的横画面」。
真的算不出来（源尺寸也没有）才是 NULL。

写法要点：

* 尺寸**不进** `DevelopStack` / profile JSON / 哈希 / 签名 / XMP（身份红线）——只进 DB 列；
* 导入时对每个文件（位图 / RAW）各写一份 `display_*`（位图与 RAW 的方向可以不同，各按自己那行）；
  其中 RAW 那份走 `store::sizes::apply_display_size_source` = **出图尺寸**（唯一口径，别处不要另算）；
* 导入前的旧库走**懒回填**：`store::backfill`（缺列的线上文件）、`dir_meta_ensure`（浏览网格读头时顺手写回）、
  `export_snapshots`（切变体时对 ≤8 张顺手补文件行）、`examples/backfill-metadata --sizes`（整库一次补齐）；
  NULL = 未知，消费方回退旧算式，绝不报错；
* 冷启动效率基线：打开任意照片 / 切任意变体，尺寸都是**库里已存的值**——不读文件头、不渲染、不等后台任务。

## 3. thumb（tiles / film 缩略图）

### 3.1 规格（人类原文照录 + 逐条解释）

1. **「导入时就要生成缩略图」**：当前实现 = **384 最长边**（tiles 与所有胶片带共用）的 AVIF，存 `thumbs.db`。
2. **「缩略图严格贴合显示需求，也就是说长宽比超过 4:1 或 1:4 的都会被截成这个比例」**
   —— 全景/超长图按**居中截取**压到设定的比例以内。
   **2026-09-24 追加确认**：人类记不准是 4:1 还是 3:1 ——「**3:1 也没问题，支持大部分相片尺寸就行**」，
   所以**保持现状 3:1**（`MAX_DISPLAY_ASPECT = 3.0`；只作用于网格/胶片带，看图档不裁）。
   * **顺序不可反（2026-10-10 崔总报「369×3693 的图很糊」后定）**：必须**先按 3:1 截取、再缩到目标档**。
     取源/解码的尺寸要把这一刀算进去 —— `render::display_aspect_scale` 给出长边会被截掉多少倍，
     `source_input_edge` 据此放大取源请求；先缩到 384 再截，1:10 的图只剩 38×114 像素，
     而 `resize_for_thumb` 不放大，铺满 tile 就是糊的。
     RAW 快路径仍**只读内嵌预览**（`DecodeSpec::embedded_preview`，不为一张网格图真解码）；
     位图内嵌预览（EXIF 缩略图）截完不够满档就退回完整解码。
3. **「缩略图只缩不扩」**：源图小于缩略图尺寸时**不放大**，照常存（现状已满足）。
4. **「显示的时候要在保持比例不变的情况下拉伸至显示区域全满」**
   （2026-09-25 更新：tiles/film 的 tile 仍按此比例裁切；总览改为完整 Screen 图，
   显示框高度随照片比例动态变化、夹在 3:2～2:3（2026-10-13 定））——
   * 目标就是**显示区域那个尺寸（含 padding）**；
   * 大图**缩小**填进去（现状就是这样）；
   * **小图要放大**（保持比例、不裁切）—— **不允许**「比显示区小就保持原始像素」那种写法
     （CSS 的 `max-width` / `max-height` 就是那套，**要避免**）；
   * 网格 tile 用 `cover`（填满 + 居中裁切），胶片带用 `contain`（填满受限的那一轴、另一轴留白）——
     两者都是「填满」，区别只在**要不要裁**；胶片带不裁是 2026-09-19 定的「竖图必须完整显示」。
   * 人类原话的解释：「这样会对一些极小图标不友好，但这是相片管理器不是图片管理器，
     不考虑那种情况；我担心的反而是过小的图案在 tile 里放着太空、在高分屏下看不清」。
5. **「每次进入 tiles/film 时，如果某张图缺缩略图，实时生成并存进去，自然维护数据完整」**
   —— 缺就补，不要求用户做任何事。
6. **「每次对相片编辑时，latest 效果会被重新渲染到缩略图」**
   —— 「鼠标松开拉杆之类的确定调整参数时，背后就要跑一次这个」。
7. **「缩图开始默认就是 sooc/raw 内置位图」**：没编辑过的照片，缩略图就是 SOOC（位图原片）/ RAW 内嵌预览那条路的产物。

### 3.2 issue 切换与缩略图（2026-09-26 更新）

**库内 tiles 读取优化（2026-09-29）**：latest 小图先查原有 `thumbs.db`；未命中时优先从
同源版本、同编辑基准、同管线版本的 latest preview 缩小生成，不能重复套编辑栈/方向。
只有预览缺失或损坏才回退原有原片渲染。镜头/LUT 解析同样延后到确需渲染时。
`+RAW` 复用目录同步后的 catalog 配对信息，不为角标读 RAW；browse 不再顺带读取配对 RAW 的 EXIF。
tiles 的旧 RAW 记录若缺宽高，先用占位比例；明确打开看图/对比时才允许补读。目录实时同步不变。

M3-W6c 的定稿模型以当前 editor profile 为真相：`latest` 是自动保存的工作副本；命名 issue 是不可变完整 profile 快照。切换 SOOC、RAW 或命名 issue 时，把该 profile 写入 latest，同时进入统一撤销/重做历史，刷新当前图的小图、看图和预览。继续调整只修改 latest；配置哈希加完整比较推导当前选中的 issue，不另存选择 ID。匹配优先级为命名定稿 → SOOC/RAW 原始源 → latest；新调整没有其它匹配时选中 latest。定稿资格只排除原始源和已有命名定稿，latest 工作副本不参与去重。

**issue 导出序号（2026-09-28，规格 `specs/export-issue-ordinal.md`）**：每个命名定稿带一个**每照片唯一的序号**（`issues.ordinal`，0–99，最多 100 个定稿、全满拒绝保存）；分配从 `assets.issue_counter` 游标顺找空位、绕圈复用删除留下的洞。导出文件名 = 模版主名 + 强制尾号：定稿 `I00`–`I99`、原片 `ISO`、RAW 标记 issue `IRA`、未匹配 latest `ILA`（latest 优先按哈希匹配已有定稿，匹配上按那个定稿的序号算——export tiles 的显示与导出同一口径）。

**browse tiles 左下角的定稿标记（2026-09-29，完整口径 `memory/DESIGN.md` §12.9.2）**：有命名定稿 → 扇形卡片图标 + **定稿数（1–100，不含 SOOC/RAW/latest）**；没定稿但编辑过（编辑栈与原始源不同）→ 毛笔图标。数据由浏览分页查询带出（`AssetRow.issue_count` / `edited`），与缩略图「编辑过走编辑管线」的判据同一份。

**定稿面板占位先行（2026-09-29）**：editor 点定稿确认后，条目**立刻**出现在定稿面板顶部（名称 + 来源 · 预览生成中，缩略图位转圈），`issue_create` 的整套渲染/AVIF 编码完成后由真实条目原位接替（列表 created_at 倒序，无跳变）；失败/换照片/异常即清占位。实施记录 `implementations/2026-09-29_finalize-pending-placeholder.md`。

**定稿链路提速（2026-10-10，崔总报「一次生成近 1 分钟 + 面板闪」）**：三处一起改 ——

1. **预览刷新离开落库链**：`confirmEdit` 落库后把 1920 预览**排进后台队列**（`lib/preview-queue.ts`：单飞 + 最新者优先；连续调拉杆只渲最后一张），不再 await（高质量降噪下这一张要十几秒，BM3D 在 3840 输入边上）；
2. **定稿快照不在响应里等**：`issue_create` 只写库 + 排队 sidecar 就返回整库，`ensure_snapshots` 在后台线程跑；失败只记日志（真正看图时按需路径会再报）；
3. **同一张图不渲两遍**：定稿那一刻 issue 栈与 latest 相同，后台任务**等 latest 预览落地后直接复制**（`reuse_latest_preview`，最多等 30s；2026-10-10 W2 起改为**后台队列的同 key 单飞等待**（`work::WorkQueue::wait`，条件变量），不再 sleep 轮询）；按需路径（对比 / 全屏）不等，直接渲。

面板不闪：`IssueThumb` 新图就绪前**旧图留守**（只有换照片才清）；缩略图缓存键的修订号只推给会随编辑变的 sooc/raw/latest，命名定稿（不可变）不跟着重建；占位条目超过 300ms 才现身（同切定稿提示的口径，很快返回时不闪一下）。实施记录 `implementations/2026-10-10_finalize-chain-and-preset-dblclick.md`。

原先“切 issue 时保留旧 latest 供返回”的设想已由人类在 2026-09-26 明确替换为“编辑状态一变即更新 latest，包括选中 issue”；返回切换前状态走撤销/重做。

**定稿图自愈（2026-10-10 W5，崔总口述）**：某张照片的定稿三档图缺了（创建失败 / 中途退出 / 缓存被清）——
**进 editor 或选中该定稿时自动补齐**：`issue_snapshots_ensure(repository_id, asset_id, sizes?)` 扫该照片
所有定稿的 `screen`(1920) / `grid`(384) **两档**，只重建缺的；顺序固定
**Screen → Grid**（小图能从 1920 缩，先渲大图 = 每张照片只付一次整管线）。
（192 那一档 2026-10-11 取消。）
静默自愈：失败只记日志，界面**不新增常驻提示**；幂等（全齐时毫秒级返回、零渲染）。
走后台队列 P3 + 同 key 单飞；补过的条目交给 `issueThumbs.refresh`（旧图留守，不闪）。
调用点：editor 的定稿库就绪（60ms 防抖）之后；browse 选中 `issue:N` 变体时（`createBrowseDisplay.onVariantSelected`）。
实施记录 `implementations/2026-10-10_editor-session-w5-issue-snapshots-self-heal.md`。

## 4. preview（编辑预览图）

### 4.1 规格

- **每次进入编辑图片时，对编辑结果生成一张 1920 最大边长的 AVIF**，存在 cache 里（按现有方案）。
- **大部分规则与缩略图一样**（只缩不扩、居中截取口径一致），**但生成节点不同**：

| 节点 | 行为 |
| --- | --- |
| **进编辑** | 生成 / 刷新 preview |
| **退出编辑** | **最后状态更新 preview** |
| **未编辑 SOOC** | 导入收尾生成 SOOC preview；初始 latest 显示复用它，不重复存一份 |
| **原始 RAW** | import/export 缺小图取内嵌图；进编辑后只为当前照片补真实 384，不额外生成 RAW 1920 |
| **存 issue** | **为 issue 生成一张 preview** 供快捷显示 |
| 总览（右上角） | **在合适的时间基于 preview 展示** |

### 4.2 与现有「大图缓存」的关系

现状 `FullCache`：`<库根>/cache/full/<asset_id>/<issue>-src<源签名>-<base>-v<pipeline>.avif`
（`issue` ∈ **`latest-<profile_hash 前 12 位>`** / `issue-<id>-<profile_hash>` / `sooc`；
`base` ∈ `sooc`/`raw` = **编辑基准**，见 §4.3）。
本文件的 **preview ≈ 这个 cache**：`latest-<hash>-raw-v*.avif` 就是「基于 RAW 的编辑结果那张 1920」。
**栈指纹进文件名**（2026-10-10 W2）：栈一变名字就变，旧快照自然失配 ——
落库不再删整目录，旧文件由 `FullCache::gc_latest`（每资产保留最新 2 份）回收；
读取方（过渡帧 / 缩略图 / 定稿复用）统一走 `develop::latest_variant`。
命名定稿创建时生成独立 1920 AVIF，命名包含 ID 与 profile 哈希；latest 缓存失效不删除命名快照。独立 384 缩略图保存在 `thumbs.db`，删除定稿才删除其快照。

> **基准必须进文件名**（2026-09-24 定，已实现）：同一张照片在两种基准下渲染出的是两张不同的图，
> 而 `latest` 只有一个名字 —— 不加这一维的话，切了基准会**读到另一基准渲染的旧图**，
> 而且看不出是错的。基准从**源文件**推（`EditBase::of_file`：RAW → `raw`，其余 → `sooc`），
> 不靠调用方传（传就会传错）。

### 4.3 编辑基准：SOOC / RAW 切换（人类 2026-09-24 定）

* **总览图下给一个切换按钮**，选这次编辑**拿哪个当底**：`SOOC`（相机直出位图）/ `RAW`，
  **默认 RAW**。规则本体：`store::develop::edit_target(conn, asset_id, base)`（`EditBase`），
  缺文件的那一侧**禁用**，不许用户白点。
* **已实现（M3-W6c）**：每个命名 issue 带「基于 SOOC / RAW 编辑」标签，点选时把该 profile 的编辑基准一并恢复到总览切换按钮。
* 同一份编辑栈落在两种像素上观感会有差 —— 所以标签必须跟着 issue 走，不能只存一份全局基准。
* **缓存命名跟着基准走**（已实现）：`cache/full/<asset>/latest-<base>-v<pipeline>.avif` ——
  两个基准各存一份，互不覆盖（理由见 §4.2 的引用块）。

## 5. 大图（`view` / `editor` 看大图）

- **从 sooc/raw 直读，然后做渲染管线**（这是「真正的那张」）。
- **「读出 sooc/raw 原图再做渲染之前怎么办」——人类定：接 AVIF 支持，进来先读 preview**
  ——「因为本身这个分辨率就只有 1920，所以自然有点糊也正常」。
- **载入提示**：这个界面要有**半透毛玻璃**的载入提示（与之前全屏模式的提示差不多），
  但**不要阻挡其他操作**（比如在 film 里点胶片带上的图）；**仅阻挡 view 部分**。

> 依赖：Rust 侧解 AVIF（§1.4）—— preview 是 AVIF，GPU 纹理要像素。
> 浏览器那条路（`<img>`）不需要解码器，但编辑视口是 Rust 直绘，绕不开。
>
> **已实现（2026-09-24）**：进编辑 / 在胶片带上换照片时，**先拿一张已经存在的图顶上**
> （毫秒级），真帧（RAW 全解码 + 管线）随后替换。取图顺序（能找到哪个用哪个）：
>
> 1. **`latest`** —— 大图缓存里**与当前编辑基准同一侧**的那一份（编辑过的照片才有）；
> 2. **`SOOC`** —— 相机直出的位图（同名 JPG）；
> 3. **要编的这张文件本身** —— RAW 走 worker 的内嵌预览，位图直接解。
>
> 三条口径（都踩过）：
> * 过渡帧走**同一条显影通道**（`RenderCommand::Developed`）与**同一个任务号** ——
>   号对不上会被当过期结果丢掉，过渡帧就永远不显示；
> * 它的**逻辑尺寸用原图尺寸**（`media::meta::read_photo_meta` 读头得出，已按方向摆正），
>   不是 1920 —— 否则真帧回来时 `set_image` 会 refit，画面跳一下；
> * 过渡帧期间**直方图是过渡图的直方图**（像素由显影线程当前帧直接给出），真帧到了再刷新 ——
>   这是可接受的，不是 bug；**不写任何缓存**（它本来就是从缓存读的）。
>
> 实现：`src-tauri/src/editor.rs` 的 `transition_plan` / `transition_outcome`。

### 5.1 编辑视口的档位与「拖动中只算预览档」（人类 2026-09-24 定）

| 档位 | 什么时候用 | 算什么 |
| --- | --- | --- |
| **Preview** | 适应窗口（zoom < 1:1）**或手指还按着**（拖杆 / 拖曲线） | 把线性源缩到屏幕档（长边 1920）再跑管线 |
| **Full** | zoom ≥ 1:1 **且已经松手** | 原尺寸跑管线（受 GPU 纹理上限约束） |

* **没有看图档位**（崔总 2026-10-11 定案）：editor 视口与浏览看图**一律原图像素**；
  拖动参数期间也是同一张图、同一分辨率（只是限流合并），**不存在**「拖动用小一号的图凑」。
* **缩放永远是视口变换**：平移 / 放大 / 适应窗口 / 100% 都**不重新出图**，也不弹载入提示；
  视口只有两种「载入」：**换照片**一次（过渡帧顶着 + 「正在载入照片…」），此后不再有。
* **限流两层**：前端按帧合并（同一帧只发最后那个值，`createLatestCoalescer`）；
  后端显影线程收任务前把队列里被顶替的**合并掉**（`merge_jobs`），渲染线程只认最新任务号。
* **仍未做**：1:1 时**只算可见区域**（视口裁切）—— 现在是整张算完再让 GPU 采样可见部分。
  登记在 `memory/FUTURE.md` §D1.5。

## 10. 2026-10-11 import（库外）小图与窗口优先队列

崔总定口径（`AGENTS.md` §2.24）：import 面对的是**外部目录**（相机卡 / SD / 待入老库 / 临时盘），
导入完就不会再访问 —— **不经营缓存**，只要「最快把窗口内那几屏显示出来」。

| 项 | 口径 |
| --- | --- |
| 库外小图格式 | **JPEG q82**（`EncodeFormat::Jpeg` + `render::render_sig_source`）；库内仍 AVIF q90 / 4:4:4（**2026-09-24 那条只限库内**） |
| 缓存身份 | 两套签名，同一个文件先后被 import 与 browse 看时各存一条，互不冒充 |
| 内嵌预览快路径 | **先出像素、比过尺寸再编码**（以前先编码再发现不够大丢掉，白付一次编码，实测 ~118 ms/张） |
| 窗口优先 | 网格在滚动 / 缩放**停下来 0.3 s** 后，把窗口内区间提到队首；请求仍只由可见格子发，滚出即撤 |
| 队列并发 | `min(8, max(2, 核数 − 1))`（留一核给 UI）；以前写死 4 |
| 跨目录内存缓存 | **换目录不再清队列**（blob URL 留着，来回切瞬间出图），LRU 600 封顶；只有 `reload` / 磁盘变化才失效 |
| 按时间读 EXIF | 一批 **512** 张（以前 8 张 × 39 次串行 IPC）；Rust 侧本来就是 4 线程并行，实测 306 张 ~140 ms |
| 选中才拿的信息 | 文件 EXIF 实测 **0.5–1 ms/张** → 仍选中时读，但加 32 条进程内 LRU；RAW 补镜头名走 worker **Low 档**（不再顶掉出图） |
| 进 view 的 screen 1920 | 来源文件走 **JPEG**（实测 AVIF 4.2–5.6 s → JPEG 1.3–2.2 s）；库内不变 |

实测（Windows release，`C:\src\tmp\pic` 306 张）：单张冷渲染 JPG **≈450–500 ms → 202 ms**、RAW ~125 ms；
一屏 24 张（4 路并发、全冷）**3.0–3.9 s → 1.5 s（JPG）/ 1.9 s（RAW）**；命中缓存 0.6 ms。

- 样片与编辑器共用 `Lut::apply_rgb8`，输入为显示参考 sRGB；先应用 LUT，再缩成 384×288。
- 作者伴生封面不重复应用 LUT；按 `design/editor.md` §3.1.1 转为 384×288 或 768×576。

  读取时按版本失效重建；metadata 最后原子发布。不修改 LUT ID、分类或照片引用，也不走第二套数据库迁移。

## LUT 文件身份与移除（2026-09-26）

- `app.db` v7 经既有迁移框架加入 `luts.file_hash` 和索引；SHA-256 按原文件字节计算，不依赖文件名、来源路径或分类。仅注释 / 换行不同也属于不同文件；本次不做颜色语义去重。
- 旧记录先保持 NULL，读取图库 / 导入时在 DB 写线程之外读取私有文件补录。文件丢失时保留 NULL 和原 ID；已有旧重复条目不合并，保护 issue / latest 的既有引用。
- 导入先快筛，再对实际拷入私有目录的字节计算哈希；最终去重 / 恢复在 IMMEDIATE 事务中执行，防止并行导入重建条目。同内容跨分类导入跳过，图库移除后重导恢复原 ID，并归入此次选择的分类。私有副本丢失 / 内容损坏时重导可修复已知哈希的原条目。
- 文件上限 128 MiB，哈希流式读取；新文件按字节快照原子发布。未入库的临时候选目录可清理，已存在的 LUT 文件不在移除操作中删除。
- LUT 移除仅置 hidden；LUT、封面、伴生封面原图与导入来源都保留。图库不展示 hidden 条目，但其文件可用性仍传给编辑器；旧照片 / 定稿继续解析原 ID。自动垃圾回收与硬删除不在本次范围内。
- 删除定稿则移除该配置快照与独立 384 / 192 缩略图、1920 预览；latest、原照片以及对应 LUT 文件保留。两种操作都默认确认，Shift 点击复用 easy destroy 快通道。

### 2026-09-26：M4-W1 源变化与派生图失效

缩略图的统一键在文件身份/路径之外加入大小、精确修改时间（纳秒）与 FileId 的源签名。
latest 和命名 issue 的 AVIF 文件名共用 `FullCache::source_name`，也包含源版本；issue 小图的 render_sig 同样带源版本。
目录同步只失效变化资产的元数据、小图与全部派生预览，不删除 issue 或 profile。
编辑显影线程核对当前源及 SOOC 参照的签名；源未变时仍复用线性图与高质量降噪结果。
照片内容变化后的迟到任务写入旧版本缓存，不会被下一次新源请求命中。

这些签名依据文件系统事实，不是整文件内容哈希；外部工具若刻意同时保留身份、大小和精确修改时间，
需要显式重建派生缓存。这一限制不改变 M3/M4 对原文件哈希不变的真实环境验收要求。
