## 1. 库的物理结构

库 = 用户指定的一个目录（库的根目录）。库根下的结构**由 raybend 管理**：

```text
<库根>/
├── catalog.db              # 库数据库（库身份、资产、导入模版、序号计数…）
└── photos/                 # 导入进来的照片
    ├── 2026-08-15/
    │   ├── MYP0001.png     # 位图按模版改名后放这里
    │   └── _RAW/
    │       └── MYP0001.ORF # 同名 RAW 放同级的 _RAW/ 下（也按模版改名）
    └── 2026-09-02/
        └── ...
```

要点：

1. **`catalog.db` 直接在库根**（不是藏在 `.raybend/` 子目录里）—— 用户明确要求。
2. **`photos/` 是导入的落地目录**；库根下除此之外只有 `cache/` 一个由我们创建的目录。
3. **`_RAW/` 是个保留目录名**：与照片**同级**，放同名 RAW。它出现在每一层落地目录下
   （如 `photos/2026-08-15/_RAW/`），而不是全局只有一个。
4. 库**不强制**目录里只有位图 —— 用户可能自己往里放东西。
   目录里「有啥就是啥」，raybend 不因此报错，只是**登记到库里的**是它自己导入的那些。
5. **`cache/` 是库内大图缓存**（M3-W3 起，人类 2026-09-24 定）：

   ```text
   <库根>/cache/full/<资产 id>/
     latest-v6.avif   # 编辑结果（每个 issue 一份；`v6` 是渲染管线版本）
     raw-v6.avif      # RAW 的基础解码结果（只有 RAW 的资产才会用）
   ```

   * 放**库里**而不是 app data：库搬到哪、换台机器、接外置盘，打开就有图，不必重渲染；
   * 格式统一 **AVIF 质量 90 / 4:4:4**（全系统缓存图一个口径）；
   * `SOOC` **不进缓存** —— 它就是那个 JPG 原文件本身；
   * **整个 `cache/` 删掉**：功能降级（重新渲染一遍），完全可用（`AGENTS.md` §6.5 的红线）；
   * 缩略图（网格 / 胶片带 / 看图小图）**不在这里**，仍在 app data 的 `thumbs.db`。

> ⚠️ 这条相对 `AGENTS.md` §6.4 早先写的 `.raybend/{repo.json,catalog.db,index.db}` **已经变更**，
> 该小节已按本文件更新。`index.db`（派生索引）暂时不建 —— 等真的需要可重建索引时再加，
> 位置仍是库根（`<库根>/index.db`），不进 `photos/`。

## 2. 库身份、多路径与在线/离线

这是本文件最复杂的一部分，用户明确要求支持两件看似矛盾的事：

- **同路径不同库**（同一个目录下换过 catalog.db）
- **同库多路径**（同一个库出现在多个目录，例如同一块盘的不同挂载点、或库被复制/U 盘换盘符）

### 2.1 真相源：中央 `app.db` 记录 + 每库 `catalog.db` 内的唯一 ID

| 位置 | 记录什么 |
| --- | --- |
| 中央 `app.db` | **所有已登记库**：库唯一 ID、名称、导入模版缓存、**该库登记过的每个路径**及其最近状态 |
| 每个 `catalog.db` | **自己的唯一 ID**（`repository_meta.repository_id`）+ 库内数据 |

路径挂载了哪个库，靠「**读该路径下 `catalog.db` 里的 ID**」与 `app.db` 的登记比对得出 ——
而不是靠路径字符串。这正是「同路径不同库」能成立的机制。

### 2.2 状态、身份与操作会话（Storage Recovery W1–W4）

库登记与连接事实分开。`app.db` 的名称、登记路径和最后成功计数可以离线展示；运行态
`ConnectionStatus` 使用 `unknown / checking / online / offline / unavailable / releasing / released`，不能把未知或未找到
当成空库。`offline` 表示位置不可达；身份错配、权限/只读、catalog 损坏、版本过新、迁移失败、
I/O、空间不足、写线程丢失和超时分别保留原因。普通输入错误、单张照片损坏不降级整个库。

- 核心 `availability::resolve_paths / resolve_preferred` 核对已登记路径；catalog ID 是库身份，FileId 是实体身份。
  旧二态 `resolve_repository / path_holds_repository` 只是兼容适配，复用同一探测；生产命令使用具体原因。
- `CatalogSessions` 协调每库一个写者与读池，业务持有 `Arc<CatalogDb>` 租约；最多保留四个闲置会话。
  根位置从同一租约取得。实际打开的 SQLite 连接再次核对期望 ID，禁止失联时凭空创建 catalog。
- 每次获取/读写检查位置与身份；失效作废 generation，关闭读池并在全局锁外退出旧写者。
  尚未执行的队列写在执行点拒绝，已经开始的事务如实返回结果。旧写者退场前不会另起同库写者。
  旧状态触发的重连只可作废它观察到的 generation，不能关闭刚恢复的新代次。
- generation 与状态 revision 分离，IPC 使用十进制字符串，避免 JS 数字精度损失；溢出明确失败。
  旧探测/旧任务的迟到结果不能覆盖新事实。在线布尔从连接状态派生，不另立一份权威。
- 列表只读登记和运行快照，不顺带扫照片。计数复用完整扫描链，读取失败/部分扫描保留最后成功值；
  完整扫描后才更新计数，执行更新时检查原租约仍有效。
- **不使用在线 TTL**。事件、focus、进入工作流与卷枚举是触发；实际打开与操作 I/O 是事实。
  2 秒枚举不能保证看见两次采样间的完整拔插，Windows 句柄行为仍需真机验证。

`App` 持有唯一库状态 store，导入/浏览/编辑/导出/设置/命令订阅同一实例。
离线保留登记、最后计数、当前内容与选择，相关写操作和导出入队受可用性闸门约束。
`lastVerifiedRoot` 仅为保留展示，不是写入授权；恢复后重读当前内容和预览，PhotoGrid 不卸载。
导入/导出长任务捕获原库 ID 与实体 FileId；失联后进入非终态等待，重新取得健康会话后才能续跑。
`TaskCatalog` 只接受原实体，不能自动转写同 ID 副本；旧租约仍失效。外部编辑失联拒绝后续发布，
保留已成功结果，不声称外部程序本身支持自动恢复。

### 2.2.1 数据升级与可操作时机（2026-09-29）

app.db 启动升级可在 splash 等待；splash 先显示，数据库在后台打开，首屏就绪/4 秒兜底都不能跳过尚未返回的升级。catalog 在自动重连/打开、核对库身份后走既有 SQL 迁移，成功前不交付可用会话；未连接的库不会为了升级被搜索整机。

catalog 升级期间显示「库数据升级中」的现有全窗遮罩，暂时阻断鼠标、触屏、滚轮和键盘；完成后自动恢复，失败释放等待并保留故障反馈。每次执行单独记账，多个 catalog 同时升级只有最后一个结束才撤罩；活动快照可补齐晚监听，旧 revision 不能覆盖新事实。

将来若版本要求批量生成必需预置图，升级要覆盖 SQL 后的生成阶段，以持久完成状态支持幂等/分批续做/失败重试。生成由 Rust/worker 执行，不能放进长 SQL 事务；schema 新字段仍走现有迁移框架。具体预置图范围与强制等待策略待实际需求，本轮未实现图片升级任务；5 秒位置探测等待与长生成任务需分开处理。规格见 specs/database-upgrade-gate.md。

### 2.3 已登记位置的重连

手动重新查找、卷变化、focus、进入工作流均可触发探测；released/releasing 不参加自动探测。
不自动搜索整机或未登记的新盘符。
卷枚举由 App 唯一所有者每 2 秒执行，只取卷位置/类型；触发合并 200ms，失败后最多在 1/3/10 秒
各重试一次，真实损坏/权限/版本/位置错误不循环当拔盘重试。事件订阅失败记录诊断，仍载入登记并
使用有界探测，不把整个应用启动卡在订阅失败上。

探测同库/同端点单飞，全局最多四个实际在途调用，单次等待 5 秒。超时只结束本次等待，原生 I/O
尚未退出时继续占预算；不承诺已取消系统调用，也不据此关闭健康任务。app.db 事务只更新 SQL/
内存状态，目录 I/O、探测和 writer/watcher 的 join 在全局锁外。

`repository.reconnect` 接入命令面板及文件菜单；默认快捷键明确留空，原因是低频库维护操作，
保留 Ctrl+K 可达，不占照片操作键。健康在线、无目标或同库已在探测时禁用。

**2026-09-29 修订稿已确认并实施**：所有状态保留齿轮，左侧状态图标负责重查；卡片保持两行，
离线/未找到中性图标提示，原位转圈，真实故障警告图标。共享组件用于导入/浏览/导出，设置统一
由 App 根层装配。画稿 `ZYUxs`/`o7xAe5` 与 browse/export 同源稿，见配对说明；真机观感另验。

catalog 创建、登记和打开执行既有网络/云同步位置禁用策略，来源读取不受该规则牵连。
位置分类识别 Windows `\\?\` 扩展路径：本地盘符仍是本地，扩展 UNC 仍是网络，云目录规则保持。
分类去前缀不改实际 I/O 路径或已持久化路径键。探测触发是非跟踪操作，状态回写不能重新触发
工作流 effect 探测；迟到的设置失败只触发自动核对，不能解除已释放屏障。
分类器和端点提示留作未来 NAS 接缝；识别包含启发式限制，不声称发现所有云客户端或远程挂载。
远程 provider/认证/暂存/远程 catalog 的边界见 `memory/FUTURE.md` G23，尚未接入协议。

### 2.3.1 同库备用位置与手动定位（W1）

“多源”在库层指同一库的可替代位置，用于换盘符等情况；同时只使用一个已验证根，不表示照片
分散存于多个根。库设置顶部展示所有登记位置和当前使用位置，完整路径可复制。离线可开设置，
位置管理无需先连上 catalog；已知离线不读模版触发报错，只有保存/重建等依赖 catalog 的操作禁用。

“定位此库…”与在线“添加位置…”共用目录选择及 `repository_add_location`。按现有位置策略只读
目标 catalog，核对期望 ID 后幂等登记；不创建替代库、不修改目标身份，保留旧位置。验证采用同一
有界探测预算，超时工作者仅验证，不会迟到后自行登记。添加位置不切换健康会话，离线则由统一
重连接口实际打开后恢复；旧任务只在原实体通过核对后续跑。取消与迟到选择不发送登记，迟到 IPC 不写旧弹窗。

移除默认二级确认、Shift 快通道；只撤销本机位置登记，不删除磁盘文件或库身份。当前使用位置
禁用并给出说明；后端在同库会话锁内再次拒绝撤销使用中位置，登记事务与新会话获取互斥。
`repository.locate` 复用设置内的定位动作，离线可执行，默认热键明确留空（低频库维护）；
添加/移除指定位置属于模态内部操作，不另注册全局命令。

### 2.3.2 来源与长任务恢复（W2/W3）

卷变化复用 App 唯一观察器，最近、勾选与当前来源合并单飞重查；展开树有界重读，照片区同路径
恢复也重新扫描。离线保留目录勾选、展开、图片选择和排除意图；代次拒绝旧扫描、计数与元信息。

导入来源捕获目录 FileId（含卷身份），来源失联只挂起该来源，其它来源继续；目标库失联暂停
所有向该目标的写入。等待时保留成功数与文件安全点，取消有效；来源/目标身份无法证明时保持等待。
扫描中断不规划半份清单；pending 目标核对完整内容与来源事实，大小相同不足以接纳。
CatalogSink 保留未提交操作，成功提交后才清空；旧 running 批次已登记成功项在重启重发时跳过，
不依赖「避免重复导入」开关。已完成批次的重新导入仍遵守该开关。

导出 waiting 让出执行槽，恢复重新验证原库实体、输出设备与捕获定稿。停止的预设不会自动开启，
移除/重置的等待项不会复活；队列仍为进程内状态，不提供跨重启恢复未持久化队列。
进度窗复用批准稿 bJD0w，中性等待说明、成功计数、取消与重新检查；模态操作不新增全局命令/默认键。

### 2.3.3 明确副本选择与主动释放（W4）

连接解析将同 FileId 的位置视为别名；同 ID 不同实体同时可达时返回 multiple_locations。
库设置的位置行「使用此位置…」经确认固定实体，存入 app.db 现有 settings 的版本化 key
`repository.preferred_location.v1.<id>`。选定实体缺席时不回退其它副本；添加位置不改变健康会话。
有未完成导入/导出或活动任务时拒绝位置切换；退场旧会话后才连接明确选择的实体。

释放先设置每库屏障、作废会话，拒绝新任务与发布；取消导入、停止该库导出等待意图，排干
活动许可、watcher、读池与写者后变为 released。登记与文件保留，其它库可继续。
缓存的编辑资源只保留可重新申请的 TaskAccess，后台任务须取得短期 TaskPermit，避免空闲缓存
永久卡住释放。released/releasing 不受 focus、卷变化或后台获取解除；明确重新连接才恢复。
屏障持续本次应用会话，重启按正常连接规则；释放不等于 OS 弹出，也不关闭其它应用的句柄。

批准稿 RQzd5 复用同一设置弹窗、位置区重新连接入口及确认组件。`repository.release` 接入
命令面板和文件菜单；默认键明确留空（低频且需要确认，避免误触）。指定位置选择属于模态
参数操作，不新增全局命令。真机四波统一验收见 `docs/removable-storage-acceptance.md`。

### 2.4 添加库的两个分支（用户指定）

```text
用户选中一个目录，点击「添加库」：
  ├─ 该目录下**已有** catalog.db
  │    → 读出其中的 repository_id
  │    ├─ app.db 里已有这个 ID → 这不是新建，而是**登记一条新路径**（同库多路径）
  │    └─ app.db 里没有这个 ID → 把该库整体登记进来（连同它已有的资产）
  └─ 该目录下**没有** catalog.db
       → 询问是「新建库」还是「该目录属于某个已知库」
         · 新建：生成新 ID、建 catalog.db、登记路径
         · 已知库：把这条路径登记到那个库名下（用于离线库换挂载点）
```

- 「一个路径被标记了但没有 catalog.db」→ 该库**显示为离线**，并可在同一路径下**创建库**
  （即补建 catalog.db）。
- **同一路径允许登记给多个库**（`UNIQUE(path_folded, repository_id)`，而不是路径唯一）。

### 2.5 库唯一 ID —— **已定：可排序的定长 base62（`Gid` 裁剪版）**

> **结论（M1-2 已实现，代码见 `crates/raybend/src/store/ids.rs`）**：
> 既不用 UUID v7，也不用原样的 18 位 `Gid` —— 取用户 `Gid` 方案的**裁剪版**：
> **去掉 `shard` 段、固定 16 位**。

```text
[ 时间刻度（10µs 一格，自 SINGULARITY≈2025-06-15） | 随机 40 bit ] → base62 → 左补 '0' 到 16 位
```

**为什么这么定（三条，都是实际收益）**：

1. **可排序**：字母表按 ASCII 升序（`0-9` < `A-Z` < `a-z`）+ 定宽 ⇒ **字典序 = 数值序 = 时间序**，
   于是「按 ID 排序就是按创建时间排序」——数据库索引与 UI 列表都省事。
2. **比 UUID 短一半**（16 字符 vs 36 字符文本 / 22 字符 base64url），且无横线，
   放进文件名、路径、URL 都不用转义。
3. **抗碰撞够用**：40 bit 随机段 ⇒ 同一毫秒内生成也不撞；「一台机器上几十个库」这个量级远超所需。

**为什么不保留 `shard`**：它是为分布式分库准备的，本项目单机、无跨节点协调，收益接近零。
**为什么不用 UUID v7**：它同样时间有序，但要引 `uuid` crate、字符串还长一倍；
用户的方案本身已成熟，裁剪后只需 `u128` 运算（**无需 bigint 移植**），因此直接采用。

> **与 Luclin `Gid` 的互操作**（将来若要把库登记到那套服务端）：需要双向转换 ——
> 补回 `shard` 段、以及 `Gid` 自带的 `toUpper`（base36 大写、定长 20）形式。
> 登记在 `memory/FUTURE.md` **G15**。

```text
            + 随机数(randomSize=6 字节 → 12 位 hex) )
      → 定长 18 字符，不足左补 '0'
校验：长度 18 + 全在 base62 字符集 + 反解回 hex 后能取出原 shard
toUpper：转 base36 大写、定长 20（大小写不敏感场景用）
```

**长度是配置项**（`lengthLimit` 与 `randomSize` 都是构造参数），所以 12 / 16 / 18 位
是同一方案的三种配法：

| 目标 | hex 位数 | 一种配法 | 随机熵 |
| --- | --- | --- | --- |
| 12 位 | ≈18（71 bit） | 时间戳 14 + shard 0 + 随机 2 字节 | 16 bit ⚠️ 偏少 |
| **16 位（本项目采用）** | ≈24（95 bit） | 时间戳 14 + shard 0 + 随机 5 字节 | **40 bit** |
| 18 位（上游默认） | 28（112 bit） | 时间戳 14 + shard 2 + 随机 6 字节 | 48 bit |

时间刻度容量：55 bit × 10µs ≈ **1780 年**，够用。

## 3. 导入模版

> **导出文件名与导入模版同引擎，但多一段强制尾号**（2026-09-28，规格 `specs/export-issue-ordinal.md`）：
> 模版主名之后追加 issue 尾号 —— 定稿 `I00`–`I99`（每照片唯一、0–99 循环、满百拒绝保存定稿）、
> 原片 `ISO`、RAW 标记 issue `IRA`、未匹配 latest `ILA`；无其它分隔符（`I` 即分隔），
> 例 `PA00034I03`。同文件多 issue 因此互不撞名（此前同主名互视为冲突的大 bug 的解法）。

### 3.1 默认模版与示例

```text
默认：:CYEAR-:CMONTH-:CDAY/MY:FILENAME
```

例：创建时间为 2026-08-15、名为 `P0001.png` 的文件被导入后：

```text
photos/2026-08-15/MYP0001.png
```

- 模版里的 `/` 是**目录分隔符**，会生成子目录。
- 落地目录的起点是 `<库根>/photos/`；模版描述的是 `photos/` **之内**的相对路径。
- 模版是**库级设置**，存在该库的 `catalog.db` 里（可随库迁移），
  同时在 `app.db` 缓存一份供离线显示。

### 3.2 变量表（`:` 前缀，替换即可）

| 变量 | 含义 | 宽度 | 例 |
| --- | --- | --- | --- |
| `:CYEAR` | 创建年份 | 4 位 | `2026` |
| `:CMONTH` | 创建月份 | 2 位 | `08` |
| `:CDAY` | 创建日 | **2 位** | `15` |
| `:CWEEK` | 一年中的第几周 | **2 位** | `33` |
| `:FILENAME` | 文件主名（**不含扩展名**，扩展名原样透传） | — | `P0001` |
| `:BRAND` | 相机品牌 | — | `NIKON` |
| `:MODEL` | 相机型号 | — | `Z7II` |
| `:SEQ000` | 序号，3 位 | 3 | `001` |
| `:SEQ0000` | 序号，4 位 | 4 | `0001` |
| `:SEQ00000` | 序号，5 位 | 5 | `00001` |

**解析规则（重要，用户特别说明）**：变量名按**已知名字的前缀匹配**，其后是字面量。

```text
模版片段 `:FILENAMEGO`  →  FILENAME + 字面量 `GO`
即：P0001 → P0001GO（GO 加在文件主名末尾，而不是当成变量名的一部分）
```

因此解析器要按「已知变量名集合」做最长前缀匹配，未匹配的 `:` 视为字面量（并给出校验警告）。

### 3.3 序号（`:SEQnnn`）

- 序号在**最终落地目录**（例 `photos/2026-08-15/`）范围内计数，计数存在**该库的 `catalog.db`** 里。
- **不同宽度各自独立计数**：同一目录下 `SEQ000` 与 `SEQ0000` 互不干扰（它们的键不同）。
- **从 1 开始**；**写满后回绕到开头**（用户明确：不纠结）。
- 回绕与并发导致的重名，由 §3.4 的重名规则兜底。
- 序号键要包含模版里**序号之前**的部分吗？—— 不需要：用户要的就是「目录级计数」。

### 3.4 重名处理 —— **用户 2026-09-16 定稿：就是加数字后缀**

```text
模版算出的目标文件名已存在 → 在扩展名之前追加 `_01`
                              仍在 → 依次 `_02`、`_03`… 直到找到空位
                              两位用满（`_99` 也被占）→ 继续涨位数：`_100`、`_101`…
```

- **主序号不因此往后挪**：`:SEQ000` 的值由模版算出来，撞名**不改**它的推进逻辑；
  解决冲突的一律是后缀 —— 所以同一目录里可能出现 `MY0001.jpg` 与 `MY0001_01.jpg` 并存。
- 追加位置在**扩展名之前**：`MYP0001_01.png`（不是 `MYP0001.png_01`）。
- 为什么从两位起步：两位以内不影响按字符排序，且这个量级足够用。
- 三种重名来源：① 模版改动后新旧命名撞车；② 序号回绕；③ 同一张照片的位图与 RAW 同名
  —— ③ 走 §4.1 的分流（一个资产两个文件，各自扩展名不同），**不算冲突**。

### 3.5 模版校验（给用户即时反馈）

- 变量名不认识 → 警告（并列出可用变量）。
- 结果路径含非法字符（Windows：`<>:"|?*` 等）→ 报错并指出位置。
- 模版末尾若为 `/` 或为空 → 报错。
- 有没有序号一样的两个模版变量？允许（同宽度会连号），但会提示。

## 4. 导入流程

### 4.1 位图与 RAW 的分流（用户指定）

对**同一张照片**（同名不同扩展名，如 `P0001.png` + `P0001.ORF`）：

| 情况 | 处理 |
| --- | --- |
| 只有位图 | 位图进目标目录 |
| 只有 RAW | RAW **正常进目标目录**（不是进 `_RAW/`） |
| 两者都有 | 位图进目标目录；**RAW 进同级的 `_RAW/`**，且**也按同一模版改名** |

例（模版 `:CYEAR-:CMONTH-:CDAY/MY:FILENAME`）：

```text
source:  P0001.png + P0001.ORF（拍摄于 2026-08-15）
target:  photos/2026-08-15/MYP0001.png
         photos/2026-08-15/_RAW/MYP0001.ORF      ← 同名，只差目录
```

- catalog.db 里**可以**关联这两者（便于「编辑位图时自动找同名 RAW」），但**不强制**：
  用户可以自由移动/改名文件，`_RAW/<同名>` 只是一种**约定**。
- 编辑位图时默认尝试载入 `_RAW/` 下的同名 RAW 来解码编辑，**用户可切换为「仅编辑位图」**。

### 4.2 目录透传（同步子目录）—— **用户 2026-09-16 定稿**

**算法**（三步，顺序不能换）：

1. **摸一遍 source 的子树**（任意层级），判断每个子目录里**有没有可导入的图片**
   （M1 只认图片：RAW + 位图，判定见 `media::kind`）。
   **只有「含可导入图片」的子目录才透传** —— 空目录、只含文档/视频/其它文件的目录
   **不建、不复制**。
2. **模版求值出 target 根**：按每张照片自己的变量（`:CYEAR`/`:CMONTH`/`:CDAY`…）算出它落哪一级目录，
   这个目录就是**该文件的 target 根**。**模版的目录部分只在这里求值一次**。
3. **把 source 的相对路径层级原样搬到 target 根之下**：文件相对于 **source 根**的目录层级
   **有几层就搬几层，一层不丢**。直接躺在 source 根里的文件就落在 target 根下（不额外套目录）。

**示意**（source = `D:\Trip`，模版 `:CYEAR-:CMONTH-:CDAY/MY:FILENAME`）：

| source 里的文件 | 落到 target | 说明 |
| --- | --- | --- |
| `D:\Trip\a.jpg` | `photos/2026-08-15/MY0001.jpg` | 根下的文件不套目录 |
| `D:\Trip\Japan\Kyoto\b.jpg` | `photos/2026-08-15/Japan/Kyoto/MY0001.jpg` | 两层全保留 |
| `D:\Trip\Japan\Tokyo\c.jpg` | `photos/2026-08-15/Japan/Tokyo/MY0001.jpg` | 同一天 → 同一个 target 根 → 共用 `Japan/` 这一级 |
| 拍摄于 08-16 的 `Japan\Kyoto\d.jpg` | `photos/2026-08-16/Japan/Kyoto/MY0001.jpg` | **模版按每张照片求值**：不同日期 → 不同 target 根，层级各自独立 |
| `D:\Trip\Notes\e.txt` | **不导入**，`Notes/` 也不建 | 该目录里没有可导入的图片 |
| `D:\Trip\空目录\` | **不建** | 同上 |

**四条纪律**：

- **模版不逐层套用**：`Japan/Kyoto` 不会被再套一遍日期模版
  （绝不会出现 `photos/2026-08-15/Japan/2026-08-15/Kyoto/`）。
- **目录只在真的有文件落地时才创建**（不留空目录）。
- **序号在每个最终目标目录内独立计数**（§3.3）：上表 `Japan/Kyoto` 与 `Japan/Tokyo` 各有各的 `MY0001`。
- **关闭「包含子目录」时不透传**（`design/main.md` §3）：只导入 source 根那一层的图片，子目录整体跳过。

### 4.3 避免重复导入

- 默认勾选「避免重复导入」（`design/main.md` §3.3）。
- 判据：**文件身份**（`(volume_serial, file_id128)`，见 `AGENTS.md` §7.3）+ 内容大小/mtime 兜底；
  导入后身份记录在 `catalog.db` 的 `asset_files` 上。
- 对已在库中的文件，**默认跳过**；若要强制再导入，界面提供显式开关（M1 可先不做）。

### 4.4 导入的进度与反馈（**用户 2026-09-15 明确要求**）

导入是**真正建立数据**的一步（写 `assets` / `asset_files` / 序号计数、把文件复制进库、排缩略图任务），
因此必须有**独立的导入进度弹窗**（不是角落里的一行字）：

| 要素 | 要求 |
| --- | --- |
| 形态 | **弹窗**（模态），导入进行中不可被误关；关掉＝取消（要二次确认） |
| 总体进度 | **当前阶段 / 总阶段**（扫描 → 复制 → 登记 → 缩略图），加总进度条与百分比 |
| 计数 | 已导入 / 跳过 / 失败，**实时更新** |
| 当前项 | 正在处理的文件（文件名 + 库内目标路径），让人知道「它没卡住」 |
| 错误清单 | 失败项可展开查看原因（权限、磁盘满、格式不支持…），**可导出** |
| 控制 | **暂停 / 继续 / 取消**（取消后已导入的部分**保留**，界面上要说清这一点） |
| 结束态 | 完成摘要（成功/跳过/失败）+「在库中查看这些照片」的跳转；失败项给出重试入口 |

- 单个文件失败（权限、磁盘满、格式不支持）→ 记入错误清单，**继续导入其余文件**；
- 整个导入可暂停/继续/取消；取消后已导入的部分**保留在库中**（不做事后回滚，
  因为文件已经落盘；M1-6 需在界面上说清这一点）；
- 缩略图生成是**导入之后的后台任务**，进度弹窗里只体现为最后一个阶段（不阻塞导入完成）。

> **设计稿状态**：⚠️ 画布上**还没有**这个弹窗 —— 见 `design/main.md` §7 待决项（M1-6 开工前补）。

### 4.5 导入失败与中断

- 单个文件失败（权限、磁盘满、格式不支持）→ 记入错误清单，**继续导入其余文件**；
- 整个导入可暂停/继续/取消；取消后已导入的部分**保留在库中**（不做事后回滚，
  因为文件已经落盘；M1-6 需在界面上说清这一点）。

## 数量体系：`相片数量` 与 `图片数量`（人类 2026-09-19 定，**关键设计**）

系统里有两个**不能混用**的计数：

| 概念 | 含义 | 字段 |
| --- | --- | --- |
| **相片数量** | **不含** `_RAW/` 里文件的数量 —— 也就是「用户看到的照片张数」 | `*.photos_count` |
| **图片数量** | **含** `_RAW/` 的数量 —— 也就是磁盘上真实文件数 | `*.images_count` |

对外的库卡片显示的是**相片数量**（库卡片弹窗里两个都显示）。

### 存法与口径

- 两张表各有这两个字段：**库表 `repositories`** 与 **库内目录表 `directories`**
  （`repositories.photos_count` / `repositories.images_count`，
   `directories.photos_count` / `directories.images_count`）。
- **目录行只统计自己**：本目录内的文件 + 本目录下的 `_RAW/`，
  **不包含**任何子目录 —— 子目录各自有自己的行。
- 导入时**逐目录统计**：勾了「包含子目录」就把每个透传的子目录**各记一行** `directories`。
- 导入结束后把该库**所有** `directories` 的这两个计数**求和**写进 `repositories`。

### 为什么要这样拆（增量同步，而不是每次全库重算）

进任何一个目录时本来就要读目录内容（顺带读一下 `_RAW/` 如果有）——
**顺手数出这两个值**，与 `directories` 里存的值比对：

- 多了 3 张 → 给该目录 `+3`；
- 少了 2 张 → `-2`；

然后把这个 **delta 原样加到 `repositories` 上**。这样计数**永远不用全库重扫**，
也不会因为「某次扫描失败」而算错 —— 是增量、可自愈、成本几乎为零。

> 这条同样适用于「用户在程序外面往目录里丢照片」：下次进目录自然就同步了
> （与 `AGENTS.md` 的「本地应用实时性优先」同一条思路）。

### RAW 的三种形态（同一次口述，2026-09-19）

**库内目录不是只能放位图** —— 规则是「**同名 RAW 与位图配对时**，RAW 进 `_RAW/`」，
不是「所有 RAW 都进 `_RAW/`」。所以：

| 形态 | 磁盘 | tiles 标签 |
| --- | --- | --- |
| 位图 | 目录内一张 JPG | 无（或扩展名） |
| RAW（**只有** RAW，没有对应位图） | RAW **直接在目录里**，不进 `_RAW` | `RAW` |
| 位图 + RAW | 位图在目录、RAW 在 `_RAW/` | **`+RAW`** |

- 第三种里位图是 **SOOC**（相机直出）的那份，**实际编辑落在 RAW 上** —— 所以标签必须与
  纯 RAW 区分开（`+RAW` vs `RAW`）。
- 用户**有权把 `_RAW/` 里的文件拷到目录下**：那样这一对就**解绑**，变成
  「位图」+「RAW」两张互不关联的图（见 `memory/FUTURE.md` 的 issue 概念）。
