## 0. 这个文件怎么用（维护规则）

1. **它是「结论账本」，不是「第二份规格」。**
   本文件只记三样：**判断**、**取舍**、**去向**（落到哪个文件的哪一节）。
   一经采纳，**正式改动写进拥有它的那份文件** ——
   `AGENTS.md` / `memory/DESIGN.md` / `memory/FUNCTION-BROWSE.md` / `memory/FUNCTION-REPOSITORY.md` / `memory/FUNCTION-IMAGING.md` / `memory/PLAN.md` / `memory/FUTURE.md`；
   本文件那一项只更新到「**已落地 + 落点**」。
   ⚠️ **禁止把规格正文抄第二份**（`AGENTS.md` §2.12：同一个东西两种表达本身就是 bug）。
2. **不用 `- [ ]` 勾选框。** 勾选项的语义属于 `specs/*.md` 的验收清单（`AGENTS.md` §5.4）。
   本文件的状态**一律写在表格的「状态」列**里
   （`待决` / `已采纳` / `已落地` / `不做` / `搁置`）。
3. **每轮 review 追加一节，不覆盖历史。** 文件顶部的 §3「当前待办总览」是**全文件唯一的汇总视图**，
   每轮重排一次；下面各轮的小节是**证据与理由**，可以长。
4. **不改写旧结论。** 结论变了就写新一节并注明「**取代 `R⟨轮次⟩-⟨序号⟩`**」。历史留着 ——
   「当时为什么这么定」本身是资产，删掉它下次会重新吵一遍。
5. **编号规则 `R<轮次>-<序号>`**（如 `R1-03`），一经分配**不再复用**；作废的标 `不做` 留行。
6. **不是待办清单的替代品。** 本轮要做的事仍按 `AGENTS.md` §5.5 走 `todo`；
   本文件管的是「**方向对不对**」，不是「今天做哪件」。

### 2.1 R1 总体判断（一句话）

**设计成熟度在整个开源相片软件里属于断层第一档；真正的问题不是"想得对不对"，而是三处取舍是否成立，
以及"创新"的自我定位需要校准。**

展开成两句：

- **设计思路**：把"现代 Web 产品"的纪律（设计令牌、组件化、命令注册表、i18n、空态/加载态/禁用态全覆盖）
  搬进一个"暗房工具"的骨架（三行外壳、暗色优先、否定式工具条）。这个组合**在 Windows 桌面端目前没人做好过**。
- **优势的真实来源**：**设计纪律 + 执行自洽**，不是**概念独创**。
  开源相片软件死的从来不是缺创意，是缺纪律 —— 所以这仍然是一副好牌，但对外介绍要用准确的说法。

### 2.2 行业位置（R1 的判定）

| 对手 | 它强在哪 | 判定 |
| --- | --- | --- |
| **darktable** https://www.darktable.org/ | RAW 显影质量与色彩管理 | UI/交互/DAM **高一到两个档次**；显影质量暂时输 |
| **digiKam** https://www.digikam.org/ | 开源里最强的 DAM（标签/搜索/人脸） | 功能面还追不上（集合/层级标签/人脸均未排期）；观感上是"Qt 桌面软件" vs "2025 年的产品" |
| **RawTherapee** https://www.rawtherapee.com/ | 无 catalog，纯转换器，质量高 | 不是同类；**已被定位为外部编辑器** —— 聪明的互补 |
| **RapidRAW** https://github.com/CyberTimon/RapidRAW | 同技术栈（Rust+Tauri+wgpu）、现代观感、AGPL | **最接近的对手**；关键差别：它是 sidecar 流派、**没有 catalog 数据库** |
| **Capture One** https://www.captureone.com/ | 色彩 / 变体 / 联机拍摄 / **Sessions** | 专业度差距最大；但**库模型基本是「现代化改编版的 C1 Sessions」**，方向本身被验证过 |
| **Lightroom Classic** | 生态、云端、镜头库、AI 蒙版 | 能力差得远；但 **UI 确实停在 2015 年** —— 观感与命令体系这两样已经能平推 |

**结论**：「**Windows 优先 + 有 catalog + 现代观感 + 开源**」这个交集**目前是空的**，
定位成立且有空位。三家里没有一家的组合能占住它：RapidRAW 无 catalog，digiKam 不现代，darktable 两边都缺。

## 3. R1 建议（按"要不要现在动"分组）

### 3.1 需校准的自我认知（改措辞，不改功能）

#### R1-10　`memory/FUTURE.md`「issue 是创新点」→ 收回一点

`memory/FUTURE.md`「issue 与 SOOC」写着：「这是本应用的一个**创新点**：每张图可以有自然的多定稿版本」。

**这个说法站不住**：issue 在功能上就是行业里已有的东西，只是换了名字。

| 概念 | 归属 | 说明 |
| --- | --- | --- |
| **Variants** | Capture One | 官方文档明确「**一切皆 variant**，原片本身就是一个 variant」—— 与「SOOC 是写死的特殊 issue」**几乎逐字对应** |
| **Virtual Copies** | Lightroom Classic | 一份文件多条编辑路线，可各自导出 |
| **Versions** | ON1 Photo RAW | 保留不同 Develop/Effects/裁剪/元数据 |
| **Snapshots** | LR / C1 | 参数快照，用途重叠 |

参考：Capture One 官方对 variants 的定义
https://support.captureone.com/hc/en-us/articles/360002478437-The-concept-of-variants-in-Capture-One
（Sessions 对比 Catalog https://support.captureone.com/hc/en-us/articles/30041173920029-Sessions-vs-Catalogs-in-Capture-One-how-they-work-and-where-to-store-them
｜ON1 Versions https://www.on1.com/ ）

**真正的差异化不在"发明了 issue"，而在"把 issue 做成第一公民"**，这四条合起来确实比 LR 彻底：

1. **导出工作区以 issue 为选择单元**（`design/export.md` §4.2：可选中单元是 issue 小片，点照片本体 = 整组全选）；
2. **浏览侧右栏「展示定稿」切换**，切完立刻刷新网格缩略图与看图（`design/browse.md`「M3-W6c」）；
3. **SOOC / RAW 是固定源**，且每个命名定稿带「基于 SOOC / 基于 RAW 编辑」标签；
4. **对比工具的左源可以是任意定稿**。

> 对着 C1 只能算**追平并补齐**（C1 甚至能一次导出同一张的多个 variant）。
> **建议措辞**：从「创新点」改为「**把行业里已有、但被做成二等公民的机制提升为第一公民**」——
> 既准确，对外也更容易站住。

**去向**：`memory/FUTURE.md`「issue 与 SOOC」小节；同时把上面四条差异点写进去（那才是可辩护的部分）。

#### R1-11　另外两处同类校准

- **`Tab` 四态循环 / 无级分栏拖拽 / 对比虚拟画布**：C1 与 LR 都有成熟形态。这里比的是**执行质量**，
  不是概念新颖度。对外不必强调"独创"，强调"更顺"。
- **时间片（相邻间隔 > 1h 断为新片）**：这是 Apple Photos「Moments」的思路搬进专业工具，
  **第一次被认真做**。但它是**受众选择**：婚礼/活动/旅拍是加分项，棚拍/静物是噪声。
  建议在 `memory/FUNCTION-BROWSE.md` §3.1 的开关说明里写清它服务谁，别默认所有人都会用。

#### R1-12　把「库身份用内容定」写成对外的差异点

`memory/FUNCTION-REPOSITORY.md` §2 的库模型（**身份记在 `catalog.db` 里，路径只是挂载点**，
于是「同路径不同库」「同库多路径」「拔盘离线后自动重挂」三件事同时成立）——
**这是我认为整个设计里最该被写进 README 与官网的一条**，而现在它只活在内部规格里。

为什么它值钱：Lightroom 的 catalog 与照片是"指针 + 目标"关系，catalog 丢失或照片搬家就是灾难；
这里有明确的**行业痛点**与明确的**机制性差异**（用内容定身份，和 git 的思路一致）。

**去向**：`README.md` 的产品介绍；官网 `website/` 的功能段（等其内容规划到位时）。

### 3.2 产品级缺口（P0/P1）

#### R1-01（P0）色彩管理必须从「后期」提到**编辑模块的门槛**

- **现状**：`AGENTS.md` §6.1「第一阶段不做色彩管理」，只保证 SDR 下不变形。
- **问题**：浏览阶段可以扛，**编辑阶段扛不住**。RAW 解码 → 场景参考管线（`memory/FUTURE.md` D1）→ 显示，
  这条链上缺 ICC 管理时，"用户看到的颜色"不保证等于 sRGB 定义的颜色，更不用说 Adobe RGB / P3。
  C1 / LR / darktable **全都有**完整 ICC 与软打样 —— 这不是可选项，是**相片编辑软件的准入门槛**。
- **缓解因素（要一并记下）**：lcms2 已在 M0 预留；「不变形」这个最低目标写得很清楚；
  管线是 scene-referred 的，接色彩管理比在显示参考管线上补要容易。
- **建议**：把 ICC 从"后期里程碑"提到 **`memory/FINISHED.md` §6（M3） 完成定义的硬门槛**；至少在编辑视口这条路上
  「输入 → 工作空间 → 显示器」三段全部到位，并给出可验证的判据（不是"看起来对"）。

#### R1-02（P0）集合 / 智能集合的排期决定

- **现状**：`memory/FUTURE.md` I 节整体后移、**未排期**。手动集合 + 保存查询的智能集合都在里面。
- **问题**：一个没有"相册 / 集合"的相片管理软件，用户没法组织照片，只能靠目录 + 标签。
  这会直接改变人们对"这是个 DAM 还是看图工具"的判断。
- **缓解因素**：**引擎底座已经在** —— 平面标签、FTS5 trigram、`query::facets`、时间线全在 M1/M2 落地，
  缺的**只是 UI 与持久化实体**。所以这是一件"成本比看起来低"的事。
- **建议**：在 M4 收口与 M5 发版之间做一次明确的取舍 —— 要么拉回一小波（静态集合 + 保存查询），
  要么在 `memory/PLAN.md` 写明"首个公开版本不含集合，理由是 X"，**不要保持沉默的未排期状态**。

#### R1-03（P1）XMP sidecar 的实际写出

- **现状**：`specs/issue-xmp-contract.md` 契约已定案，**实际写入属后续波次**（`M3-W7` 记录确认）。
- **问题**：这是"**数据不是黑箱**"的对外承诺。缺它，从 LR / darktable 迁移过来的用户
  无法验证"我的评级与调整真的存下来了"，也拿不到逃生舱。
- **建议**：优先做**只写不读**（评标 + issue 参数导出为 sidecar），**读回与冲突解决**留到
  `memory/FUTURE.md` I 节的互操作实现；「DB 为真相源、XMP 为通道」的规则已经在 `AGENTS.md` §6.4 写好了。

### 3.3 交互取舍（P1/P2，需要人类拍板）

#### R1-04（P1）`Shift` 区间的「翻转」语义

- **现状**（`memory/FUNCTION-BROWSE.md` §5.2）：点 A → `Shift` 点 C → **B、C 翻转**（不含 A），C 成为新锚点。
- **理由原文**：「逻辑简单、无需保存复杂状态、操作又灵活」。
- **问题**：代价被转移到了用户身上。Windows 资源管理器、macOS Finder、LR、Bridge、C1、
  浏览器、Excel —— **所有地方** `Shift+点击` 都是"从锚点扩展选中到此处"。这里是**唯一一个不同的**。
  从审片（culling）角度动机成立（批量改判已选/未选），但偏离需要**极强的视觉反馈**，
  否则会变成"我明明要 B..C，结果 B 被取消了"。
- **建议（二选一，请人类定）**：
  * **A（保守）**：`Shift` = 业界语义的**扩展**，另给 `Ctrl+Shift`（或 `Alt+Shift`）= **区间翻转**；
  * **B（保留）**：维持翻转，但在状态栏/toast 里**明确报出**"翻转 2 张"，并在 `memory/DESIGN.md` §14
    补一条该操作的视觉反馈规格（否则这一条会以 bug 报告的形式回来）。

#### R1-05（P1）旗标不持久化与用户预期冲突

- **现状**（`memory/FUNCTION-BROWSE.md` §3.2 / §10 第 6 条）：旗标**只在内存**，关软件即清空，
  「一定程度替代未来的 bucket」。
- **问题**：旗标是摄影工作流里最常被理解为"已标记"的东西。**LR 的 pick/reject 是持久元数据，
  而且是筛选主力**。用户关掉再打开发现全没了，第一反应是 bug 不是 feature。
- **同类先例都在持久化**：LR 的 Quick Collection、Bridge 的 Collections、本项目 `memory/FUTURE.md` H6 的
  picture bucket —— 那些**临时工作集也都是落盘的**。
- **建议（三选一）**：① 恢复上次会话的旗标（落 `app.db.settings`，仍然"不是元数据"）；
  ② 退出时询问是否保留；③ 维持现状但在 UI 上把临时性讲到无法误解
  （例如图标带"会话"角标 + 首次使用时一条 toast 说明）。

#### R1-06（P2）外壳垂直占用：紧凑 120px / 宽松 150px

- **实测值**（`src/styles/tokens.css`）：`--bar-title-h` 36/44 + `--bar-flow-h` 48/62 + `--bar-tool-h` 36/44
  = **120 / 150px**；加上中列自己的 statusbar（32）就是 **152 / 182px**。
- **问题**：2560×1440 上无所谓；在 1920×1200 / 16:10 笔记本上很贵
  （LR Classic 的模块选择条只有一条细带）。
- **建议**：评估"**哪些工作流可以自动收起某一层**"——例如导入时 `flowbar` 的 `ExifStrip`
  几乎无用；`toolsbar` 已经有"无内容整行隐藏"的规则，把它真正用起来。
  ⚠️ 这是对 §2.1 表面分层地图的改动，**先改设计稿再改代码**（`AGENTS.md` §5.1）。

### 3.4 工程与文档纪律

#### R1-07（P1）AVIF 缩略图的生成节点口径统一

- **现状**：`memory/FUNCTION-IMAGING.md` §3.1-1 说「**导入时**就要生成缩略图」，§8 现状里又说
  「按需：可见 tile 请求时渲染并写缓存」—— **两套口径并存**。
- **判断**：AVIF 的体积优势是真的（第三方基准：约 **−43%**，101kB vs JPEG 177kB），
  解码代价约 **+32%**（13.0ms vs 9.8ms）——见 https://gist.github.com/mvsde/3e42f33723b0cfff296f01bedc0dea94 。
  浏览侧这点解码差异吃得住；**真正的成本在编码**，而编码恰好在**导入路径**上。
- **建议**：明确成一条 —— **导入只登记 + 投递后台缩略图队列**，让"导入 5000 张"的耗时不被
  ravif 编码主导（编码代价已实测，见 `memory/FUTURE.md` C8）。同时在 §6 的状态表里把这一点写死。

#### R1-09（P1）规格漂移：条带高度已经三处不一致（**有证据**）

| 位置 | 值（紧凑 / 宽松） | 状态 |
| --- | --- | --- |
| `memory/DESIGN.md` **§8.2** | `--bar-title-h` 36/44、`--bar-flow-h` 48/62、`--bar-tool-h` 36/44 | ✅ 2026-09-16 按人验收反馈收紧后的**新值** |
| `memory/DESIGN.md` **§9.2**（密度令牌表） | 40/48、52/68、40/48 | ❌ **旧值，未同步** |
| `src/styles/tokens.css`（实现，§8.4 的真相源） | 36/44、48/62、36/44 | ✅ 与 §8.2 一致 |
| `design/export.md` §2（**2026-09-26 最新出稿**） | 「`titlebar` 40 / `flowbar` 52 / `toolsbar` 40（紧凑档）」 | ❌ **用了旧值** |

**即：同一个文件里 §8.2 与 §9.2 互相矛盾，而最新的设计说明书沿用了错的那一份。**
这不是吹毛求疵 —— 它正好印证这套文档体系最大的成本：`memory/DESIGN.md` 1335 行 + 三份大规格
+ 四本 `.pen` 说明书（共约 2500 行），单作者维护必然局部过期。

- **建议**：§9.2 那一列**要么删掉改成"见 `tokens.css`"**，要么加一条显式约束：
  「本表由 §8.2 派生，**改 §8.2 必须同步此处**」；顺手修 `design/export.md` §2。
- **可推广的做法**：把这类"派生表"统一标注派生来源（本仓已有 `design/browse.md` §5.3
  「与实现冲突时的判据」与 `memory/DESIGN.md` §8.4「以实现为准」两个好机制，只是没覆盖到 §9.2）。

#### R1-08（P0）自研去马赛克 / 降噪的质量基线

- **现状**：`AGENTS.md` §8 问题清单**第 1 条**就是「去马赛克与画质算法自研成本高」，
  候选取舍见 `memory/FUTURE.md` D2/D3。
- **判断**：这是**唯一一件"做不好就没有口碑"的事**，而且没有捷径。
  当前对冲是 M4-W4「送外部编辑器」——**这个对冲是对的**，但它只在"用户自己认得出要送出去"时才生效；
  内置出图如果明显输给 darktable，用户第一次打开就形成判断了。
- **建议**：给 M3/M4 的出图定一条**可验证的质量基线**（例如固定几张样片 × 与
  darktable / RawTherapee / 相机直出的对照），并把「**达不到就走外部编辑器路线、内置只保证够用**」
  写成明确的判据 —— 让"不做极致"是一个**决定**，而不是一个**结果**。

## 11. R6：XMP 导入导出的范围口径修正（2026-09-30）

触发：崔总要求查实「XMP 规范性 + 各家软件 sidecar 行为」，随后对「积极做导入」的投入产出提出判断，并给出范围口径。

### 11.1 判断与取舍（人类拍板，R6-01）

**结论：导出做，导入不急。** 先建立自有格式表达与 sidecar（写出），目的是**表态**——开放态度、用户的数据资产归用户、开源精神；
别的软件能否读我们的 sidecar 属**边界之外**，不作为投入依据。导入兼容降级为远期，待真实需求拉回。

崔总的理由（原话见 `docs/user-requirements.md` 2026-09-30 节）：

- **「无感导入」只存在于想象**：要求用户旧软件（a）已开启写 sidecar、（b）用标准命名、（c）导入方式配合，条件过苛；Lightroom 默认根本不写（已查实）。
- **有意识的用户不会来**：懂 XMP 管理的用户不缺钱买 LR / Capture One，不需要从小软件切过来；**不指望从大软件抢用户**。
- **基本盘另有其人**：「有拍照、舍不得买正版、一直凑和」的用户（崔总本人即此类），未来只会更多。
- **别家的导入支持点到为止、基本烂尾**：吃力不讨好，有但没维护。

Agent 查实材料（2026-09-30 网络核实；全表与来源见 `todos/2026-09-30-xmp-export-first.md` §4）支持上述判断：

- Lightroom Classic 官方：RAW→sidecar、JPEG/TIFF/PSD/PNG/DNG→写进文件本体（且无法强制 JPEG 走 sidecar）；**默认全部留 catalog，什么都不写**。
- Adobe XMP Spec Part 3 对 sidecar 只有一句 "should" 级建议（同目录、同名 + `.xmp`）；实际生态分两派命名
  （`<name>.xmp` / `<name>.<ext>.xmp`），darktable 读 Adobe 命名但不写它、digiKam 有兼容开关、
  FastRawViewer 有命名方案设置——三家都要做跨方言适配，证明没有统一实践。
- darktable 是最认真的进口者，其文档仍自述「永远不会得到相同结果」，且部分 LR 映射模块已标 deprecated——
  「点到为止 + 欠维护」的实证；欠维护是**结构性**的（对方版本演化持续产生适配账）。
- 导入兼容的成本结构是「命名 × 软件 × 版本」的组合，且对用户是一次性事件（迁移完即用尽），不支持排在导出前面。
