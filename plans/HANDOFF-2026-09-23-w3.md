### 3.2 第一个必须回答的问题：**参数在哪儿生效**（本波最大的技术分叉）

| 方案 | 怎么做 | 代价 / 风险 |
| --- | --- | --- |
| **① CPU：全尺寸** | 每次参数变化在对源像素跑一遍管线（2.5MP 预览档或 24MP 全尺寸），再 `set_image` | 24MP 单线程必卡（几十到几百 ms）；预览档 2.5MP 单线程约 10–30ms **可能够用**（dev 档 opt-level 2，量得准） |
| **② CPU：预览档 + 松手补全尺寸** | 拖动中只重算预览档（1920 长边），松手后再算全尺寸档 | 实现最简单，W3 能立刻出成果；缺点：1:1 档下拖动看到的是放大后的预览档（糊一点），松手才变清 |
| **③ GPU：着色器里做** | 参数进 uniform，`spike.wgsl` 里算 | 最快（W4 的 LUT/清晰度都要它）；**但同一份数学得在 CPU 再来一遍**（缩略图/看图的 JPEG 路径走 CPU）——两份实现是「同一件事两处写」的大忌 |

**建议**：W3 先做 ②（结构上把「参数 → 线性像素缓冲 → 纹理」这条链路跑通），
把 ③ 作为 W4 的正式形态；无论选哪个，**先定「数学的唯一定义处」**：

* 用一组**测试向量**（输入像素 + 参数 → 期望输出，外部给定）把公式钉在 Rust 侧；
* 将来上 GPU 时，同一组向量同时喂 CPU 与 GPU 两条路做**交叉验证**（GPU 那条可以把离屏回读
  加进 `examples/editor-offscreen.rs`，那里已经有现成的像素证据框架）。

### 3.3 第二个必须回答的问题：**RAW 的线性数据从哪来**（scene-referred 的前提）

现状（W2）：RAW 走的是**内嵌预览 JPEG** —— 它已经被相机做过色调映射，是 sRGB 8bit。
拿它做曝光/对比，严格说仍然是「在 8bit 显示空间上编辑」，与 `PLAN.md`「不是 8bit 显示空间」矛盾。
三条路：

| 路 | 做法 | 代价 |
| --- | --- | --- |
| (a) 内嵌预览 + **线性化** | sRGB → linear → 管线 → 显示变换 → 再编码 | 最省，W3 可落地；诚实标注为「准线性」（色阶已被相机压过，暗部拉伸会出阶梯） |
| (b) 完整解码 + **自研/移植去马赛克** | rawler 给 CFA → RCD/AMaZE…（`FUTURE.md` D2 已核许可） | 大工程；建议作为**独立一小波**或 W4 的并线任务，不要塞进 W3 |
| (c) 两条并存 | 管线输入统一是 **linear RGB 缓冲**（来源可以是 a 或 b） | 结构上最对：W3 按 (c) 搭壳、用 (a) 填内容；换成 (b) 时不动管线 |

**建议**：W3 按 (c) 的结构 + (a) 的实现；把「去马赛克取舍」作为 W3 的
**定案并记录**交付项（`PLAN.md` 那一句要求的），落到实施记录 + `FUTURE.md` D2，
真上马放到 W4 或专门一波。

  「编辑中」**不是** issue，是「当前工作栈」（设计稿的定稿页签就是这么画的：SOOC + 编辑中 + 定稿按钮）；

  `media::kind::is_sidecar` 里**被认出来**，没有读写实现（也没引 `quick-xml`）——

* 撤销：先看 `store/marking.rs` 的 `ChangeSet`/`UndoStack` 能不能直接用（见 §3.1 那行），

  这样「重置这一项 / 重置全部」是同一套判断；
* 迁移文件里**只加表**、不动老表（除了必要的列），并给 `catalog_0005` 写一条
  「从 v4 升上来数据不丢」的测试（框架里已有 `fresh_catalog_db_applies_all_migrations` 这类范式）。

### 3.5 建议的施工顺序（每步都能单独冒烟）

1. **数据层**：`catalog_0005_develop.sql` + `store/develop.rs`（读/写编辑栈 + issue）+ 单测
   —— 纯 DB、不碰 GPU，最容易被后面的工作依赖；
2. **管线数学**：Rust 参数模型（与 `params.ts` 的镜像 + 断言）+ 纯函数管线
   （曝光 / 反差 / 高光 / 黑区 / 色温 / 饱和 / vibrance / 曲线），**测试向量外部给定**；
3. **接进渲染线程**：`editor_set_params` → 线程里应用（先按 §3.2 的方案 ②）→ `set_image`；
   量一次「预览档一遍管线」的真实耗时（dev 档 opt-level 2），把数字记进实施记录；
4. **前端接线**：拉杆 → 帧合并的意图（复用 `lib/editor-intent.ts` 那套：合并 + 尾样本）→
   松手落库（防抖），失败要有可见提示；
5. **缩略图 / 看图反映编辑**：`display::EditSpec` 从占位变成真参数 + `render_sig` / `PIPELINE_VERSION`
   同批抬版本；看图那条路复用 `display_image`；
6. **收口**：`editor-offscreen.rs` 加「带参数的用例」（期望值外部给定）+ 六条质量门 +
   真机清单（人能看见画面变化）+ 实施记录 + commit（**不 push**）。

### 3.6 五个最容易踩的

1. **抬 `PIPELINE_VERSION` 必须与改渲染行为同批** —— `render.rs` 里记着三次毒缓存事故
   （RAW 占位图、方向、方向优先级），每次都是「算法改了、版本没抬 → 用户看到旧结果而程序一切正常」；
2. **别在 8bit 显示空间做调性** —— 至少先走 sRGB→linear（§3.3），
   否则暗部一拉就出色带，而这类问题在真机上才看得见；
3. **拖动中每帧一条 IPC 是可以接受的，但要帧合并 + 尾样本** ——
   `lib/editor-intent.ts` 的 `createPanAccumulator` 就是模板（合并 + 停手那一次必发）；
4. **参数范围/默认值的单一真相在前端 `params.ts`** —— Rust 侧要么镜像 + 一条**跨语言一致性断言**
   （照 `dto-contract` 的做法），要么让载荷自带范围（更稳但更啰嗦）。**别两边各写一份还没有测试**；
5. **渲染线程的换纹理只有 `set_image` 一个入口**，并且它内部会按 `fit_mode` 重新适配 ——
   参数生效后如果画面「跳一下」，先看那里，不要在下游补偏移。
