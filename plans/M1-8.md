# M1-8 — M1 验收反馈修复（UI 细节）

> 来源：人类用 Windows exe 实测 M1 后的 8 条反馈（2026-09-16）。
> 计划先行，改动前先过 plannotator 评审。

## Context（为什么改）

M1 已交付，人类在真机上跑了一遍，回来 8 条问题。其中 **3 条是确定性代码 bug**（下面已定位到根因），
另外几条是观感与规格层面的，需要先定口径再动手：

| # | 反馈 | 性质 | 根因（已定位） |
| --- | --- | --- | --- |
| 1 | titlebar 中间按不住、窗体无法移动 | **bug** | 空白拖拽区那个 `<div class="h-full min-w-4 flex-1" />` **没有** `data-tauri-drag-region` —— Tauri 只认带属性的元素**自身**，子元素不带就不拖 |
| 2 | 左侧「最近」太高 | **bug** | 见 #3（同一个根因） |
| 3 | 「来源」上方把手拖不动 | **bug** | `SplitStack` 传的 `minSize: 80 / 100` 被 Zag 当**百分比**（`toCssPanelSize(number) → "N%"`）：等于「最近至少 80%、来源至少 100%」——布局数学直接畸变 |
| 4 | 「已选目录」看不见；且不该有把手 | 规格 + bug | 被 #3 挤没；且按新规格它应当**自动高度**（勾选才出现） |
| 5 | 新建库的库根示例路径显示成 `\\` | **bug** | JSX 属性 `placeholder="D:\\Photos\\Library"`：**JSX 字符串不做反斜杠转义**，用户看到的就是两个反斜杠 |
| 6 | 很多元素有 focus 黑边 | **bug（已达成因）** | 人类实测澄清：不是鼠标点出来的，而是**弹窗关闭时焦点从没离开过触发按钮**（点遮罩关窗不移动焦点）→ WebView2 按「程序性聚焦」画出 UA 黑圈。详见下方「C. 焦点」 |
| 7 | 「紧凑」要更紧、「宽松」要收一点 | 规格（已定：**温和收紧**） | 现值偏松，见 `tokens.css` density 段；新值见下方「D. 密度」 |
| 9 | **帮助菜单与工作流切换层级冲突**（菜单弹出时，工作流按钮的文字浮在菜单面板之上） | bug（根因待量） | 静态看**不该发生**：菜单是 portal + `z-50`（`Menu.tsx:74`），工作流 chip 只有 `z-10`（`FlowSwitcher.tsx:67`）。所以先**在真浏览器里量**再改，别按猜的改。详见「G. 浮层层级」 |
| 8 | **C 盘目录展示疑似「假的」** | 待人类确认窗口（见「待定」） | 代码侧是**真**的：`volumes_list`（Windows: `GetLogicalDrives`+`GetDriveTypeW`；Linux: `/proc/mounts`）+ `dir_list` → `std::fs::read_dir`，命令都已注册；`junk_kind` 不滤 `Windows`/`Users`。但人类看到的是**「mnt/home + 部分 C 盘目录」的合集** → 两种可能，见下方「F. 来源树」 |

## Approach（推荐做法）

### A. 左列：改成「两段可拖 + 底部自适应」

```text
┌ 最近 ──────────────┐   ← Splitter 段 1（minSize: "120px"）
├ ── 把手 ─────────── ┤
│ 来源（树）          │   ← Splitter 段 2（minSize: "160px"）
├────────────────────┤   ← **没有把手**
│ 已选目录            │   ← 自动高度：勾选 0 个 → 整块不存在；
└────────────────────┘      勾 n 个 → 高 ≈ n 条；超过上限（约 40% 列高 / 4 条）→ 内部滚动
```

- `minSize` 一律改成**带单位的字符串**（`"120px"`）—— Zag 支持 `px`，会按容器实际高度换算百分比；
  数字则一律是百分比（这是 #2/#3/#4 的根因，`SplitStack` 的文档注释要写清这条）。
- 「已选目录」搬到 `SplitStack` 之外（`flex-col` 里 `shrink-0` + `max-h-[40%]` + `overflow-auto`），
  由 `Show when={checkedDirs().length > 0}` 控制显隐 —— 与 `REPOSITORY.md`/`BROWSE.md` 的「已选目录 = 横条列表」语义一致。

### B. titlebar 拖拽

给空白拖拽区那个 div 加 `data-tauri-drag-region`（它已经是 `flex-1`，宽度天然吃满中间）。
顺带把窗口三键左侧那条静默区域也纳入（若存在）。**不给按钮加** —— 按钮会自动阻断拖动（既有注释已说明）。

### C. 焦点圈：关窗前先**主动清掉焦点**（人类给的方案，比原方案更准）

成因（人类实测澄清）：点遮罩关窗时**焦点自始至终没离开触发按钮**，浏览器把这种「程序性保留的焦点」
当成键盘焦点 → 画出 UA 黑圈。所以「按输入模态判断」解决不了它（那不是鼠标点击造成的）。

做法（**顺序要紧：先清焦点，再关闭** —— 反了会闪一下黑边）：

1. 全局：**任何时候按 `Esc` 先清焦点**再让事件继续 —— 一处捕获期监听，不做散点修补：
   `window.addEventListener("keydown", (e) => { if (e.key === "Escape") blurActive(); }, true)`
2. `Dialog` 封装层：点遮罩（`ArkDialog.Root` 的 `onInteractOutside`/背景点击）时**先 `blurActive()` 再关闭**。
3. `blurActive()`：`(document.activeElement as HTMLElement | null)?.blur()` —— 落到 `<body>`，不带焦点圈。
4. 顺带把**真键盘焦点**的圈做成主题色（`--focus-ring` / `--focus-ring-w` 这两个令牌早就定义了，
   但没有任何地方用它，现在落的都是 UA 黑圈）：`:focus-visible { outline: var(--focus-ring-w) solid var(--focus-ring); outline-offset: 1px; }`
   → 键盘 Tab 时的圈是「设计过的」而不是黑的；幽灵圈则由 1/2 两条从源头掐掉。

> 不做 `data-input` 输入模态那套（人类明确不想要满世界打补丁）；本方案只有一处全局监听 + 弹窗封装层两行。

### F. 来源树：把「奇怪的合集」解释清楚 + Linux 侧收敛

人类看到的是「`mnt`/`home` 这类 Linux 目录 + 部分 C 盘目录」混在一起，且 `Windows`/`Users` 不在。
代码侧已排除两类解释（命令都注册了、`junk_kind` 不滤这两个名字、`rows.ts` 没有合并逻辑），所以只剩两种可能：

| 可能 | 说明 | 该怎么处理 |
| --- | --- | --- |
| **A. 看的是 WSL 里的 `pnpm tauri dev` 窗口**（Linux 构建） | Linux 侧的卷来自 `/proc/mounts`：既有 `/`（它的子目录就是 `mnt`/`home`/`usr`…），又有 `/mnt/c`（它的子目录是真正的 C 盘内容）。两个卷各自展开，在同一个矮面板里就会看成「合集」 | **Linux 侧收敛卷列表**：只保留用户真会当来源的挂载点（`/home`、`/mnt/*`、`/media/*`、`/run/media/*`），把 `/` 与 `/boot`、`/usr`、`/etc`、`/var`、`/proc`、`/sys`、`/dev`、`/run`、`/snap`、`/tmp`、`/srv`、`/opt`、`/lib*`、`/bin`、`/sbin`、`/lost+found` 排除掉 |
| **B. 看的是 Windows exe，而那些名字真的在 C 盘根上** | `C:\home`、`C:\mnt` 有可能是历史遗留目录（WSL 相关工具会建）；`Windows`/`Users` 因为在字母序**靠后**、面板又矮，需要滚动才看得到 | 无需改代码；实施时顺带在验收说明里写清「树是可滚动的」 |

两种情况**互不冲突**，A 的改动是纯收益（Linux 侧本来就只是开发用），所以无论答案是哪个都照做 A。

### G. 浮层层级（z 轴）：先量后修 + 立一条不变量

现状（都是散落的字面量，没有体系）：

| 浮层 | 现在 | 位置 |
| --- | --- | --- |
| 菜单 `Positioner` | `z-50` | `components/ui/Menu.tsx` |
| 提示气泡 `Positioner` | `z-50` | `components/ui/Tooltip.tsx` |
| 弹窗遮罩 / 弹窗体 | `z-40` / `z-50` | `components/ui/Dialog.tsx` |
| 工作流 chip 的文字 | `relative z-10` | `shell/FlowSwitcher.tsx`（当初是为了压住指示块，见那里的注释） |
| 分段控件 chip 的文字 | `relative z-10` | `components/ui/SegmentedControl.tsx` |

**诊断（第一步就做，不猜）**：菜单打开时，在「菜单面板与被压住的元素重叠的那一点」调
`document.elementFromPoint(x, y)`，看命中的是谁；同时把双方的 `getComputedStyle` 里的
`z-index / position / isolation / transform / filter` 与各自的「层叠上下文祖先」打出来。
（`transform`/`filter`/`isolation` 会凭空造出层叠上下文 —— 这类问题十有八九出在这里。）

**修法（按诊断结果取一条，并保证体系化）**：

1. 在 `tokens.css` 立一条 **z 轴阶梯**（并写进 `DESIGN.md`）：
   `--z-bar: 10`（外壳三条）< `--z-popover: 40`（菜单/提示/选择器）< `--z-modal-scrim: 60` < `--z-modal: 70` < `--z-toast: 80`；
   所有浮层改用这些令牌，**不再写字面量**；
2. 外壳的每一条（`titlebar`/`flowbar`/`toolsbar`）如果确实需要 `z`，就统一挂 `--z-bar`，
   并**不要**在其中任何元素上写更高的值（chip 的 `z-10` 改成相对同层可见的那个令牌）；
3. 若诊断发现凶手是某个 `transform`/`filter`/`animation`（例如 `motion.css` 的入场动画），
   就把动画限制在**不影响层叠**的属性上，或给它显式 `isolation` 归位。

**永久回归断言**（写进 `pnpm smoke:ui`）：打开帮助菜单 → 在菜单面板范围内的若干点调
`elementFromPoint`，**必须全部命中菜单内部**；不打开时同一批点必须命中菜单**外面**（反过来证明测的是真东西）。

## 已定（人类 2026-09-16 答复）

1. **焦点圈**：按「先清焦点、再关闭」做（见 C）。Esc 一律先清焦点；点遮罩同理。**不做输入模态那套**。
2. **点遮罩关闭**：保留（业界常规）。
3. **密度**：温和收紧（见 D 的表）。
4. **C 盘那条**：待人类确认当时看的是哪个窗口（WSL dev 窗口 / Windows exe）——见「F. 来源树」；
   无论哪个答案，F 里的 Linux 卷收敛都照做。
