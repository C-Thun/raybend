## 0. W0 —— 先修 Windows 页面打不开（P0，阻塞一切 Windows 验证）

> **这是开工前的第一件事。** 在修好之前，**任何 Windows 侧的验证都无法进行**。

### 0.1 现象

| 平台 | 构建方式 | 结果 |
| --- | --- | --- |
| WSL/Linux | `pnpm tauri dev` | ✅ 正常（窗口 + 页面内容都在） |
| **Windows** | 裸 `cargo build` + 直接跑 exe | ❌ **窗口出来了，但页面访问不到** |

### 0.2 根因（已定位到源码级）

```rust
// tauri-2.11.5/build.rs:256
let custom_protocol = has_feature("custom-protocol");
let dev = !custom_protocol;          // ← dev 由 feature 决定，不是 debug/release！
```

```rust
// tauri-codegen-2.6.3/src/context.rs:176
let assets = if let Some(assets) = assets {
    quote!(#assets)
} else if dev && config.build.dev_url.is_some() {
    let assets = EmbeddedAssets::default();   // ← dev=true 时嵌入资源是空的！
    quote!(#assets)
} else {
    // 从 frontend_dist 真正嵌入资源
};
```

调用链：`cargo build`（无 CLI）→ `custom-protocol` feature 未开 → `dev = true`
→ **嵌入资源为空** → webview 去连 `devUrl`（`http://localhost:1420`）→ 本机没服务 → **页面打不开**。

### 0.3 为什么之前没发现（驗证漏洞）

M0-1 那次 Windows 验证**只检查了 `MainWindowHandle` 与 `MainWindowTitle`**，
**从未检查页面内容**。“窗口出现了”不等于“功能对了”（`AGENTS.md` §2.8）—— 这次是活生生的例子。

另外还有个次要问题：那次 exe 的时间是 `02:50`，而 `dist/` 是 `10:28` 重建的，**产物比前端资源还旧**。

### 0.4 修法

**根因是 `src-tauri/Cargo.toml` 里没有 `[features]` 段** ——
`create-tauri-app` 模板自带 `custom-protocol`，在 M0-1 “删净模板演示” 时被一并删掉了。

```toml
# src-tauri/Cargo.toml 补回
[features]

# 生产构建必须启用。裸 `cargo build` 不加它会得到 dev=true，
# 嵌入资源为空 → webview 去连 devUrl → 页面打不开。
# Tauri CLI 的 `tauri build` 会自动加，但我们的 Windows 构建路径不走 CLI。
custom-protocol = ["tauri/custom-protocol"]
```

Windows 构建命令相应改为：

```bash
# 注意用 -p 而不是 --workspace（--features 需要能定位到具体包的 feature）
cmd.exe /c 'pushd \\wsl.localhost\Ubuntu-24.04\home\andares\repos\c-thun\raybend & cargo build -p raybend-desktop --features custom-protocol'
```

### 0.5 验证方式（必须包含页面内容）

仅看窗口句柄不够 —— 至少满足以下**两条**才算通过：

1. 用 `take_screenshot` 或人工目视确认**页面真的画出来了**（不是白屏/错误页）
2. 用调试手段确认 **webview 没有向 `localhost:1420` 发请求**

> 修好后要把这条经验写进 `AGENTS.md` §5.3 的 Windows 构建命令旁。

## 1. Context —— 为什么现在要做这个

M1 的原始定义是「建仓 → 导入 → 缩略图可见 → 重启仍在一份」。但经过美术设计阶段，
**M1 的实际范围显著扩大了**：用户给出的导入界面包含了完整的外壳（`titlebar` / `flowbar` / `toolsbar`）
与三列工作区，还有若干跨模块的通用范式（`easy copy`、`easy destroy`、`shortpath`、按时间分组、
批量排除、双档密度、i18n）。

因此 M1 不再只是「数据底座 + 一个导入面板」，而是：

> **把设计稿变成能跑的实物** —— 建立一个可复用的设计系统（令牌 + 基础组件 + i18n），
> 在其上实现外壳与导入工作区，并让它们接上真实的相片仓与导入管线。

**关键判断**：设计与数据底座**可以并行推进**，但 UI 必须建立在设计系统之上，
所以 M1-1（设计系统）排在所有 UI 工作之前。

6. **一个「组件陈列室」页面**：把 16 个组件的全状态 × 两主题 × 两密度铺出来，供人工比对设计稿

### 4.2 关键决策（需在实现前定）

#### 4.2.1 为什么先做「陈列室」而不是直接做界面

用户的规则是「先定义一批最小基础组件」。陈列室让每个组件的全状态可被**一眼比对**，
不必等外壳做完才发现按钮的禁用态或密度切换不对。它同时是**验收物**（见 §7）。

#### 4.2.2 纯自定义 vs Ark UI（逐组件定）

`design/main.md` §4.7 已核对：Ark UI 有对应部件。但**不是所有组件都值得引入 Ark UI**：

| 组件 | 方案 | 理由 |
| --- | --- | --- |
| `Button` / `IconButton` / `Badge` / `Tile` / `PathText` / `SplitHandle` / `ScrollBar` | **纯自定义** | 无复杂状态机，自己写更可控 |
| `Tooltip` / `Menu` / `Dialog` | **Ark UI** | 有焦点管理、定位、ESC/外点关闭等无障碍逻辑 |
| `SegmentedControl` | Ark UI `ToggleGroup` 或纯自定义 | 需实测：我们的「色块移动」动画 Ark UI 未必给 |
| `Switch` / `Checkbox` | **Ark UI** | 无障碍与键盘行为 |
| `RadioCircle`（圆形勾选） | 自定义 + `Checkbox` 的 `asChild` | 视觉特殊 |
| `TreeNode` | **Ark UI `TreeView`** | 层级、展开状态、键盘导航都复杂 |
| `Panel` | 纯自定义 | 只是容器 |

> ⚠️ **`Splitter` 与 `TreeView` 是当初选 Ark UI 的两个理由**，必须在 M1-5 真正用上。
> 若实测发现哪个不可用，需立刻回头评估组件库选型（这是选型成本最低的时刻）。

#### 4.2.3 密度的实现方式

```text
<html data-theme="dark|light" data-density="compact|loose">
```

两档各一套尺寸变量。**禁止** `transform: scale()`；**字号与图标尺寸两档相同**（`DESIGN.md` §8.1）。

## 9. 待确认问题

### 9.1 导入的执行与反馈 UI 在设计稿里没有（**最重要的缺口**）

原 `PLAN.md` 的 M1-W5 列了：**重命名规则、是否复制/移动/就地引用、导入进度与统计、错误清单**。
但你给的导入界面设计里**这些都没有**。三种可能：

- (a) 这轮不做 —— 导入按默认策略（复制 / 不重命名）执行，进度只在状态栏给个数字
- (b) 需要补设计 —— 我先出一版「导入进度与选项」的设计稿，再实现
- (c) 部分做 —— 只做进度与统计，选项留到以后

**倾向 (a)**：M1 的目标是跑通闭环，选项面板会让范围膨胀。但这直接关系到
「5000 张导入」这条 DoD 的体验，需要你定。

### 9.2 简易看图是否属于 M1

你描述的「双击/回车切查看、Esc 返回、滚轮平滑缩放、左上角浮出返回按钮、
双击在适合屏幕↔100% 之间切换」目前写在导入中列的交互表里。

- 若**属于 M1** → 需要做一个 DOM 版简易看图（M2 的 wgpu 视口是另一回事）
- 若**留给 M2** → M1 双击图片只做「选中」或什么都不做

**倾向属于 M1**：它不依赖 GPU，且在导入时逐张确认照片是真实需求。但会增加 M1-5 的量。

### 9.3 多仓在 M1 的边界

右列是「所有库的列表」，但 `PLAN.md` 把「多仓、离线卷」放在 M5。

**倾向**：M1 只做「列出 + 选择一个 + 新建」，**不做**移除/改名/离线卷处理。

### 9.4 字体文件现在就接入吗

`DESIGN.md` §7 定的是 Inter + Noto Sans SC（均 SIL OFL 1.1，可自由嵌入）。
但 Noto Sans SC 完整包约 **10–20 MB**（你的网络中等带宽）。

- (a) 现在就接入完整字体（体量大但一次搞定）
- (b) 只用**子集**（按 `DESIGN.md` §11 的 key 列表抽常用字，体量可降到 1–2 MB）
- (c) 先用系统字体（Windows 用「微软雅黑 UI」），字体留到发布前

**倾向 (b)**：桌面应用最终要内嵌字体保证一致，但子集化能兼顾体量与观感。
不过子集化会让「用户自定义文本」（如文件名、路径）落到 fallback 字体上 —— 需要你接受这个折中。

### 9.5 两处「档位值」需要定

- **照片 tile 缩放滑块的档位**：设计稿里只有滑块，没有档位表（连续还是 5–6 档？档位值是多少？）
- **Recent 的「最近 50 条」与「按时间分组阈值 1 小时」存哪**：`app.db` 的设置表，还是仓内？

**倾向**：tile 尺寸做 **6 档**（如 96 / 128 / 160 / 200 / 256 / 320）；配置统一放 `app.db` 的设置表
（Recent 是跨仓的，放全局库）。
