# M2-W1 第三轮修复：RAW 排序 / 竖拍 RAW 缩略图 / DPI 变更卡死

> 第三轮。前两轮（`92f2b7a`、`de3a3e4`）分别改了片内排序与显示序映射，人类复核**仍未达成目标**，
> 且报了两个新问题。本轮的要求是：**每条都要有证据**，修完自己先验，再交人类。

## Context（人类上报的三条，原文口径）

1. 「raw 排序还是没解决，raw 与位图分开排了，按时间模式下同一个时间段被重复了 2 遍，一遍纯位图一遍纯 raw」
2. 「raw 的图片如果是纵拍，在 tiles 列表里只旋转了图片的展示框……框内的图没转，就仿佛是从横向的图片中截取了纵向的一段展示，双击打开后是能看到完整图的，但是方向仍然是没有旋转的」
3. 「拖动导致 dpi 变更时还是会卡住然后挂掉」

## 一、竖拍 RAW 缩略图（#2）—— 根因已锁定，证据充分

**证据链**：

- 源目录 `C:\src\tmp\pic` 142 个 RW2 中 **22 个是 orientation=8（纵拍）**，例如 `P1000023.RW2`；
  同名的 `P1000023.JPG` 也是方向 8、传感器尺寸 3712×2784（需转 90° 才是 2784×3712）。
- 缩略图缓存签名 `PIPELINE_VERSION = 3` 是 `2a60576`（09-17 **13:25**）抬的；
  而 RAW 的**方向处理**是 `9efeaf0`（09-17 **13:58**）才进来的 —— **方向修复落在版本号之后**。
- 于是 `v3` 签名对「转向之前的旧缩略图」**依然命中**，图没转；
  而 tile 的**纵横比**来自新元数据（`media/tiff.rs` 有测试「竖拍 RAW 的方向不能丢」）→ 框是纵的。
  ⇒ 「**框纵、图横**」的机理与人类描述完全吻合。

**修法**（顺序不能反）：

1. 先**用 `thumb-probe` 对着 `P1000023.RW2` 实测一次**：确认「现管线渲染出来的图」是纵的
   （若仍不是 → 说明方向在 RAW 路径里真的没接上，那才是要改的代码；此时问题**不是**缓存）。
2. 抬 `PIPELINE_VERSION` 3 → 4（`crates/raybend/src/thumbnail/render.rs`）。
   旧缩略图会变成孤儿，由既有 GC 清掉（`thumbnail/cache.rs` 的 `render_sig NOT IN (…)`）。
3. 结论写进 `implementations/`：**「改渲染行为就要抬版本号」这条以后按发布清单走**
   （这是第二次踩同一个坑：第一次是 `2a60576`）。

## 二、DPI 变更卡死（#3）—— 无 panic，按「挂起」查

**已知事实**：

- `/tmp/raybend-desktop.log` 里两次启动**都没有 panic**（上一轮的 `Surface::configure` 崩溃已消除）。
  所以这次是**卡住**（挂起）而不是崩溃 → 与上一轮不同的问题。
- 渲染循环里 `shared` 锁是分段持的、没跨 `render()`；事件通道无界 → **不是锁死**。
- 但循环**每帧**调 `refresh_window_facts(&window, …)`
  （`inner_size` / `scale_factor` / `is_maximized` / `is_decorated` 等**跨线程**调用）。
  Windows 拖动窗口时跑的是**模态消息循环**，这些调用会被拖住 —— 「拖动时卡几秒」机理吻合。

**修法**：

1. **每帧的跨线程调用改成事件驱动**：窗口事实只在 `Resized` / `ScaleFactorChanged` /
   初始化时刷新（事件处理器已在更新 dpi/size）；渲染线程不再每帧去问窗口。
2. 渲染循环加**阶段耗时日志**（等命令 / apply_command / render / 加锁各自耗时，只在超阈值时打），
   窗口事件加**速率计数**（拖动时会刷屏，正好能看出事件风暴）。下次复现就能直接看出卡在哪一段。
3. **把复现变成程序化的**（不再靠人手拖）：用 PowerShell 的 Win32 `SetWindowPos` / `MoveWindow`
   把 spike 窗口在两块屏之间来回搬 —— 这会真实触发 DPI 变化。做成
   `scripts/spike-dpi-move.mjs`（或加进 spike 窗口的一键按钮），人类和我都能一键跑。
4. 若证据显示卡在 wgpu/DXGI 的 `get_current_texture`（swapchain 重建期间阻塞），
   则按 `AGENTS.md` §6.1 的既定退路处理，并把结论登记 `FUTURE.md`（透明挖洞的 Windows 风险）。

## 三、RAW 与位图分层（#1）—— 根因已证，**不在排序，在时间本身**

### 已得到的人类确认

- 现象出现在**导入工作流**（源目录 tiles）；
- 屏幕上就是**两个同名的分组标题**（同一天出现两次）。

### 证据（对真实源目录 `C:\src\tmp\pic` 走一遍应用同一套口径）

```text
EXIF 时间读到了多少：位图 158/158    RAW 0/142          ← RAW 一个都没读到 ✗
切出 9 片，其中 6 片「纯一种格式」；同一天出现多次（09-12 ×3、09-13 ×5）
  2026-09-13  00:54→01:08   位图   3   RAW   0        ← 纯位图
  2026-09-13  03:58→04:26   位图   0   RAW  10        ← 纯 RAW
  2026-09-13  13:52→17:59   位图 129   RAW   0        ← 纯位图
```

**机制**：位图的时间来自 EXIF（真拍摄时间），RAW 读不到时间就退到 **mtime**（拷贝时间，
与拍摄时间差几小时到几天）→ 两种格式落进**不同的时间片** → 同一天的分组标题出现两次，
而且每组只剩一种格式。

⇒ 这也解释了**为什么前两轮都白改**：`92f2b7a`（片内保持传入顺序）与 `de3a3e4`（片内按文件名自然序）
改的都是**片内顺序**，而片**边界**早就把两种格式分开了。分组根在时间，不在排序。

⇒ 同一病根还解释了**库里的时间全是 NULL**（`测试库` 8 张 `taken_at` 全空）——
时间采集在导入那条路上同样丢了。

### 修法（按优先级）

1. **查清“RAW 时间为什么读不到”**（两种可能，必须先用真实文件分辨）：
   - (a) 这些 RW2 的 `DateTimeOriginal` 确实在（我早前的实测从 `P1000019.RW2` 读出过
     `2026:09:13 00:54:28`）—— 那就是**采集链路上丢了**（扫描的快速兜底赢了、
     或者结果没合并回条目），要修的是 `media/source.rs` / `import` 的合并逻辑；
   - (b) 部分 RW2 确实没写（那就靠下面的配对继承兜底）。
   验证手段：拿真实文件跑现有探针（`examples/thumb-probe.rs`、`examples/raw-smoke.rs`）
   把时间打出来；再加一条针对 `source_times` 的合成测试。
2. **RAW 从同名位图继承时间**（无论 (a)/(b) 都要做，这是本轮的**主修**）：
   同一目录下 `P1000019.RW2` 与 `P1000019.JPG` 是同一张照片（RAW 分流规则已经这么认了，
   见 `REPOSITORY.md` §4.1）。RAW 自己没有拍摄时间（缺失、或只有 mtime 兜底）时，
   **继承同名位图的时间**。这样：
   - 源目录里的两种格式落回同一片（人类看到的就是“一个时间段内 JPG 与 RAW 挨着”）；
   - 导入后的库里 `taken_at` 也不再是 NULL。
   位置：`media/source.rs`（源扫描/时间）/ `import/fsops.rs`（入库前定时间）
   共用一个“配对继承”纯函数，可单测（同名不同扩展名、目录不同、多张同名、大小写、缺一边）。
3. **已有库的补救**：范围待定（见下）。

### 需要人类定的一个范围问题

已经导入的库里 `taken_at` 全是 NULL —— 要不要本轮一并做**重扫补救**
（一个命令：遍历库里资产、按配对规则回填缺失的拍摄时间）？
我的建议：**本轮做“新导入走对”，补救留成单独一步**（它要改已入库数据，属于写操作，
想单独评审、单独切一个提交，不跟本轮渲染/DPI 两件混在一起）。

### #1 的验证

- 合成测试：给“RAW 无时间 + 同名 JPG 有时间”的输入，断言 RAW 继承后与 JPG 同片；
- 真实数据：对 `C:\src\tmp\pic` 再跑一遍本节的模拟脚本（或等价探针），
  断言「纯一种格式的片」从 6 降到 0（只在真的没有同名位图时才会出现纯 RAW 片）；
- 人类在导入网格再看一次：同一时间段里 JPG 与 RAW 挨着，不再出现同名标题两遍。
