## 3. Approach

### 3.1 目录与职责（`crates/raybend/src/store/`）

```text
store/
├── mod.rs           对外 API：open_app_db / open_catalog / RepoStore 类型
├── path_semantics.rs 路径规范化：NFC + 大小写折叠 + 分隔符统一（纯函数，可单测）
├── file_id.rs        文件身份：(VolumeSerial, FileId128)，Windows 用 Win32、其它平台用 (dev, ino)
├── migration.rs      迁移执行器：PRAGMA user_version + 迁移前快照 + 版本闸门
├── migrations/       纯 SQL 文件，按序号命名，用 include_str! 嵌进二进制
│   ├── catalog_0001_init.sql
│   └── app_0001_init.sql
├── pool.rs           读连接池（PRAGMA 统一设置）
├── writer.rs         单写者 actor（mpsc + 专属连接 + 事务助手）
└── repo.rs           仓模型：repo.json 的读写与校验（uuid / 名称 / 根目录集合）
```

**分层纪律**：`store` 只依赖 `rusqlite` 与标准库，**不认识 Tauri、不认识 wgpu、不认识缩略图**。
路径由调用方注入（`src-tauri` 用 Tauri 的 path API 取 `%LOCALAPPDATA%` 后传进来）——
这是业务 crate 不依赖 Tauri 的具体落法。

### 3.2 两个库的 schema v1（只做 M1 真用得上的）

**`app.db`（全局）**

| 表 | 用途 | 关键列 |
| --- | --- | --- |
| `settings` | 应用设置（Recent 上限、时间分组阈值、缓存上限…） | `key` PK, `value`(TEXT/JSON), `updated_at` |
| `repositories` | 仓注册表 | `id` PK, `uuid` UNIQUE, `name`, `catalog_version`, `created_at`, `last_opened_at` |
| `repository_roots` | 一个仓可以有多个根目录 | `repo_id`, `path`, `path_folded`, UNIQUE(`repo_id`,`path_folded`) |
| `jobs` | 持久化任务队列（M1-3 的扫描/缩略图、M1-6 的导入都用它） | `id`, `kind`, `payload`(JSON), `state`, `attempts`, `created_at`, `updated_at` |

**`catalog.db`（每仓）**

| 表 | 用途 | 关键列 |
| --- | --- | --- |
| `assets` | 一张照片（逻辑实体） | `id` PK, `taken_at`(INTEGER 毫秒，可空), `camera`, `lens`, `focal_mm`, `f_number`, `exposure_ms`, `iso`, `width`, `height`, `orientation`, `format`, `rating`, `flag`, `imported_at`, `updated_at` |
| `asset_files` | **物理文件**（一张照片可以有多个文件） | `id` PK, `asset_id` FK, `role`('primary'/'companion'), `path`, `path_folded`, `ext`, `size_bytes`, `mtime_ms`, `volume_serial`, `file_id`(BLOB 16), `missing_since` |
| `asset_files_identity` | 身份唯一索引的载体（`file_id` 为空时退化为路径） | 见 §3.4 |
| `assets_fts` | 中文可用的全文索引（`tokenize='trigram'`） | `filename`, `camera`, `lens` |
| `schema_meta` | 写入本库的 schema 版本与算法版本 | `key`, `value` |

- **为什么把文件与照片分开**：RAW+JPG 成对是真实存在的（你的样本里就有 142 对），
  而「一张照片」在界面上只该出现一次。合并与否是产品决策（见 §9 问题 2），
  但**schema 先支持两种解释**：现在按「两个文件 → 一个 asset」写入，
  若你决定分开，只是插入逻辑改一处，不用改表结构。
- **EXIF 直接放 `assets` 而不是单独表**：M1 的查询全是「按拍摄时间排序 / 按机型筛选」，
  单独表只添一次 JOIN，没有收益。将来真的要「同一张照片的多套元数据」再拆。

### 3.3 写并发：单写者 actor（`AGENTS.md` §6.4）

```text
所有写操作 ──► WriterHandle (mpsc<Command>) ──► 专属线程 + 专属 Connection ──► SQLite
读操作    ──► 读连接池（N 个只读连接，WAL 下不阻塞写）
```

- 命令用枚举（`InsertAssets` / `SetRating` / `EnqueueJob` …），每批在**一个事务**里完成；
- `Drop`/`shutdown()` 时发终止命令并 join —— 保证退出前事务已提交（M1-7 的「杀进程后队列与库一致」要靠这个前提）；
- 单写者让「并发写」在类型层面就不可能出现 —— 这是选它而非「到处开连接 + 忙等」的理由。

**PRAGMA 统一设置**（读池与写连接都设）：
`journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`、`foreign_keys=ON`。

### 3.4 文件身份与路径（`AGENTS.md` §7.3）

- **身份优先用 `(volume_serial, file_id128)`**：Windows 走 `GetFileInformationByHandleEx(FileIdInfo)`；
  其它平台退化为 `(dev, ino)`。取不到时写 NULL，**由路径兜底**（`missing_since` 标记丢失）。
- **路径三列**：`path`（NFC 规范化、保留大小写，供展示）、`path_folded`（NFC + 小写，供唯一索引与比较）、
  以及原文（`path_raw`，供将来还原）。**唯一索引建在 `path_folded` 上**，这样 Windows/macOS 的大小写不敏感语义
  与 Linux 的敏感性差异在语义层被吃掉，而不是散落在各处的 `lower()`。

### 3.5 迁移、备份与版本闸门（**本单元的重点**）

```text
打开库
 ├─ 读 PRAGMA user_version = V_db
 ├─ 若 V_db > V_known（程序支持的版本）→ **拒绝打开**，返回明确错误（提示用更高版本的程序）
 ├─ 若 V_db < V_known → ① 先 VACUUM INTO 快照（保留最近 7 份，按时间命名）
 │                     ② 在事务里逐条执行迁移
 │                     ③ 更新 user_version
 └─ 正常打开
```

- 迁移**只向前**，每条迁移在**独立事务**里（失败即整条回滚，`user_version` 不前进）；
- 快照目录：`<app data>/backups/`（catalog 快照与 app.db 快照分开），`VACUUM INTO` 是原子且不阻塞读的方式；
- 迁移文件用 `include_str!` 嵌入 → 单文件分发时不会漏带 SQL；
- **测试**：v0→v1 正常升、快照生成与轮转（保留 7）、`V_db > V_known` 必须拒绝、迁移中途失败要回滚。

### 3.6 云同步盘 / 网络盘检测（`AGENTS.md` §6.4）

`classify_location(path) -> LocationKind { Local, Network, CloudSync, Unknown }`（纯函数 + 少量平台调用）：
UNC 前缀与 Windows 驱动器类型（`GetDriveTypeW`）能判网络盘；常见云盘同步目录（OneDrive/Dropbox/坚果云…）
按路径模式识别。**命中时返回警告而不是拒绝** —— 用户可能确实想这么放，但必须让他知道风险。

## 5. 依赖（请你在评审时确认，`AGENTS.md` §2.9 要求先讨论）

| 依赖 | 用途 | 为什么是它 | 体积/风险 |
| --- | --- | --- | --- |
| `rusqlite`（`bundled`） | SQLite 绑定 | `bundled` 自带 SQLite 源码编译，**不依赖系统 sqlite**（Windows 上尤其重要），且能开 FTS5 | 编译时间略增（一次性） |

| `serde` + `serde_json` | `repo.json` 与 `jobs.payload` | 已在 workspace | 已在 |
| `tempfile`（**dev-dependency**） | 测试用临时目录 | 测试不该写用户的真实目录 | 仅测试 |
| ~~`r2d2` + `r2d2_sqlite`~~ | 读连接池 | **倾向不引**：需求只是「几个只读连接 + 借还」，自己 30 行足够，少一层依赖与版本纠缠 | 见 §9 问题 1 |

## 11. 评审意见的落实（2026-09-15）

四条意见已收到，逐条落点如下。

### 11.1 读连接池：自己写 ✅（依你的意见）

不引 `r2d2`。`store/pool.rs` 自写一个小模块：`Mutex<Vec<Connection>>` + 借/还 + 容量上限 +
「连接坏了就丢弃重建」这一条基础防护（本机文件，不是远程服务，故障概率极低）。
**不为它做重试/健康检查/超时那套** —— 那才是 r2d2 的价值所在，而这里用不上。

### 11.2 库与导入：业务规格已落 `LIBRARY.md` ✅

你口述的整套业务（库结构、同路径多库/同库多路径、在线离线、导入模版与变量、序号、
重名 `_XX`、位图/RAW 分流、目录透传）已整理成 **`LIBRARY.md`**，并据此调整了本单元的 schema：

| 调整 | 说明 |
| --- | --- |
| **库物理结构变更** | `catalog.db` **直接在库根**（不再有 `.raybend/` 子目录与 `repo.json`）；导入物落 `photos/`。`AGENTS.md` §6.4 已同步更新（原布局与你的口述冲突，按你的口述改） |
| **`app.db` 的库表改为「ID + 多路径 + 状态」** | `libraries(id, name, import_template_cache, created_at, last_opened_at)` + `library_paths(library_id, path, path_folded, last_seen_at, status)`，`UNIQUE(path_folded, library_id)`（**不是**路径唯一 —— 这是「同路径不同库」的前提） |
| **库 ID 存在 `catalog.db` 内** | 新增 `library_meta(key, value)` 表，第一行就是 `library_id` |
| **导入模版与序号进 `catalog.db`** | `library_meta` 存 `import_template`；新增 `seq_counters(directory, width, value)`，主键 `(directory, width)` —— 对应你要求的「不同位数各自计数」 |
| **资产表按「库内相对路径」存** | 导入后的文件归我们管理，路径列存 `photos/...` 相对路径（同时保留原始绝对路径用于溯源） |
| **`asset_files.role` 增加 `raw`** | 位图/RAW 关联用 `role ∈ {bitmap, raw}` + `pair_id`；**关联不强制**（你可以自由移动文件），查找时按「同目录 `_RAW/` 下同名」的约定 |
| `index.db` | 本单元**不建**（`LIBRARY.md` §1 已说明：真需要可重建索引时再加） |

**M1 的范围划分**（避免 M1-2 提前吞掉 M1-6）：M1-2 只交付**表结构 + 打开/迁移/备份/写并发**；
模版解析、序号分配、重名处理、RAW 分流、目录透传在 **M1-6** 实现 —— 但表结构现在就为它们留好位置。
