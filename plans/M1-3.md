## 1. Context —— 这一波要解决什么，以及 v1 之后变了什么

**这一波的直接目标**：让库里**真的有东西** —— 磁盘上的照片变成 `assets` / `asset_files` 记录，
并生成**能看的缩略图**。这是 M1-5（导入工作区）、M1-6（导入执行）与之后整个浏览模式的地基。

**v1 之后出现的三件新情况**（这就是要重排计划的原因）：

| # | 新情况 | 对本波次的影响 |
| --- | --- | --- |
| 1 | **`BROWSE.md` 落地**（浏览模式规格） | 需要一批 v1 时没规划的**数据字段**（色标 / 喜欢 / 锁 / 作者 / 描述 / 地理 / 标签）——见 §3.A |
| 2 | **标签体系**（`BROWSE.md` §7） | `app.db` 要加**全局标签词典**，每库要加**资产↔标签关联**；这两个表现在**都不存在** |
| 3 | **浏览稿已出**（`design/browse.pen` 七帧） | 缩略图要同时服务**网格 9 档**（`--tile-cell-w`，最大 512）与**胶片带**（浏览稿是 96×80 显示，缓存给 2×）；即**两种尺寸档**而不是原来只想的 GRID 一档 |

**顺带确认的好消息**：v1 里担心的「RAW 内嵌预览」在本波次**不需要**——用户的真实样本是
JPG + RW2 **同名成对**（`ASSISTANCE.md` A3 历史记录 / `REPOSITORY.md` §4.1），位图那张就是缩略图来源；
只有 RAW 没有 JPG 的情况用**占位缩略图**兜住（见 §7 问题 1）。

## 2. 本波次的范围（Wave scope）

```text
M1-3  扫描 · 元数据 · 缩略图      ← 这一波（本文件）
```

## 3. Approach

### 3.A schema v2：把浏览要的字段补齐（**本波次第一步**）

M1-2 已建好迁移框架（版本闸门 + 快照 + 逐条事务 + 完整性检查），所以这一步很便宜：
**新增 `catalog_0002_*.sql` 与 `app_0002_*.sql` 两条迁移**，跑一次就是 v2。

**`catalog.db`（资产侧，全部可空，带默认值）**：

| 列 | 用途（出处） |
| --- | --- |
| `color_label` | 色标 6 态：`null`(无) / `red` / `yellow` / `green` / `blue` / `purple`（`BROWSE.md` §3.2） |
| `like_state` | 喜欢三态：`null` / `like` / `dislike` |
| `lock_level` | 锁：`0` 无 / `1` 不可删 / `2` 不可编辑（`BROWSE.md` §3.4） |
| `author` | 作者（可编辑；将来按库自动写，`FUTURE.md` H7） |
| `description` | 描述（可编辑） |
| `gps_lat` / `gps_lon` | 经纬（REAL） |
| `country` / `province_state` / `city` / `sublocation` | 地理四段（可编辑） |

> **旗标不进库**：`BROWSE.md` §3.2 明确旗标**只在内存**（跨库跨目录、关软件即清），
> 所以**不建列**；现有 `flag` 列留给「入库时判定」之类的持久语义，语义要与旗标分开写清楚。

**标签（两张表，分居两库）**：

| 库 | 表 | 说明 |
| --- | --- | --- |
| `app.db` | `tags(id, name, name_folded, created_at, use_count)` | **全局词典**（`BROWSE.md` §7.1：「用过的标签会存进 app.db」）。`name_folded` 用现成的 `path_semantics` 折叠函数复用同一套「相等」判据 |
| `catalog.db` | `asset_tags(asset_id, tag_id, tagged_at)` | 每库的关联；`tag_id` **不带外键**（跨库），弱引用 + 允许孤儿 |

> 跨库引用不做外键是**有意**的：标签词典在 `app.db`，而 `catalog.db` 要能**单独搬走**（`REPOSITORY.md` §2）。
> 库打开时由上层做一次「词典对齐」：把本库用到的 tag_id 在 `app.db` 补登记名称。

**现有 `assets_fts` 索引**（v1 建的是 `file_name/camera/lens`）：v2 顺手把 **`tags` 与 `description`** 加进索引，
为 `FUTURE.md` H8（搜索扩展到照片信息）铺路 —— 注意保持 **trigram**，并记住**两字查询搜不到**（要 `LIKE` 兜底）。

### 3.B 扫描与变更追踪（`media/scan.rs` + `media/diff.rs`）

- **扫描**：可中断（`AtomicBool`）、按目录批量顺序读（HDD 友好）、并发可配（默认 `min(4, cores)`）；
  只认白名单扩展名（`media/kind.rs`），跳过隐藏文件 / `:Zone.Identifier` / 我们自己的库文件。
- **变更追踪**（本单元最有价值的部分）：对已有记录做差异比对，优先级
  `(volume_serial, file_id)` → `(size, mtime)` + 同目录名相似度 → 折叠路径 → 新文件；
  扫不到的置 `missing_since`，**绝不删记录**（`AGENTS.md` §6.4）。
- **重命名/移动识别**靠 v1 就建好的 `file_id`（`store/file_id.rs`，改名后不变 —— 已有测试守着）。

### 3.C EXIF 与缩略图

- **EXIF**：`kamadak-exif`（纯 Rust / MIT）→ 填 `taken_at` + `camera_*` / `lens` / `focal_mm` / `f_number` /
  `exposure_ms` / `iso` / `width` / `height` / `orientation`；**`taken_at_source` 记录来源**
  （`exif` / `filename` / `file_mtime`），这是 v1 就留好的透明性设计。
- **缩略图缓存**：`<app data>/cache/<repository_id>/thumbs.db`（独立文件、复用 `store::pool` / `store::writer`）。
  键 = `(cache_key, size_class, render_sig)`，其中 `cache_key` 用**文件身份**（这样导入工作区里**还没入库的源文件**
  也能共用缓存 —— M1-5 要显示源目录网格）。
  **两个尺寸档**（新情况 3）：`grid`（长边 384，够 9 档里最大的显示；512 档按需再提）与 `strip`（长边 192，胶片带 2×）。
  `render_sig` 含 `pipeline_ver`，算法升级后旧缓存自动变孤儿。
- **渲染**：`image`（只开 `jpeg`/`png`/`tiff`）解码 → `thumbnail()` 盒式缩放 → **JPEG q82** 编码；
  **RAW / 非图片 → 程序化占位图**（深底 + 「RAW」字样，不依赖字体文件）。
  **红线**：删掉整个 cache 目录 = 只是要重新生成，库文件一个字节都不受影响（`AGENTS.md` §6.5）。
- **任务队列**：复用 M1-2 建好的 `jobs` 表（`state` / `attempts` / `priority` 都有）；
  worker 池默认 `min(4, cores)`；崩溃后把 `running` 重置为 `pending`（超过 attempts 上限 → `failed`）；
  取消 = 标志位 + 每完成一项检查一次。

### 3.D 吞吐实测（决定要不要 SIMD）

`examples/thumb-bench.rs`（不进 `cargo test`）在 `/mnt/c/src/tmp/pic`（301 文件 / 4.2 GB）上跑：
报告 **文件/秒、MB/秒、平均缩略图字节、P50/P95 单张耗时**。
WSL 下 `/mnt/c` 走 9p 会比 Windows 慢，**只用来回答「够不够用」与「要不要上 `fast_image_resize`」**。

## 7. Verification

3. **在真实样本上跑扫描**（只统计不写库）：文件数 / 配对情况 / 时间戳来源分布
4. **在临时库上跑完整链路**：建库 → 扫描 → EXIF → 缩略图 → 关进程 → 重开 → 数据仍在、缩略图还能读

6. **崩溃续跑**：伪造 `state='running'` 的任务 → 重启后被重置并跑完

- 拿样本看一眼：**JPG 缩略图的观感**（锐度/色彩是否可接受）、**RAW 占位图是否可接受**

## 8. 待你定夺

1. **RAW 内嵌预览要不要进这一波？**
   (a) **先不做**（推荐）：RAW 用占位图；你的样本里 RAW 都配了同名 JPG，观感几乎不受影响；
   (b) 现在就做：引 `rawler` + **独立 worker 进程**（`AGENTS.md` §6.3 要求），能覆盖「只有 RAW」的情况，
   代价是新依赖 + 进程间协议 + Windows 上 rawler 未官方支持；
   (c) 折中：先 (a)，但把 worker 进程的**接口与协议**定下来，等编辑里程碑接后端时填实现。
2. **EXIF 依赖 `kamadak-exif`**（纯 Rust / MIT）可以吗？（备选 `rexif`，更小但维护弱）
3. **缩略图编码 JPEG q82** 可以吗？（备选 WebP：更小但编码慢、`image` 的编码支持有限）
4. **实时目录监听（`notify`）推到 M5** 可以吗？M1 用「按需扫描」已经够（导入后扫一次、库刷新时扫一次）。
5. **缓存位置 `<app data>/cache/<repository_id>/thumbs.db`** 可以吗？（库根保持只有 `catalog.db` + `photos/`）
6. **schema v2 的字段清单**（§3.A）有没有要加/要改的？特别是：**旗标不建列**（只在内存）你确认吗？
7. **缩略图两档（grid 384 / strip 192）**够吗？还是要直接支持到 512（浏览网格最大档）？
8. **色标 5 色的正式取值**：浏览稿暂用 `#D9635C / #E8B93E / #6FBF73 / #5B9BD5 / #9B7FD4`，
   要进 `DESIGN.md` 并做对比度校验（**黄与品牌辅色 `#F0B033` 尤其要拉开**）—— 这一步想在 schema 定稿前完成。

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 真实照片上解码/缩放慢（WSL 走 9p） | §3.D 先量化；不达标再上 `fast_image_resize`（SIMD） |
| RAW 占位图被当成 bug | 占位图直接写「RAW」字样；实施记录 + `BROWSE.md`/`REPOSITORY.md` 里都写明这是有意取舍 |
| 扫描把用户目录读爆（符号链接环、超深目录） | 默认不跟随符号链接、限深度、可中断 |
| 缩略图任务与导入抢写 | 都走同一个单写者；**每张一个短事务**，不持有长事务 |
| `thumbs.db` 损坏 | 它是缓存：打不开就删掉重建（红线：删缓存目录后功能仍可用） |
| 依赖体积（`image` 不小） | 只开 `jpeg`/`png`/`tiff`，不开 `avif`/`hdr` |
| **跨库标签成孤儿**（词典在 app.db） | 库打开时做一次「词典对齐」；孤儿标签在 UI 上按「待命名」显示而不是崩 |
