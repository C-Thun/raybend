## 1. Context —— 为什么现在做这个

M1-5 交付了导入工作区的三列：能选库、能勾目录、能看到照片网格、**导入按钮的可用性已经算好**，
但按钮按下只显示一句「导入中…（M1-6 实现）」。M1-6 就是把这句话兑现 —— 也是 M1 完成定义
（`PLAN.md` §M1 DoD）里「把照片真的导进库、重启后状态完整」那一条的主体。

这一单元结束时应当能做到：

```text
勾 3 个目录 → 选一个库 → 按「导入」→ 进度弹窗逐阶段推进 → 完成后这些照片
在库里的 photos/ 下按模版就位（RAW 在同级 _RAW/），catalog.db 里有 assets/asset_files 行，
缩略图任务已入队，重启应用后它们还在
```

## 3. Approach

### 3.1 模版求值（`crates/raybend/src/import/template.rs`）

纯函数，**本单元最该被钉死的一块**（`REPOSITORY.md` §3.2–§3.5）：

```rust
pub struct Template { parts: Vec<Part> }          // Part = Literal(String) | Var(Var) | Seq(usize)
pub enum Var { CYear, CMonth, CDay, CWeek, FileName, Brand, Model }

pub fn parse(src: &str) -> Result<Template, TemplateError>;      // 语法 + 非法字符 + 末尾 '/' + 空
pub fn validate(src: &str) -> Vec<Warning>;                       // 未知变量（不致命，给即时反馈）
pub fn render(&t: &Template, ctx: &RenderCtx) -> String;          // 目录部分 + 文件名部分
```

三条容易做错、必须写进测试的规则：

1. **最长前缀匹配**：`:FILENAMEGO` → `FILENAME` + 字面量 `GO`（**不是**未知变量）。
   已知变量名集合排序后按前缀匹配；`:` 后不匹配任何变量名时按字面量输出 + 一条警告。
2. **序号宽度即身份**：`:SEQ000` 与 `:SEQ0000` 在**同一目录**下是两个独立计数器（键 = 目录 + 宽度）。
3. **变量来自「每张照片自己」**：同一批里不同日期 → 不同目标根目录（`REPOSITORY.md` §4.2 的表格）。

### 3.2 目标路径规划（`import/plan.rs`）—— 本单元的核心，纯逻辑 + 可注入 FS

输入：扫描结果（源根、每个文件的相对路径、身份、拍摄时间） + 模版 + 选项（含子目录 / 避免重复）。
输出：`Vec<PlannedItem>`（源路径、目标相对路径、角色 bitmap/raw、状态 skip/fail/plan）。

```rust
pub trait FsProbe {                       // 真实实现查盘；单测用内存实现（不碰真文件）
  fn dir_exists(&self, rel: &str) -> bool;
  fn file_exists(&self, rel: &str) -> bool;
  fn free_bytes(&self) -> Option<u64>;
}
pub fn plan(files: &[SourceFile], tpl: &Template, opts: &PlanOptions, fs: &dyn FsProbe,
            known: &KnownIdentities, seq: &mut SeqAllocator) -> PlanResult;
```

按 `REPOSITORY.md` §4.1/§4.2 实现，顺序不能换：

```text
① 目录透传：源子树的每个目录，只有「含可导入图片」才保留（空目录/只含文档不建、不复制）
② 模版求值出「该文件的 target 根」：模版的目录部分只在这里求值一次
③ 把文件相对源根的目录层级原样搬到 target 根之下（几层搬几层，不逐层套模版）
```

三条纪律写进测试：**同一个 target 根下才共享序号**；**位图/RAW 同名成组**（两者都有 → RAW 进
同级 `_RAW/`；只有 RAW → 正常进目标目录）；**重名加 `_01`…`_99` → `_100`**（主序号不因此后退，
追加位置在扩展名之前）。

### 3.3 执行器（`import/runner.rs`）—— 后台线程 + 原子标志 + 事件节流

- **不占主线程**：`std::thread::spawn` 一个导入线程（不是 `spawn_blocking`，它要活几分钟）。
- **暂停 / 取消**：`Arc<AtomicU8>` 表示 `Running | Pausing | Paused | Cancelling`；
  检查点是**每个文件之间**（复制中途不打断，半截文件比慢更糟）。
- **每个文件的顺序（不能反）**：

  ```text
  ① import_items 先插一行 status='pending'（target_rel 已确定）
  ② 复制文件（.part 临时名 → 复制完 rename 就位；避免半截文件被当成成品）
  ③ 更新 status='copied'
  ④ 登记 assets / asset_files（在同一批事务里）
  ⑤ 更新 status='done'
  ```

  这样任何时刻被杀，重开都能凭 `target_rel` + `import_items.status` 判断该文件到底落没落
  （M1-7 的崩溃演练就查这个）。
- **批量事务**：每 200 个文件或每 500ms 提交一次（进度显示要跟得上，事务也不能太碎）。
- **单文件失败不打断整批**：`status='failed'` + `reason`，继续下一个（`REPOSITORY.md` §4.5）。
- **磁盘预检**：开始前查目标卷可用空间，小于「源总字节 × 1.05」→ **先提示再决定**
  （本机 `C:` 只剩 ~58GB，这不是理论风险）。
- **进度事件**：内部维护快照，**节流到 ≥100ms 一条**（阶段切换、暂停、结束立刻发），
  避免「每文件一事件」把 WebView 打爆。

阶段机（`REPOSITORY.md` §4.4 的四个阶段）：

```text
扫描(scan) → 规划(plan) → 导入(import：复制+登记同拍推进) → 缩略图(thumbs)
```

> **一处刻意的偏差**：规格把「复制」与「登记」写成两个阶段，实现里它们是**同一拍**推进的
> （每批事务提交时一起前进）。理由：分成两遍会让中断后的续跑判断变复杂（可能复制了没登记），
> 而 §3.3 的「先 pending 后 done」已经把这件事表达清楚了。界面上仍然是两条独立计数。

### 3.4 命令与事件（`src-tauri/src/import.rs`）

| 命令 | 语义 |
| --- | --- |
| `import_start(repositoryId, sourceDirs, opts)` | 起一个 run：建 `import_runs` 行 → 起线程 → 返回 `runId` |
| `import_pause(runId)` / `import_resume(runId)` | 原子标志切换；暂停生效点在文件之间 |
| `import_cancel(runId)` | 请求取消；**已导入的部分保留**（返回值里带上「已保留 N 张」） |
| `import_status(runId)` | 当前快照（弹窗重开、刷新后恢复现场用） |
| `import_errors_export(runId, path)` | 把错误清单写成 JSON/CSV（路径由前端用 `tauri-plugin-dialog` 的 save 选） |

事件名 `import://progress`（节流后的事件 + 阶段切换 + 结束），载荷就是 §3.5 的 DTO。

### 3.5 前端（`src/api/import.ts` + `src/features/import/`）

- `api/import.ts`：命令封装 + `onImportProgress(handler)` 事件订阅（返回取消订阅函数）；
  **浏览器降级**：命令返回「不在 Tauri 里」的空结果、事件订阅返回空函数（照 M1-5 的惯例）。
- `features/import/store.ts`：吃事件流 → 派生 UI 状态（阶段、百分比、四类计数、当前项、错误列表、状态）。
  单测喂**假事件流**：阶段推进 / 暂停 / 单文件失败 / 取消 / 结束摘要。
- `features/import/ImportProgressDialog.tsx`（新画布帧）：
  阶段条 + 百分比 + `已导入 / 跳过 / 失败` 计数 + 当前项（文件名 + 库内目标路径）
  - 错误清单（可展开、可导出）+ 暂停/继续/取消 + 结束摘要（含「在库中查看这些照片」）。

- 导入完成后：右列的库卡片刷新张数、中列网格刷新（复用 M1-5 的 store 动作）。

## 7. Risks

| # | 风险 | 处理 |
| --- | --- | --- |
| 1 | **半截文件被当成成品**（复制中途崩溃） | 复制到 `.part` 再 rename；`import_items` 先 pending 后 done |
| 2 | 序号并发/回绕撞名 | 主序号不后退，一律靠 `_01…` 后缀兜底（已定）；计数器走单写者 |
| 3 | 事件把 WebView 打爆（大目录每文件一条） | 节流 ≥100ms + 阶段切换立即发；快照里只带**错误清单尾部** |
| 4 | 取消后用户以为「回滚了」 | 弹窗文案写清「已导入的保留在库中」，取消要二次确认 |
| 5 | 磁盘写满（C: 只剩 ~58GB） | 开始前预检可用空间；失败项记入错误清单并继续 |
| 6 | 9p/WSL 的复制速度不代表真机 | 性能只记**形态与算法结论**，吞吐数字标注环境，不下结论 |
| 7 | 透传把 source 的目录层级搬错（多套一层/丢一层） | `REPOSITORY.md` §4.2 的五种情形逐条写成单测，`error!` 不放过 |
| 8 | 模版把非法字符写进目标名 | `validate` 在 Rust 侧统一判（库设置弹窗与导入前都走它） |

## 8. 默认值（如不同意请在评审时直接说）

| 项 | 默认 |
| --- | --- |
| 复制 vs 移动 | **复制**（第一阶段不做移动；照片的原始来源保持不动） |
| 避免重复导入 | 默认**开**（M1-5 已把它落进设置）；对已在库的文件**跳过**并计入 `skipped` |
| 取消后的处置 | **保留已导入的部分**，不做事后回滚（文件已落盘） |
| 缩略图阶段 | 导入完成后**入队即算这一阶段完成**，生成是后台任务，不阻塞「导入完成」 |
| 错误导出格式 | JSON（结构稳定，便于将来喂给诊断）；用 `tauri-plugin-dialog` 的 `save()` 选路径 |
| 并行度 | 复制**串行**（HDD 友好，且错误顺序可读）；缩略图并行度沿用现成的 worker |
| 新增依赖 | **无**（事件用已在依赖里的 `@tauri-apps/api`，选路径用已装的 `tauri-plugin-dialog`） |
