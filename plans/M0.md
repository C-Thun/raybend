## 环境现状（实测，2026-09-15）

开发机是 **Windows + WSL2（Ubuntu 24.04）**，两端能力差异很大，这直接决定 M0 的执行方式：

| 能力 | WSL2 Ubuntu 24.04 | Windows 侧 |
| --- | --- | --- |
| Rust | ✅ 1.91.1（仅 `x86_64-unknown-linux-gnu`） | ⚠️ 1.86.0 MSVC（**低于 rawler 要求的 1.89**，需升级） |
| Node / pnpm | ✅ v26.5.0 / 12.3.4 | ❌ 未安装（本计划刻意不需要） |
| WebView 引擎 | webkit2gtk 4.1 + GTK3 ✅ | ✅ WebView2 运行时 `152.0.4191.66` |
| MSVC 工具集 / Windows SDK | — | ❌ **均未安装**（`vswhere` 无 VS 实例；`Windows Kits\10` 只有 `UnionMetadata`，无 Include/Lib） |
| 磁盘 | `/` 剩 139G | `C:` 剩 78G（已用 92%），无其他盘 |
| 仓库位置 | `/home/andares/repos/c-thun/raybend`（WSL 文件系统），remote = `github.com:C-Thun/raybend` | 经 `\\wsl.localhost\Ubuntu-24.04\...` 可访问（**已实测可读**） |

### 由此得到的两个硬结论

1. **Windows 侧现在无法构建任何 Rust 二进制**。缺 MSVC 的 `link.exe` 与 Windows SDK 的 `.lib`（`kernel32.lib` 等），编译会停在链接阶段。Windows 上那 496M 的 cargo registry 只是下载的源码包，不代表构建过。**这是 M0 的阻塞项**（见「待确认决策 D10」）。
2. **agent 可以从 WSL 驱动 Windows 构建**：`cmd.exe` 互操作可用，`pushd` 到 UNC 仓库路径**实测可用**（`pushd \\wsl.localhost\...\src-tauri & dir /b` 成功列出内容）。注意 cmd 的 `%CD%` 是 parse-time 展开，不能用它验证目录是否切换。

### Windows 侧构建方式（M0 落地的关键）

因为 Windows 侧不装 Node，走「前端在 WSL 构建、Windows 只跑 Rust」：

```bash
# ① 在 WSL 里产出前端产物
pnpm build                       # → dist/

# ② 从 WSL 驱动 Windows 侧运行（target 落 Windows 本地盘，避免 9p 链接 I/O）
cmd.exe /c 'pushd \\wsl.localhost\Ubuntu-24.04\home\andares\repos\c-thun\raybend\src-tauri & set CARGO_TARGET_DIR=C:\rb-target\raybend & cargo run'
```

- 首选路径：`cargo run` 直接读 `frontendDist`（`../dist`）内嵌资源，**不需要 Node**。
- **待验证**（M0-1 第一步）：`cargo run` 在存在 `devUrl` 配置时的实际行为；以及一个更省事的备选——dev server 跑在 WSL（`pnpm dev`），Windows 侧经 WSL2 的 localhost 转发访问 `http://localhost:1420`，若可行则 HMR 也能用且不需要在 Windows 装 Node。两条路都要实测，取可行的那条并写进 AGENTS.md。
- 后续若要出安装包（M6），Windows 侧可用 `cargo install tauri-cli` 得到 `cargo tauri build`，同样不需要 Node。

## Approach

M0 分成 **7 个波次**，M0-1 先把骨架与工具链立正，中间 5 个并行验证，M0-7 收口并移交 UI 设计阶段。

```text
M0-1 仓库基线（许可/workspace/工具链/前端骨架/Windows 构建路径打通）
  ├── M0-2 渲染可行性 spike ★最高风险
  ├── M0-3 RAW 解码 spike
  ├── M0-4 存储基准 spike
  ├── M0-5 缩略图吞吐 spike
  └── M0-6 前端骨架与虚拟化 spike
        └── M0-7 架构定稿 + 移交 UI 设计阶段
```

**四条贯穿全阶段的纪律**：

1. **spike 代码一律写进 `crates/raybend` 的正式模块**，不写临时脚本、不写 `src-tauri` 里的一次性代码。理由是 spike 的结论要直接长成 M1 的模块。唯一例外是渲染 spike 的**调试窗口**：窗口创建放 `src-tauri`，图形代码仍在 `crates/raybend`。
2. **每个 spike 必须留下可复现命令与数据**，写进 `implementations/2026-09-15_M0-<n>_<name>.md`。没有数字的结论不算结论。
3. **选型已定但不在 M0 引入**：组件层用 **Ark UI**（`@ark-ui/solid`）、图标用 **Tabler**（`@tabler/icons-solidjs`），实际引入发生在 UI 设计阶段产出界面稿之后。M0 的前端只用 Solid + Tailwind + 手写虚拟化，避免过早绑定。
4. **只用 pnpm 与 cargo**，不引入 npm/yarn/bun 等第二套工具链。

**渲染 spike 的窗口策略**：**不动主窗口**。M0 期间主窗口保持不透明、正常样式；渲染 spike 用 `WebviewWindowBuilder` 另开 `label = "spike-viewport"` 的调试窗口（`transparent: true`）。即使「透明挖洞」彻底失败，主窗口与后续设计工作也不受影响，退路代价可控。
